# Docker inside a Sandbox runs under the Sysbox runtime, with an explicit `--privileged` fallback

Agents routinely need `docker` for the projects they work on (databases, compose stacks, integration tests); without it they improvise (e.g. installing Redmine bare on the Sandbox instead of running its container). A Sandbox is an ordinary Docker container, so `dockerd` inside it fails: adding `CAP_NET_ADMIN` only fixes the bridge; the daemon also needs mount, cgroup and namespace privileges (`CAP_SYS_ADMIN`, unconfined AppArmor/seccomp), which in stock Docker means `--privileged`, i.e. root-equivalent on the host. Sessionboxer therefore runs Docker-enabled Sandboxes under the [Sysbox](https://github.com/nestybox/sysbox) container runtime when the host has it, and otherwise falls back to `--privileged` while telling the user in every surface that the isolation boundary is gone.

## Considered Options

- Mount the host's `/var/run/docker.sock` into the Sandbox (rejected): trivial, but the Agent then controls the host daemon (root-equivalent), its containers run outside the Sandbox, and `/workspace` paths do not exist on the host, so bind mounts break. It also violates ADR-0005's spirit: the Sandbox would reach host resources directly.
- Docker-in-Docker with `--privileged` only (rejected as default, kept as fallback): self-contained and works everywhere, but a privileged container can escape to the host; it must be an explicit, warned choice.
- Sysbox runtime (chosen): `sysbox-runc` gives the container its own user namespace, a virtualized `/proc` and `/sys` (FUSE), shiftfs/ID-mapped mounts and a mounted `/var/lib/docker`, so an unmodified `dockerd` runs inside without `--privileged` and without weakening isolation. Cost: a one-time host install (`sysbox-ce` .deb, Linux only, kernel 5.12+), and Sysbox restrictions inside the Sandbox (no raw device access, some `/proc` writes denied).
- Rootless Docker inside the Sandbox (rejected): still needs `newuidmap`/user namespaces the outer container does not grant, and fuse-overlayfs performance is poor.

## Consequences

- A `DockerMode` per Session: `none` (default), `sysbox`, `privileged`. It is fixed at creation, persisted (`sessions.docker_mode`, migrated with a default of `none` for existing rows) and shown in the session header, the sidebar list and `sessionboxer ls`.
- Settings gain `dockerInSandbox` (default off) as the default for new Sessions; New Session and `sessionboxer new --docker/--no-docker` override per Session. `GET /settings` also reports `dockerModeAvailable` (`sysbox` if `docker info` lists the `sysbox-runc` runtime, else `privileged`), re-evaluated on every call so installing Sysbox needs no restart.
- The Control Plane sets `HostConfig.Runtime = "sysbox-runc"` for `sysbox`, `HostConfig.Privileged = true` plus an anonymous volume on `/var/lib/docker` for `privileged` (the nested daemon's overlay layers must not live on the Sandbox's own overlayfs; Sysbox mounts that directory itself). Everything else (no host ports, CPU/memory limits, the `sessionboxer` network) stays as in ADR-0005.
- The image installs `docker-ce`, `docker-ce-cli`, `containerd.io`, buildx and compose from Docker's apt repository and adds `agent` to the `docker` group. The entrypoint starts `dockerd` (via `sudo`) only when `SESSIONBOXER_DOCKER` is set, after moving PID 1 out of the root cgroup so the nested daemon can create cgroup v2 subtrees, and removes stale pid files (`/run` is part of the container rootfs and survives Stop). If the daemon does not answer within 30 s the Sandbox still starts, and the log tail goes to the container's stderr.
- Nested state (images, containers, volumes) lives inside the Sandbox and survives Stop/Resume; Delete removes it with the container. Nested containers reach the network through the Sandbox's own bridge, so the outer ADR-0005 rule (no host ports) holds.
- The warning is shown wherever the fallback applies: the sidebar Settings button carries a ⚠ when Sysbox is missing; Settings and New Session explain `--privileged` next to the Docker toggle; the session header renders the mode in the warning color; the CLI prints a warning to stderr after `new`.
- The briefing tells the Agent to test `docker info` and, when it fails, to ask the user to enable Docker for a new Session instead of trying to start a daemon or add capabilities.

## Spike result (M7)

Host: Ubuntu 22.04, kernel 6.8, Docker 29.7. `sysbox-ce_0.7.1` installed; `docker info` lists `sysbox-runc`. The unmodified `sessionboxer/sandbox:dev` image started with `--runtime=sysbox-runc --network sessionboxer --cpus 2 --memory 4g`: Xvfb/xfce/x11vnc/noVNC came up as usual and the computer-use MCP took screenshots; the container had a private user namespace (`0 165536 65536`) and `sysboxfs` FUSE mounts on `/sys` and `/proc`. With Docker's packages installed inside, `dockerd` started with `overlayfs` on cgroup v2, `docker run --rm hello-world` printed its banner and an Alpine container fetched `https://example.com`. `docker stop` + `docker start` of the Sandbox kept the nested images. Verification through the Control Plane for all three modes is recorded in the M7 commit message.
