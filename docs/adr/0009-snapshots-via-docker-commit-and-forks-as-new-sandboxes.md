# Snapshots are `docker commit`s taken after every Agent turn; a fork is a new Session on a new Sandbox started from one of them

Users want to branch a conversation ("try approach B from here while A continues") and to go back to how the box looked at an earlier point. Both need a copy of the Sandbox state at a moment in time, not just the transcript: files, installed packages, browser profile, and the Provider's own session store (Claude's `~/.claude/projects`, Devin's local session data), which is what makes the Agent "remember" the conversation. A Sandbox is a Docker container, so `docker commit` gives exactly that copy, cheaply (overlay layers, ~1-3 s, container paused meanwhile). Sessionboxer therefore takes a Snapshot automatically after every completed turn (a default-on Setting), stores its metadata in SQLite, and implements a fork as a *new* Session whose Sandbox is created from the Snapshot image.

## Considered Options

- Fork with Claude's native ACP `session/fork` inside the same Sandbox (rejected as the general mechanism, kept as a possible later refinement): highest conversation fidelity and supports forking at a specific assistant message (undocumented `_meta.jetbrains.air.fork.messageId`), but Devin has no fork, and two Sessions on one Sandbox breaks one-Sandbox-per-Session: shared `/workspace`, one mouse, refcounted Stop/Delete.
- Replay the transcript into a fresh Session's first prompt (rejected as default, remains the conceptual fallback): works for any Provider but loses tool results and screenshots, costs tokens, and the files would still have to come from somewhere.
- Snapshot the container and start the fork from it (chosen): filesystem and Provider state come for free with the image; the Daemon in the new Sandbox finds its state file and the Provider's session store and resumes the conversation as after Stop/Resume; the two Sessions are fully independent afterwards. Cost: disk for the layers, a pause of the source container per commit, and `docker commit` snapshots the whole rootfs, so anything the Agent wrote outside `/workspace` is included too (desired).
- Volume-based snapshots (`/workspace` only) (rejected): misses installed packages and the Provider's session store, which are the whole point.

## Consequences

- `Snapshot { id, sessionId, ordinal, reason: "turn" | "manual", imageTag, imageId, eventSeq, sizeBytes, queuedMessages, createdAt }` in a new `snapshots` table (cascade-deleted with the Session). Images are tagged `sessionboxer/snapshot:<sessionId>-<ordinal>` and labelled `sessionboxer.snapshot=<id>`; `sizeBytes` is the sum of the layers the image adds on top of the base image as Docker reports them (`image history`), so shared layers between Snapshots of one Session are counted once per Snapshot, not once physically. `eventSeq` ties the Snapshot to a point in the transcript; `queuedMessages` records what was in *Saved for later* at that moment so a fork can pick one of them later.
- Ordering after a turn is fixed: store `turn_ended`, set the Session idle, take the Snapshot, then pump the queue. That way a Snapshot never contains the filesystem effects of the *next* queued prompt, and forking at Snapshot *n* plus "send queued message *k*" reproduces what the queue would have done, on a different box.
- Snapshots of one Session are serialized (a per-Session promise chain); a manual Snapshot requested during a turn waits for nothing but the previous Snapshot and captures the box mid-turn (`eventSeq` = last event so far), which is allowed.
- `docker commit` copies the container's environment, including the injected Provider token, into the image config. The commit passes `--change "ENV <var>="` for every variable `providerEnv()` injects, so Snapshot images never carry a usable credential; the fork's container gets the current token injected at creation like any other Sandbox.
- Settings: `autoSnapshot` (default `true`, applies to existing Sessions immediately) and `snapshotKeep` (default 10, `0` = unlimited). Pruning removes the oldest `turn` Snapshots beyond the limit; it never removes manual Snapshots or a Snapshot some Session was forked from (`workspaceSource.type === "fork"` references it). Deleting such a Snapshot by hand is a 409. Deleting a Session removes its Snapshot images unless a fork's container still uses them; a GC at startup removes labelled images no row references.
- Sizes in the UI: `Session.diskBytes` is the container's writable layer (`SizeRw` from `inspect?size=1`), refreshed on load, create, Stop, Resume and after each Snapshot; `snapshotBytes`/`snapshotCount` are aggregated in the Session query. The sidebar shows "`<machine> machine · <total> in <n> snaps`" under each title, with the tooltip explaining that these are logical Docker layer sizes.
- Fork (`POST /sessions/:id/fork { snapshotId, title?, prompt?, savedMessages[] }`): a new Session with `workspaceSource: { type: "fork", sessionId, snapshotId, label }`, events copied up to `eventSeq` (status events excluded) plus a `forked` event, the chosen saved messages copied into its own queue, the optional prompt sent as soon as the Daemon is up, and the Sandbox created from `snapshot.imageId` with the same Provider, Docker mode and limits. The origin Session, its Sandbox, its ACP conversation and its queue are not touched.
- The Provider state copied into the fork is loaded under a fresh Sandbox, so the ACP session is resumed (`session/load`) by the new Daemon exactly as after Resume. The same ACP session identity must never be opened by two live Sandboxes at once: the Devin CLI refuses ("Session ... is already open in another process"), and Claude would write two histories into one store. Since each Session owns one Sandbox this cannot happen through the Control Plane.
- Snapshots are not migrations: a Snapshot image is tied to the base `sessionboxer/sandbox:dev` layers it was committed on. Rebuilding the base image does not affect existing Snapshots (their layers stay), but a fork from an old Snapshot runs the old Daemon and Provider CLI versions baked into it.

## Verified (M8)

Claude and Devin Sessions on this VM: a turn that wrote `/workspace/alpha.txt` produced Snapshot #1 (`<1 MB` layer, ~1.3 s commit, token blanked in the image config: `CLAUDE_CODE_OAUTH_TOKEN=`). Forking at #1 with a queued message as first prompt started a new Sandbox that had the file, answered from the inherited conversation, and ran the message, while the origin's transcript, queue and Snapshot list stayed unchanged. Stop/Resume of both origin and fork; Snapshot deletion of a fork origin refused (409); metadata survived a Control Plane restart; disabling `autoSnapshot` stopped new automatic Snapshots without a restart. Recorded UI run in the M8 commit message.
