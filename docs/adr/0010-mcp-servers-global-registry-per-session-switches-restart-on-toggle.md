# MCP servers: a global registry, per-Session switches, applied by restarting the Agent in place

Users want to give the Agent more tools than the built-in `desktop` MCP server, configure them once, choose per Session which are on, and flip them at any point of a Session. The research in `docs/research/mcp-servers.md` established the constraints: Claude (`claude-agent-acp`) takes its server list over ACP at `session/new`/`session/load` and cannot change it mid-session; Devin's model only sees servers from `~/.config/devin/mcp_config.json`; both re-read the list only when the Agent process starts; both honour `tools/list_changed`, so an always-on gateway MCP that proxies the others would allow instant toggles at the price of renaming every tool and proxying every call.

## Considered Options

- Per-Session configuration only (rejected): the same server would have to be typed for every Session, and secrets would live in every Session row.
- A gateway MCP inside the Sandbox that proxies user servers and emits `tools/list_changed` (rejected for now, kept as a later refinement): instant toggles, but tools appear as `gateway__server__tool`, every call is proxied, and Devin's config still has to be written before start.
- Restart the Agent with the new list and reload the same ACP session (chosen): ~1 s for Claude, a few seconds for Devin, conversation kept via `session/load` (the same path Stop/Resume uses), tools keep their native names. A toggle during a turn cannot restart the Agent without killing the turn, so it is deferred to the end of the turn.

## Consequences

- Registry: `Settings.mcpServers: McpServerDef[]` in `~/.sessionboxer/config.json` (`{ id, name, transport: stdio|http|sse, command, args, env[], url, headers[], enabledByDefault }`, `env`/`headers` entries carry a `secret` flag). Names are `[a-zA-Z0-9][a-zA-Z0-9_-]*`, unique, and `desktop`/`sessionboxer` are reserved. The public shape (`PublicMcpServerDef`, what `/api/settings` returns and the UI edits) replaces every set secret value with `null`; the UI sends `null` back to keep it and a string to replace it (`mergeMcpServers`). Secret values therefore never reach the browser after being typed.
- Per Session: `Session.mcpEnabled: string[]` (registry ids, SQLite column `mcp_enabled`) and `Session.mcpPending` (a change is waiting for the turn to end). New Sessions default to the `enabledByDefault` ids unless the request says otherwise; forks copy the origin's ids. Ids that no longer exist in the registry are dropped when read.
- Resolution happens in the Control Plane: `resolveMcpServers()` turns ids into full definitions (secrets included) and rewrites `localhost`/`127.0.0.1`/`::1`/`0.0.0.0` URLs to `host.docker.internal`, which every Sandbox gets via `ExtraHosts: host.docker.internal:host-gateway`. The resolved list goes to the Daemon over `_sessionboxer/mcp/set` on every Daemon connect (so a Sandbox restarted from a Snapshot or Stop/Resume gets the current set), on a Session PATCH with `mcpEnabled`, and to all live Sessions when the registry changes.
- Daemon: waits for the first `mcp/set` before starting the Agent (30 s fallback to no user servers, for Control Planes that predate this); always prepends the built-in `desktop` server; passes the list as ACP `mcpServers` to Claude on `session/new` and `session/load`; for Devin writes `mcp_config.json` before spawning `devin acp`. On `mcp/set` with a different list while idle it kills the Agent process, restarts it and reloads the ACP session (result `applied: true`); during a turn it stores the list and applies it right after `turn_ended` (`applied: false`, `DaemonStatus.mcpPending`). Applications are serialized on one promise chain. A `mcp_changed { servers }` event is emitted when a set takes effect; the UI renders it as a transcript marker.
- Devin's config file lives on tmpfs (`/dev/shm/sessionboxer/mcp_config.json`, mode 0600) with `~/.config/devin/mcp_config.json` a symlink to it, so `docker commit` captures a dangling symlink and no secret; the image still ships a static file with only `desktop` for Daemons that predate this. Claude receives secrets over ACP only; `claude-agent-acp` puts them on the `claude` command line (`--mcp-config`), so they are visible in `ps` inside the Sandbox, which is the Agent's own trust domain anyway (ADR-0003). Neither the Control Plane log nor Session rows contain secret values.
- A Daemon that does not implement `mcp/set` (a Sandbox created before this change) makes a toggle fail with a 502 pointing at Stop/Resume, which copies the current Daemon into the box.
- UI: Settings gets an "MCP servers" section (cards, inline edit form, `Import JSON…` for `{"mcpServers": {...}}` blobs with credential-looking keys pre-marked secret); New Session gets a checkbox picker; the Session header gets an "MCP" button with a count and a *pending* label, opening a dialog with a switch per server.
- Image: `uv`/`uvx` installed system-wide (most Python MCP servers are launched as `uvx <package>`); `npx`, `node`, `python3` were already there.

## Verified (M9)

On this VM against a host-side streamable-HTTP MCP server that requires a bearer header: Claude and Devin Sessions created with it enabled listed it and called its tool through `host.docker.internal` (host log confirmed the call); the public Settings API returned the header as `null` while `config.json` held the value; toggling while idle removed it, added `uvx mcp-server-fetch`, and the Agent still recalled the earlier answer (`--resume`/`session/load` observed); toggling during a turn set `mcpPending` and applied after `turn_ended` in that order; a fork inherited the enabled ids; Stop/Resume re-sent the set; a Snapshot image contained only the dangling `mcp_config.json` symlink and no secret. Recorded UI run (Settings CRUD, import, validation, picker, header dialog, pending state, Desktop regression) in the M9 commit message.
