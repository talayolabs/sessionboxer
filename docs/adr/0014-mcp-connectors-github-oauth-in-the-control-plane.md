# MCP connectors: preset servers that log in with OAuth, GitHub first, several entries per kind

Registering GitHub's remote MCP server (`https://api.githubcopilot.com/mcp/`) by hand means creating a token on GitHub and pasting it as an `Authorization: Bearer …` header (ADR-0010). The request was a GitHub-branded button that runs the OAuth login instead, reusable for more "special" MCP servers later, and the same server addable more than once so different GitHub accounts can be used side by side.

Probing GitHub: its protected-resource metadata points at `https://github.com/login/oauth`, whose authorization-server metadata lists only the authorize, token and device endpoints, with **no dynamic client registration**. So unlike most remote MCP servers a client cannot self-register; every MCP host ships its own pre-registered OAuth App, and `claude-agent-acp` / `devin acp` cannot log the Agent in to GitHub's server on their own. The login therefore has to be run by the Control Plane and the resulting token handed to the Agent as a plain header, which is what it already gets for any HTTP server.

## Considered Options

- Let the Agent do the MCP OAuth handshake (rejected): needs a registered client the Agents do not have, and the token would live in the Sandbox (snapshots).
- A `github` transport with GitHub-specific code all over the registry (rejected): the next connector would copy it.
- **Connectors as presets on top of the MCP registry (chosen)**: `McpServerDef.connector: { kind, account, connectedAt, expiresAt } | null`; a `CONNECTORS[kind]` table with label, URL, scopes, token header and a default Client ID; a `Connectors` module in the Control Plane running the OAuth flow and writing the token into the entry's secret header. The Daemon sees an ordinary `http` server with a `Bearer` header (`McpServerSpec` omits `connector`). One entry per login: `connector.kind` is not unique, names are.
- Which GitHub OAuth grant:
  - **Device Flow by default (chosen)**: needs only a Client ID, works from any host name, no callback registration per install. The UI shows `github.com/login/device` and a `XXXX-XXXX` code, the Control Plane polls `access_token` (`authorization_pending`, `slow_down` adds 5 s, `access_denied`, `expired_token`).
  - **Authorization Code + PKCE when a Client secret is configured (chosen as the alternative)**: GitHub's OAuth Apps still require the secret at the token endpoint, so this only works for a user who registers their own app; callback `GET /api/connectors/github/callback` on the Control Plane, `state` = flow id, S256 challenge.
  - Refresh tokens (deferred): the OAuth App has "expire user access tokens" off; if enabled, `expiresAt` is recorded and the card shows *token expired* with Reconnect.
- Client registration: Sessionboxer ships the Client ID of a public "Sessionboxer" OAuth App (Device Flow enabled) so the button works out of the box; `Settings.connectors.github.clientId/clientSecret` override it (the secret is write-only, `clientSecretSet` in the public view).

## Consequences

- Protocol: `CONNECTOR_KINDS = ["github"]`, `CONNECTORS` preset table (URL, `readonlyUrl`, scopes, `defaultClientId`, `tokenHeader`), `McpConnector`, `McpServerDef.connector`, `Settings.connectors`, `PublicSettings.connectors.github { clientId, clientSecretSet }`, `ConnectorStartRequest { serverId | null, name }`, `ConnectorFlow { id, kind, serverId, mode: device | redirect, url, userCode, verificationUri, expiresAt, status, error, server }` (`server` is the public, redacted entry).
- Control Plane: `POST /api/connectors/:kind/start` creates the entry (or reuses `serverId` for Reconnect) with an empty secret `Authorization` header, stores it immediately, and returns the flow; `GET /api/connectors/flows/:id` for polling; `GET /api/connectors/:kind/callback` for the redirect flow (small HTML page, closes itself); `POST /api/connectors/servers/:id/disconnect` blanks the header and account but keeps the entry. On success `GET https://api.github.com/user` gives the `login` shown as *Connected as @login*. Flows live in memory for 15 min; the token, secret and PKCE verifier never appear in flows, logs (name/kind/mode only) or the callback page. `mergeMcpServers` keeps the connector state across a Settings save (secrets arrive as `null`) and clears the account if the user removes the token header by hand. Tokens are ordinary secret headers, so the existing snapshot redaction covers them.
- Web: **Add GitHub** (octocat mark) next to Add / Import JSON; `ConnectorDialog` (unique name, device code with Copy / Copy & open GitHub, redirect status, connected result, errors); connector cards show icon, *Connected as @login* / *Not connected*, Connect/Reconnect, Disconnect, Edit, Delete; `summarize()` shows `GitHub · @login` in the New Session picker and the Session MCP popover. Settings → **GitHub login (OAuth App)**: Client ID, write-only Client secret with a *Forget* checkbox. Connector changes are saved by the Control Plane at once (no Save needed), and the form mirrors them.
- Adding a connector = a `CONNECTORS` row, an icon case and, if its OAuth differs from GitHub's, a branch in `connectors.ts`; servers with dynamic client registration could later skip the baked Client ID.
- Not done: read-only variant toggle (`/mcp/readonly` is in the table, no UI), refresh tokens, GitHub Enterprise hosts, persistence of pending flows across a Control Plane restart.

## Verified (M12)

`Connectors` against a fake GitHub (`.local/connectors-test.mjs`, monkey-patched `fetch`): device start with the default Client ID and scopes; polling through `slow_down` → `authorization_pending` → token; `/user` lookup; token stored as `Bearer …` in the private entry and `null` in the public view; two entries (`github-work` → alice, `github-personal` → bob) with independent tokens; duplicate and reserved names refused; `resolveMcpServers` hands the Daemon the bearer header without `connector`; a Settings-form round trip keeps token and account, removing the header clears the account; Disconnect keeps the entry of one account and leaves the other untouched; `access_denied`; redirect mode once a secret is set (`state`, `S256`, callback URL), bad `state`, GitHub `error` callback, code exchange with `code_verifier` + secret, expiring token recorded, callback replay harmless; forgetting the secret returns to device mode. Live: `POST /api/connectors/github/start` against real GitHub returned a device code for the shipped Client ID. Recorded browser run: button and icon, dialog with name validation, device-code screen and copy controls, reconnect on an existing entry, two entries surviving Save/reload with no token shown, New Session picker, OAuth App settings (secret write-only, forget), redirect mode with a secret set, cleanup; console clean, Control Plane log free of tokens. Not tested: an authorized login end to end (no GitHub account in the test environment) and the Agent calling GitHub tools with the stored token.
