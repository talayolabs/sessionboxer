# File references in the chat open in Remote VS Code, through a built-in extension the Daemon talks to

Agents name files all the time ("the bug is in `src/App.tsx:42`", a **Read** tool row, a diff), and the Code pane shows the same Workspace in VS Code, but getting from one to the other meant retyping the path in Quick Open. The user asked for the references to be clickable, landing on the file (and line) in the editor.

## Options for driving the editor

- **Reload the iframe with a URL parameter**: openvscode-server's workbench does not take a file to open on its URL (only `?folder=` / `?workspace=`; `vscode://file/...` links are for the desktop app), and a reload would lose the editor state anyway.
- **`postMessage` into the iframe**: the web workbench listens for no such message; embedding hosts extend it with a *workbench construction options* bundle, which openvscode-server does not expose.
- **The VS Code API through an extension**: `vscode.window.showTextDocument(uri, { selection })` does exactly this, in the connected window, without reload. The extension needs a way to receive the request; a loopback HTTP endpoint inside the box is the smallest.

The third is what is built.

## Decisions

- **Built-in extension** `sessionboxer` in `/opt/openvscode-server/extensions/` (built-in, so it is there on every window and cannot be uninstalled from the UI; no marketplace involved; `extensionKind: ["workspace"]`, so it runs in the server-side extension host next to the files). On activation it listens on `127.0.0.1:${SESSIONBOXER_CODE_OPEN_PORT}` (7101) for `POST /open` with `{ path, line?, column? }` (1-based) and opens the document with the selection at that position, revealed in the centre; line is clamped to the document. The port is loopback inside the Sandbox's network namespace, so only processes in the box can reach it. If the port is taken (a second window's extension host: openvscode-server starts one per connected window, the first keeps the port), it retries every 2 s so the endpoint moves to a surviving host when the first window closes.
- **The Daemon is the trust boundary**: `_sessionboxer/code/open` (`CodeOpenParams`) resolves the path against `/workspace` and refuses anything that leaves it (`../`, absolute paths elsewhere) before touching the extension; it starts openvscode-server if needed and, because the extension host only exists once a window is connected, retries the POST for up to 45 s ("VS Code has no window connected…" after that). Control Plane: `POST /api/sessions/:id/code-server/open` → `SessionManager.codeOpen`.
- **Web side**, in `apps/web/src/file-links.ts`: a reference is a Workspace-relative or `/workspace/...` path (optionally `./`) to a file with an extension or a well-known name (`Dockerfile`, `Makefile`, `.env*`, `.*rc`, …), with an optional `:line[:col]` or GitHub-style `#Lline[Ccol]`. In prose a bare filename without a folder (`index.ts`) counts only with a `:line` (too many false hits otherwise); `example.com`-like names and paths whose first segment looks like a host are skipped; video/image/audio/PDF paths are left to the attachment cards (Markdown and Mermaid files are code too, so they get both). `rehypeFileLinks` marks references in text nodes, inline `code` and Markdown links (`data-file`, `data-line`, `data-column`), skipping `pre` and existing anchors; `Markdown` renders those, and Workspace-file links, as `FileLink`. Tool rows link the paths in their title and, when the title names none, the file from ACP `locations` (now kept in the transcript model), the raw input (`file_path` with Claude's `offset` as the line) or a diff; diff blocks link their path.
- **Navigation**: `FileLink` is a `span[role=link]` (so it can sit inside the tool header button) calling the `OpenFile` context; the Session view provides it, switches the pane to **Code** and hands `CodePane` a target (with a nonce so the same link works twice). `CodePane` calls `codeOpen`, shows "Opening path:line…" in its toolbar meanwhile and any failure in its error banner. Without the context (no Session around) the references render as plain text.

## Consequences

- Clicking `src/App.tsx:42:7` in a reply, a prompt or a tool row switches to the Code pane with the file open and the cursor at line 42, column 7, also when VS Code was not started yet (the click starts it; the open waits for the window). Verified live in the browser and over the API, including `/workspace/...` and `#L` forms, path containment refusals and a missing file (VS Code's own error is surfaced).
- The extension is copied into every Sandbox before it starts, like the Daemon (`SANDBOX_SYNC` in the Control Plane's `docker.ts`), so Stop → Resume is enough for boxes created from an image that predates it; the image build carries it too. When a box still lacks it (skipped because its image has no openvscode-server), the open fails at once with a message naming the cause instead of waiting for a listener that will never appear. Otherwise the endpoint exists only while a window is connected, so a link clicked with the iframe not yet loaded waits rather than fails.
- Text nodes of agent output are scanned with a regular expression on every render of a message; the patterns are anchored on whitespace/punctuation and cheap, but a very long message re-renders its links each time the Markdown re-renders (streaming chunks), as the rest of the Markdown does already.
- Paths the agent names that do not exist yet ("I will create `src/new.ts`") are links too; clicking them shows VS Code's "unable to read file" in the banner. Creating the file on the fly was left out on purpose (a click should not write into the Workspace).
