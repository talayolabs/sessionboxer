# An embedded Cloudflare quick tunnel so a phone gets in with one QR scan

After stage 1 (ADR-0033) the Control Plane can be reached remotely, but every transport in the README asks the phone for something first: joining a Headscale/Tailscale network (an app, a login server URL, a registration), or a domain, a Cloudflare account and DNS for a named tunnel. The user wants the laptop at home reachable from the phone with *only* "click Pair, scan, running" — no app, no VPN enrolment, no DNS or certificates — and chose an embedded Cloudflare quick tunnel over a Headscale join button with our own certificates. Cloudflare's `cloudflared tunnel --url <origin>` without an account gives a random `https://<four-words>.trycloudflare.com` that any browser can open, with a real certificate; `cloudflared` dials out, so nothing is opened on the home router. Verified on this machine before building: the public URL reaches the local listener with the tunnel hostname as `Host` and `X-Forwarded-For` / `X-Forwarded-Proto: https` set by `cloudflared`.

## Decision

**A `quickTunnel` setting runs `cloudflared` as a child of the Control Plane.** `QuickTunnel` (`apps/control-plane/src/tunnel.ts`) spawns `cloudflared tunnel --url <LOCAL_ORIGIN> --no-autoupdate --metrics 127.0.0.1:0` (`--no-tls-verify` added only when the Control Plane serves HTTPS itself); the arguments are fixed and the origin is the Control Plane's own listener, nothing from the UI reaches the command line. Its output is watched for the first `https://[a-z0-9-]+\.trycloudflare\.com`; state goes `off → starting → up`, or `error` with cloudflared's last `ERR` line (its startup `WRN`s, such as the UDP buffer size, are not errors and never shown). An exit while enabled restarts it after 2 / 5 / 15 / 30 / 60 s (cloudflared reconnects to Cloudflare by itself; only a dead process needs us); no URL within 45 s kills and restarts it. Switching off, and Control Plane shutdown (`close()` in the exit handler), `SIGTERM` the child. `Settings.quickTunnel` (default `false`) is stored, so the tunnel comes back at the next start — with a new address.

**The binary is found or downloaded, pinned and checksummed, like `gh` (ADR-0016).** `findCloudflared` takes `~/.sessionboxer/bin/cloudflared` or one on the `PATH` that answers `--version`; otherwise `ensureCloudflared` downloads the pinned release (`2026.9.1`; linux amd64/arm64, macOS amd64/arm64 `.tgz`, Windows amd64) from GitHub, verifies the SHA-256 against constants taken from Cloudflare's release notes, and installs it under the Sessionboxer data directory (not a temp dir) with a staged rename. `SESSIONBOXER_CLOUDFLARED_VERSION` selects another release, whose checksums are then read from that release's notes on GitHub (Cloudflare publishes them there, not as a file). The downloaded binary must itself answer `--version` before it is used.

**Runtime state, not configuration.** `PublicSettings.remote.tunnel: TunnelStatus { state, url, error, version }` is what the UI shows; `pairingOrigin(remote)` (protocol) is the tunnel URL while `state === "up"`, else `remote.publicUrl` — so the QR and link from **Pair another device** carry the tunnel address as soon as it is up, and fall back to the configured one otherwise. `SESSIONBOXER_PUBLIC_URL` is not rewritten: the GitHub OAuth callback and the printed startup link stay on the stable address, because the tunnel one is gone at the next start. Changes are pushed over the UI feed as `{ type: "remote", remote }` (`SessionManager.notify`), so the switch turns from *starting…* to the address without polling; startup also logs a pairing link on the tunnel URL like it does for the local one.

**Trusting the tunnel's forwarded headers without `SESSIONBOXER_TRUST_PROXY`.** `cloudflared` connects from this machine and keeps the visitor's `Host`. `Auth.forwarded(c)` therefore believes `X-Forwarded-*` on a request when `trustProxy` is set *or* the request's `Host` equals the tunnel hostname currently up *and* the TCP peer is loopback (`getConnInfo`). That is what marks the phone's cookie `Secure` (Cloudflare terminated HTTPS), records its real address, and lets the cross-origin check accept `Origin: https://<tunnel>`. Only a process on this machine could forge such a request, which could already do anything; a LAN client cannot, since the peer is not loopback. Trust is scoped to the one hostname and lapses the moment the tunnel is down.

**UI.** In **Settings → Devices and remote access**, a **Share over the internet (Cloudflare quick tunnel)** checkbox stored at once (not with the form's Save), *starting…*, the address with **Copy** when up, the last error in red while down, and a sentence on what the pairing link points at. The explanatory text states the trade-offs: public address behind the same login, traffic through Cloudflare, new address every start.

## Considered Options

- **A "Join the tunnel" button for Headscale plus Let's Encrypt DNS-01 certificates** (the alternative offered): keeps traffic private, but the phone still installs Tailscale and enrols once, and the user needs a Cloudflare API token for the certificate. Offered; the user chose zero steps on the phone.
- **Rewrite `SESSIONBOXER_PUBLIC_URL` to the tunnel URL** (rejected): it would move the OAuth callback and every configured link to an address that dies at the next start.
- **Trust forwarded headers whenever the peer is loopback** (rejected): a local reverse proxy that is *not* configured with `SESSIONBOXER_TRUST_PROXY` would then be trusted implicitly; the check is bound to the tunnel hostname instead.
- **`cloudflared` as a system service / Docker container** (rejected): the point is no extra installation; a child process that stops with the Control Plane is also what makes "switch off = gone" true.
- **A named Cloudflare Tunnel from the UI** (not now): needs a Cloudflare account, a domain and DNS; it stays the documented path to a permanent address.

## Consequences

- One click on the laptop, one scan on the phone; the tunnel URL is public, so the access token is the only wall — the README says so, and pairing codes stay one-use, 5 minutes.
- The address changes at every start of the tunnel; paired phones stay logged in (the cookie is per device) but bookmarks go stale. Quick tunnels have no SLA, are rate-limited and may be changed by Cloudflare; the named tunnel and the private-network paths remain the production advice.
- Traffic passes through Cloudflare (TLS-terminated at their edge, re-encrypted to `cloudflared`); the phone's noVNC, terminal and VS Code sockets survive thanks to the 25 s keepalives from stage 1.
- The first switch-on downloads ~40 MB; a machine without a supported release (e.g. Linux armv7, Windows arm64) gets an error telling it to install `cloudflared` itself.
- Verified live: real quick tunnel on this VM, anonymous 401 through it, pairing redeemed from the public URL with a `Secure` cookie, `PUT` accepted with the tunnel origin and refused with a foreign one, the UI feed WebSocket open through Cloudflare receiving the server pings, `cloudflared` killed → `error` → back up at a new address, switch off → process gone; fake-`cloudflared` unit run for parsing, ERR extraction, back-off, timeout, disable and close.
