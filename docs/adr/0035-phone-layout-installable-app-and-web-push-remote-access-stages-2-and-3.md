# A phone layout, an installable app and Web Push (remote access stages 2 and 3)

Stage 1 (ADR-0033) and the quick tunnel (ADR-0034) get a phone logged in with one scan, but the UI it lands on is the desktop one: a 290 px sidebar on a 390 px screen, the chat squeezed beside a desktop pane, a header of twenty buttons, and a composer that the on-screen keyboard pushes off screen. And a phone that is asleep hears nothing: the "turn ended" and "pull request feedback" notifications are `new Notification` calls from a page that must be open and connected. The research note (`docs/research/remote-access-from-a-phone-or-another-machine.md`, §5–6) planned these as stage 2 (layout, PWA) and stage 3 (Web Push).

## Decision

**One UI, two shells, switched at 800 px (`MOBILE_QUERY`, `apps/web/src/mobile.ts`).** Above it nothing changes. Below it `App` renders the phone shell: the sidebar becomes an off-canvas drawer (☰ in a top bar with the current title and status dot; a backdrop and × close it, and so does picking a session, *New* or *Settings*, because the route changes); the session header keeps only the title, the status badge and a ⋯ button that opens the rest of the header — provider, branch selector, Snapshot, Fork, Pull, MCP, Instructions, Inspect LLM, Stop/Resume, Delete — as a bottom sheet. The header's flex row and the sheet are the *same element* (`.session-actions`, `display: contents` on a desktop, a fixed sheet on a phone), so no action exists twice.

**The chat is a pane on a phone.** `Pane` gains `"chat"`; `SessionView` computes `shown` from the saved pane: on a phone `hidden` means `chat` and exactly one of Chat / Desktop / Code / Terminal / Context / PRs (present when PRs are attached, with the unread count) / an open PR fills the screen, picked from tabs along the bottom; on a desktop `chat` means `hidden` and the chat stays beside the secondary pane as before. The chat element is kept mounted and `hidden` rather than unmounted, so the composer text, scroll position and follow-scroll survive tab switches. The same `localStorage` pane key serves both shells, so a laptop window narrowed past 800 px keeps its pane.

**Heights follow the visual viewport.** `useVisualViewportHeight` writes `--app-height` and `--keyboard-height` from `window.visualViewport` on resize/scroll (skipping pinch-zoom, where `vv.height` shrinks for another reason); the phone shell is `height: var(--app-height)` with `overflow: hidden`, so the on-screen keyboard shrinks the app and the composer stays above it instead of the page scrolling. `interactive-widget=resizes-content` in the viewport meta asks Chrome for the same, `viewport-fit=cover` plus `env(safe-area-inset-*)` on the top bar, the tabs and the sheet keep them clear of notch and home indicator.

**A keyboard for the touch desktop.** noVNC's gestures already work; what a phone lacks is a way to type, and the keys its keyboard does not have. The Desktop toolbar gets a **Keyboard** button (connected sessions only) that opens `DesktopKeyboard` (`apps/web/src/DesktopKeyboard.tsx`): a near-invisible `<textarea>` focused to bring up the phone's keyboard, whose `keydown`s are turned into `rfb.sendKey(keysym, code, down/up)` pairs, with an `input` fallback that diffs the textarea's value for keyboards that only report composition (autocorrect, swipe typing) — each inserted character is sent, each deletion a BackSpace, and the buffer is cleared after a space so autocorrect has nothing to rewrite. A bar above it adds Ctrl, Alt, Shift and Super as *sticky* modifiers (pressed down on the box, released after the next key or when the bar closes), plus Esc, Tab, Enter, Backspace and the arrows. While the bar is open `rfb.focusOnClick` is off so tapping the canvas does not steal focus from the textarea; view-only (the agent working, no *Take control*) disables the whole bar.

**An installable app, without caching.** `manifest.webmanifest` (standalone, dark theme colour, the existing icons) and the Apple meta tags make *Add to Home Screen* / *Install app* produce a full-screen app. The service worker `public/sw.js` is registered from `App` on secure origins; it caches nothing — the UI is served by the Control Plane and must always match its API — it only handles `push` and `notificationclick`.

**Web Push, done by the Control Plane itself (RFC 8291 / 8292).** `apps/control-plane/src/web-push.ts` implements the payload encryption (ECDH on P-256 with an ephemeral key, HKDF, AES-128-GCM, `aes128gcm` content coding) and the VAPID JWT (ES256) with Node's `crypto` only, checked against the RFC 8291 test vector; no `web-push` dependency. VAPID keys are generated once into `config.json` (`Settings.vapid`, stripped from `PublicSettings` like the other secrets; only the public key goes to browsers via `GET /api/push`). Subscriptions live in `push_subscriptions` (one per device, `REFERENCES devices ON DELETE CASCADE`), created by `PUT /api/push` and removed by `DELETE /api/push` — both refused for a bearer-token principal, since a subscription belongs to a browser; the status endpoint never returns endpoint or keys. Revoking a device or logging out deletes its subscription with the device; a push service answering 404 or 410 deletes it too. `PushNotifier.send` targets every subscription *except* devices whose UI WebSocket says its page is visible (`UiClientMessage { type: "visibility" }`, sent on `visibilitychange`); a phone that is asleep has no visible page. `SessionManager` pushes on `turn_ended` (title, first line of the agent's last message, `#/sessions/<id>`) and `PullRequests` on new PR activity (`…/pr/<prId>` for one PR, `…/prs` for several), each in a `try`/`catch` so a push failure can never fail the turn. The service worker's click handler focuses an existing app window and posts `{ type: "navigate", url }` (the page keeps its WebSocket and transcript, only the hash changes) or opens one; `parseRoute` now understands `#/sessions/<id>/prs` and `#/sessions/<id>/pr/<prId>` and turns them into a pane request. The page's own PR notification goes through the same service worker (`registration.showNotification`, Android refuses `new Notification` on pages with a worker) with the same `tag` as the push, so a device that gets both shows one.

**UI.** **Settings → Devices and remote access** gets *Notify this device when a turn ends or a pull request gets feedback* (asks permission, subscribes with the server's key, registers), **Send a test notification**, the reason when it cannot work (not HTTPS; a browser without Push — on iPhone the app must be on the Home Screen first; permission denied) and `notifications on` beside each device in the list that has a subscription.

## Considered Options

- **A separate mobile app or a second React tree** (rejected): one component tree with a media query keeps every feature (attachments, saved messages, branches, context gauge…) available on the phone without a second implementation.
- **Unmount the chat when another tab shows** (rejected): loses the composer draft and the scroll position; `hidden` keeps them and costs nothing since the transcript is already virtual-ish (collapsed groups).
- **The `web-push` npm package** (rejected): 200 lines with Node's `crypto` cover what is needed, verified against the RFC vector, and add no dependency tree to a security-sensitive path.
- **Pushing to every device, including the one looking at the page** (rejected): the phone in hand would buzz for the reply appearing in front of it; visibility over the existing WebSocket is exact and free.
- **A caching service worker for offline use** (rejected): the UI without its Control Plane is nothing, and a stale UI against a new API is a bug generator.
- **noVNC's own `showDotCursor`/touch keyboard** (n/a): noVNC has no on-screen keyboard; its `sendKey` is the intended API for one.

## Consequences

- The phone gets the whole product, one pane at a time; a laptop window narrower than 800 px does too (harmless, and the cheapest way to test the phone shell).
- Web Push needs HTTPS (the tunnel gives it) and, on iPhone, the app on the Home Screen (iOS 16.4+); Safari otherwise reports "unsupported" and Settings says so. Push messages transit the browser vendor's relay (FCM, APNs, Mozilla) as ciphertext.
- The quick tunnel's address changes per start, but a subscription is tied to the push service's endpoint, not to our address, so notifications survive a new tunnel address; only the URL inside a notification is a hash route on whatever origin the app was opened from.
- The VAPID private key is a secret in `config.json` like the access token; `PublicSettings` never carries it. Rotating it is not offered: it would orphan every subscription.
- The `DesktopKeyboard` value-diff path is a heuristic for soft keyboards that do not report keys; hardware keyboards and desktop browsers take the `keydown` path and are exact.
