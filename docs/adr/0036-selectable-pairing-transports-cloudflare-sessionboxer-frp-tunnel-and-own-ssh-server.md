# Selectable pairing transports: Cloudflare quick tunnel, the Sessionboxer frp tunnel, an own server over SSH

ADR-0034 gave the phone a zero-setup way in, at the price of an address that changes at every start and traffic through Cloudflare. The user wants to choose per pairing between that, a **stable address on a server the project runs** (`https://<name>.tunnel-sessionboxer.talayolabs.com`, replacing the Headscale deployment there, which needed an app and a network join on the phone) and **a server of their own** reached with plain `ssh`, and asked for a menu on **Pair another device** that yields the QR for the chosen one. Requirements that stay: nothing to install on the phone, the Sessionboxer login remains the wall, no secret of any transport visible in the UI or the logs.

frp was chosen over rathole for the project server: rathole is a per-port TCP forwarder with no hostname routing, no metrics and a WIP API, while frp routes HTTP by subdomain, has a Login/NewProxy server-plugin hook for a name registry, and exports Prometheus metrics (`frp_server_client_counts`, `frp_server_proxy_counts`, `frp_server_connection_counts`, `frp_server_traffic_in/out`) for Grafana; rathole's own benchmark puts latency within a fraction of a millisecond of frp's, which the two internet hops phone → VPS → laptop dwarf.

## Decision

**One supervisor, three transports.** `SupervisedTunnel` (`apps/control-plane/src/tunnel-base.ts`) holds what ADR-0034 had built into `QuickTunnel`: the `off → starting → up | error` status with `url`, `error`, `version`; `set(enabled)`; spawning a child, watching it, restarting after exit with 2 / 5 / 15 / 30 / 60 s back-off, an optional start timeout, SIGTERM on disable and on Control Plane shutdown; plus the binary helpers (`findBinary` in `~/.sessionboxer/bin` then `PATH`, `download`, `untarFile`, `probeVersion`). `QuickTunnel` (`tunnel.ts`) extends it unchanged in behaviour; `FrpTunnel` (`tunnel-frp.ts`) and `SshTunnel` (`tunnel-ssh.ts`) are the two new ones; `Tunnels` (`tunnels.ts`) owns all three, applies `Settings.tunnels`, reports `TunnelStatuses { cloudflare, sessionboxer, ssh }` and the list of hostnames currently up.

**Sessionboxer tunnel = `frpc` against a small server contract.** The Control Plane asks the configured server (`Settings.tunnels.sessionboxer.server`, default `https://tunnel-sessionboxer.talayolabs.com`) for `GET /api/v1/info` — `{ service: "sessionboxer-tunnel", domain, frps: { host, port, tls, token }, nameRule, frpVersion, grafana }` — and `GET /api/v1/names/<name>` → `{ name, available, reserved }` (both schemas in the protocol package, `TunnelServerInfo`, `TunnelNameCheck`; `TUNNEL_NAME_RE` mirrors the server's rule: 3–40 lowercase letters, digits, dashes, not at the ends). It then writes `~/.sessionboxer/frpc.toml` (mode 600) with `serverAddr/serverPort` from the info, `user = <name>`, `metadatas.secret = <secret>`, `metadatas.client = "sessionboxer"`, `transport.tls.enable = true`, `transport.poolCount = 4`, `loginFailExit = false`, and one `[[proxies]]` of `type = "http"` with `subdomain = <name>` to `LOCAL_ORIGIN`, and spawns `frpc -c` on it. Up is frpc's `start proxy success`; frpc's `connect to server error` / `start error: …` (the server's registry answers `router config conflict` for a taken subdomain and refuses a wrong secret at login) / `login to server failed` become the shown error. The **name** defaults to the machine's hostname, sanitised to the rule; the **secret** is 32 random bytes generated into `config.json` by `ensureTunnelSecret` at first start and never returned by the API (`PublicTunnelSettings.sessionboxer.secretSet`), never accepted from the UI (`TunnelSettingsUpdate` omits it), never logged. The server binds a name to the hash of the first secret that logs in with it, so the URL is stable for as long as `~/.sessionboxer` exists. `frpc` is found or downloaded like `cloudflared`: pinned `0.71.0`, SHA-256 per platform tarball in the source (linux/darwin, amd64/arm64), `SESSIONBOXER_FRP_VERSION` overrides (then the checksum is read from the release's `frp_sha256_checksums.txt`). Two Control Plane routes back the settings UI: `GET /api/tunnels/sessionboxer/server[?server=]` (info + the name this machine would take) and `GET /api/tunnels/sessionboxer/names/:name[?server=]`.

**SSH = the system `ssh -N -R`.** `SshTunnel` runs the user's own `ssh` (found on the PATH; version from `ssh -V`) with fixed options — `BatchMode=yes` (no prompts to hang on), `StrictHostKeyChecking=accept-new` (the host key is pinned on first use, a changed one is an error shown in the UI, never accepted silently), `ExitOnForwardFailure=yes`, `ServerAliveInterval=15` / `ServerAliveCountMax=3`, `ConnectTimeout=20` — and `-R <bind>:<remotePort>:<local host>:<local port>`, where `bind` is `*` (needs `GatewayPorts` on the server) or `localhost`. Fields from Settings go on the command line only after validation in `applySettingsUpdate` (host: no spaces, `@`, leading `-`; user: no spaces, `@`, `:`, leading `-`; key path: no leading `-`; `IdentitiesOnly=yes -i <file>` when a key file is given, otherwise the agent and default keys), and always after `--`, so none can become an option. Up is ssh's `debug1: remote forward success for:`; ssh's other non-debug output (banner, host-key notes) is ignored, complaints (`Permission denied`, `remote port forwarding failed`, host-key changes) are shown. The URL the QR carries is the configured **public URL** if any (the reverse proxy on the server, with the certificate), else `http://<host>:<remotePort>` when binding on all addresses — and no URL at all when bound to localhost without a public URL, since then nothing on the internet reaches the port: the transport reports that as its error.

**Forwarded headers are believed per tunnel hostname.** `Auth`'s single `tunnelHost` became `tunnelHosts(): string[]` — the hostnames of every tunnel that is up. A request whose `Host` is one of them *and* whose peer is loopback (cloudflared, frpc and ssh all deliver from this machine) has its `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host` trusted; anything else needs `SESSIONBOXER_TRUST_PROXY=1` as before. The origin check on state-changing requests keeps working against the forwarded host, so a request through one tunnel with another tunnel's `Origin` is refused.

**Settings shape and migration.** `Settings.quickTunnel: boolean` became `Settings.tunnels: { cloudflare: { enabled }, sessionboxer: { enabled, server, name, secret }, ssh: { enabled, host, port, user, identityFile, remotePort, remoteBind, publicUrl } }`; `loadSettings` maps an old `quickTunnel: true` to `tunnels.cloudflare.enabled`. `PublicSettings.remote.tunnel` became `remote.tunnels: TunnelStatuses`, broadcast as before on every change. `PUT /api/settings` takes a partial `tunnels` (`TunnelSettingsUpdate`), validates, saves, and calls `Tunnels.apply` — a transport whose configuration changed restarts, one merely left enabled does not.

**UI.** `pairingOrigin(remote, transport)` (protocol) picks the origin for the chosen transport — `remote.publicUrl` for *Local network*, the tunnel's URL only while it is `up`. In **Settings → Devices and remote access**, **Pair another device ▾** opens a menu with the four transports, each with its current address or state; picking one starts it when it is off (SSH refuses until a host is set) and requests a pairing code, and the QR + link appear once the origin exists (until then the section shows *starting…* or the error). Below, one card per tunnel: a switch, its address with **Copy** or its error, and its settings — for the Sessionboxer tunnel the server (queried for `info` when it changes) and the name (availability checked after a pause in typing, the resulting `https://<name>.<domain>` shown), for SSH host, port, user, key file, remote port, bind mode and public URL, with Save / Discard. Help text carries the trade-offs: changing address (Cloudflare), traffic through the project server and how the name is owned (Sessionboxer), `GatewayPorts` and plain `http://` losing clipboard, notifications and the VS Code pane (SSH).

## Consequences

- The phone side stays "scan, tap, logged in" for all four; the trade-off moves to the laptop side, where the menu makes it explicit per pairing.
- Several transports may be up at once, each with its own hostname; a device cookie is valid through any of them. The Control Plane prints a fresh one-time pairing link whenever a tunnel comes up, as before.
- The Sessionboxer tunnel terminates TLS at the project server (Traefik, wildcard certificate via Cloudflare DNS-01) and re-encrypts to `frpc` over frp's TLS; its operators see connection counts and traffic per name in Grafana, and could see content — the same trust as Cloudflare's edge, one party fewer. Latency is the two hops via the server's location.
- Losing `~/.sessionboxer/config.json` loses the tunnel secret and with it the name on the server (the server's operators can release it); the UI says so next to the name.
- SSH over `http://` is deliberately allowed: a working chat and desktop on a phone is better than nothing, and the text says what stays disabled without HTTPS.
- The server side (frps, registry, Prometheus, Grafana, wildcard TLS) lives in `talayolabs/sessionboxer-tunnel`, deployed by Coolify; the Headscale it replaces is gone from that domain and from the README, which keeps Tailscale (with a self-hosted Headscale as a variant) as the private-network option.

## Addendum: the laptop→frps hop is verified

The first version left frps on its own self-signed certificate and `frpc` without `transport.tls.trustedCaFile`, which in frp means `InsecureSkipVerify` — encrypted, but an active MITM between the laptop and the server could have read the tunnel secret at login. Now the server's frps presents the same Let's Encrypt wildcard Caddy serves (read from Caddy's storage, frps restarted on renewal — in the tunnel repository), and the Control Plane writes `~/.sessionboxer/tunnel-ca.pem` — Node's bundled Mozilla roots plus the private CAs of ADR-0015 (`trustedCaBundle`), so a corporate-proxy or self-hosted server still works when its CA is trusted here — and sets `transport.tls.trustedCaFile` to it with `transport.tls.serverName = <frps host>`. Before spawning `frpc` at all, `FrpTunnel` does one TLS handshake to `frps.host:port` with that bundle: an untrusted certificate is reported in Settings as such ("presented a certificate this machine does not trust … the tunnel secret was not sent"), a network error as unreachable, and only a clean handshake leads to writing `frpc.toml`. frpc then verifies every control and work connection itself. Rejected: pinning the leaf or the Let's Encrypt intermediate (both rotate), and trusting the frps certificate on first use (a MITM at first use would win). Consequence: a self-hosted tunnel server must serve a certificate the laptop trusts; the fallback self-signed frps (before `CLOUDFLARE_API_TOKEN` is set) is refused.
