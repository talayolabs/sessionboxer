# Per-Session settings in one object and one dialog

Per-Session configuration had grown in as many places as there were features: the model and options in New Session and the composer footer (ADR-0013), MCP switches behind an **MCP** header button (ADR-0010), the instructions behind an **Instructions** header button (ADR-0022), **Inspect LLM** as a third header button (ADR-0032), the Docker mode decided at creation from a global setting (ADR-0008), the auto-snapshot override in the Snapshots popup (ADR-0009), and the git identity in the New Session form. Each was a flat `Session` field with its own SQLite column, its own `PATCH /api/sessions/:id` key and its own dialog; the Sandbox's CPUs/memory and the snapshot retention had no per-Session value at all. The research note in `docs/research/per-session-settings-in-one-place.md` inventories this.

## Decision

**One `Session.settings` object.** The durable, user-chosen values move under `SessionSettings` in the protocol: `model`, `options`, `inspectLlm`, `mcpEnabled`, `instructions`, `autoSnapshot`, `snapshotKeep` and `sandbox: { dockerMode, cpus, memoryGb, gitIdentity }`. Values that are resolved dynamically against the global Settings are nullable, `null` meaning "follow Settings" (`autoSnapshot`, `snapshotKeep`, `sandbox.cpus`, `sandbox.memoryGb`; `resolveSessionSettings(settings, globals)` gives the effective numbers). Values frozen at creation are stored concrete (`instructions`, `sandbox.dockerMode`, `sandbox.gitIdentity`) so a later Settings change never alters a running Session. What the Daemon owns stays top-level on `Session`: `status`, `containerId`, `error`, `queueRunning`, the `*Pending` flags, `availableOptions`, the snapshot metrics, branches and timestamps.

**One JSON column.** `sessions.settings TEXT` holds the object; `migrate()` backfills it once from the old columns (`model`, `options`, `mcp_enabled`, `instructions`, `inspect_llm`, `auto_snapshot`, `docker_mode`, `git_user_name`, `git_user_email`), which are left in place in existing databases and no longer created in new ones. Nothing else in the table changes.

**One request shape, old shapes folded.** `CreateSessionRequest.settings: SessionSettingsInput` and `ForkSessionRequest.settings` (partial overrides on top of the origin's copy, including the creation-only values — the only way to change them); `UpdateSessionRequest.settings: SessionSettingsPatch` for the live ones (`model`, `options`, `inspectLlm`, `mcpEnabled`, `autoSnapshot`, `snapshotKeep`, `sandbox.cpus`, `sandbox.memoryGb`; `.strict()` so a frozen field is a 400). The flat creation fields the CLI and older clients send (`model`, `options`, `instructions`, `mcpEnabled`, `inspectLlm`, `docker`, `gitIdentity`) remain accepted and are folded into `settings` by `createRequestSettings`. The Daemon side is untouched: `Sessions.edit` pushes MCP → model → options → Inspect LLM in the same order as before, and the `*Pending` flags keep their meaning.

**One form, three modes.** `SessionSettingsForm` (`apps/web/src/SessionSettingsForm.tsx`) renders the sections Agent (Provider read-only, model, options), Instructions, MCP servers & connectors, Inspect LLM (Claude Code only), Snapshots and Sandbox. `create` (New Session) starts from the global defaults, `fork` (a collapsible section of the Fork dialog) from the origin, and `live` (the new **⚙ Settings** button in the Session header, which the phone's ⋯ sheet picks up because it sits in `.session-actions`) saves each control as it changes and shows the creation-only values read-only with **Fork with different settings…** as the way out. `applyNote(status, how)` in the protocol package gives the one wording for what happens next ("Applies when the current turn ends.", "Restarts the Agent in place; the conversation is kept.", "Applies to the next Sandbox built for this Session…"). The MCP, Instructions and Inspect LLM header buttons and their dialogs are gone; the composer footer keeps model and options as quick controls, and the Snapshots popup keeps its auto-snapshot switch (it is opened from the sidebar, for any Session).

## Consequences

- New per-Session settings are a field in `SessionSettings`, a branch in `SessionSettingsForm`, and — when live — a key in `SessionSettingsPatch` handled by `Sessions.edit`; no new column, route key or dialog.
- Effective Sandbox resources (`cpus`, `memoryGb`) come from the Session first, then Settings, when a Sandbox is created, forked or rebuilt; changing them on a running Session applies to the next Sandbox. Snapshot retention is likewise per Session.
- "Back to the Provider's default" (`model: null`) is not offered in the live dialog: the Daemon's `_sessionboxer/model/set` takes a non-empty model, and the Control Plane ignores a falsy one. A Daemon extension would be needed first.
- Reading a legacy database keeps working (the backfill runs once; the old columns are ignored afterwards); a Control Plane downgrade would not see the newer settings.
