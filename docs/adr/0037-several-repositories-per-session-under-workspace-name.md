# Several repositories per Session, each under `/workspace/<name>`

A piece of work rarely lives in one repository: a frontend, a backend, one CI repository per environment, the queue configuration, the documentation. Until now a Session had exactly one `WorkspaceSource` (a git URL, a copied host folder, or nothing) seeded into `/workspace` itself, and everything that knew about "the project" — the clone step, the briefing, the pull-request `#123` shortcut, **Pull to folder** — assumed that single root. The user wants to list several repositories when starting a Session, add and remove them while it runs, and see per repository where it stands; Bitbucket and a shared "Project" entity were explicitly left for later.

## Decision

**`/workspace` stays the root; every repository is a top-level directory in it.** A Session owns `repos: SessionRepo[]` (`id`, `name`, `source: RepoSource` = `{ type: "git", url, ref? } | { type: "copy", path }`, `status: pending | ready | error`, `error`, `git: RepoGitState | null`, `createdAt`). The Sandbox lays them out as `/workspace/<name>`, independent nested git repositories — no meta-repository, no worktrees — so the Daemon's workspace-relative surface (raw files, uploads, tar, containment, VS Code, terminal, snapshots, forks) keeps working unchanged with paths such as `backend/src/foo.ts`, and VS Code discovers the nested repositories by itself. Single-repository Sessions get the same layout (`/workspace/<name>`), not the root, so the agent's rules are the same for every new Session. `<name>` defaults to the URL or folder basename, sanitised to `[A-Za-z0-9_][A-Za-z0-9._-]*` (≤ 100 chars), with `-2`, `-3` on a case-insensitive clash; the user can set it. The manifest `/workspace/.sessionboxer/repos.json` (`{ workspace, repos: [{ name, path, source }] }`) is written by the Daemon whenever the list changes.

**Compatibility by a reserved name.** Sessions created before this carry one repository named `"."` (`WORKSPACE_ROOT_REPO`), meaning the source was seeded into `/workspace` itself; the migration derives it from `workspace_source`. Such a Session shows a notice, cannot take a second repository (409) and cannot have its root removed (400). `CreateSessionRequest.workspaceSource` stays accepted from old clients and becomes one repository; `Session.workspaceSource` remains for the sidebar icon, forks (`{ type: "fork", sessionId, snapshotId }`) and the PR lookup through fork origins. Repositories are a `repos` JSON column on `sessions` (no table: they are read and written as a list, and a Session has at most 50).

**Seeding and live changes are the Control Plane's, inspection and deletion the Daemon's.** At provisioning every `pending` repository is cloned or copied in parallel into `mkdir -p /workspace/<name>` (clone as the `agent` user with the GitHub credentials of ADR-0016 when enabled; copy through `putArchive` + `chown`), each recording its own `ready` / `error` without failing the Session. `POST /sessions/:id/repos` adds one to a running Session the same way (a failed clone deletes the directory and the entry, 502); `DELETE /sessions/:id/repos/:repoId[?force=1]` asks the Daemon to remove the directory. The Daemon (`packages/sandbox-daemon/src/repos.ts`) inspects each repository — branch, dirty tree, `ahead` of upstream (`null` when the branch has no upstream and its tip is on no remote branch), branches whose tips no remote has — on connect and after every turn (`_sessionboxer/repos/inspect`), and refuses `repos/remove` without `force` while `repoWorkAtRisk` says something would be lost. For a *copied* folder the risk is not git's: it is whether the box's changes have been pulled to the host, so the Control Plane computes the sync plan first and answers 409 with the count of unpulled changes; a copy that was pulled (or never touched) goes without confirmation. Additions and removals are recorded as `repo_changed` events, shown in the transcript, and queued as a note on the agent's next prompt ("Repository X was added at /workspace/X"), since the agent otherwise has no way to learn its world changed.

**The agent is told the layout.** The static briefing (`images/sandbox/sandbox-briefing.md`) says `/workspace` is the Session root, each top-level directory an independent git repository, `.sessionboxer/repos.json` the list, git commands run inside the repository they concern, and paths, commits, branches and PRs must say which repository they belong to. The Daemon appends a rendered table of the current repositories (name, path, origin) to the instructions it hands the agent on every session start (system prompt for Claude Code, first-message prefix for Devin, as in ADR-0022).

**Pull requests and sync follow the list.** `PullRequests.workspaceRepos` collects the GitHub `owner/repo` of every git repository of the Session (falling back to `workspaceSource`, through fork origins); a bare `#123` resolves only when there is exactly one, otherwise the user is asked for `owner/repo#123` or the URL; **Address** is offered when the PR's repository is one of them. Sync baselines are per repository (`<sessionId>-<repoId>.json`, the old `<sessionId>.json` for a `"."` root); `GET/POST /sessions/:id/sync` take `repoId`, the Daemon's manifest and tar take the repository directory, and **Pull to folder…** shows a picker when several copied folders exist.

**UI and CLI.** The New Session form lists repository rows (git URL + optional ref, or host folder with **Browse…**, each with an optional name) under **+ Git repository** / **+ Host folder**; none means an empty Workspace. The header shows one chip per repository (`…` pending, `⚠` failed, `●` work at risk, tooltip with branch and state) opening a dialog to add or remove; the sidebar icon summarises the sources. `sessionboxer new` takes several `--git <url>[@ref]` and directories together, `--name` per repository in order, `--empty`, and `ls` prints `/workspace/<name>  origin  (status)` per repository.

## Consequences

- One Session can hold the whole system the user is changing; the agent sees all of it under one root and is told which directory is which. The cost is that "the project" is no longer a fixed path: the agent, the UI and the user say `/workspace/backend` rather than `/workspace`.
- Old Sessions keep working as they were, at the root; the two layouts coexist by the `"."` name rather than by moving files inside running boxes.
- Provisioning of several repositories is parallel, so one private repository that fails to clone leaves the others usable and the failure on its chip.
- Removal never deletes anything on the host or on a remote; it can only lose work inside the box, and only after the user confirms what that work is.
- Not done here: Bitbucket credentials and PRs (a connector like GitHub's, researched separately), a persisted "Project" to reuse a repository set, SSH deploy keys, per-repository git identity.
