# Bitbucket (Data Center) as a Connector: one pasted HTTP access token, `bb` in the box

The GitHub Connector (ADR-0014, ADR-0016, ADR-0027) gives a Session one login for everything: the MCP server, `git clone`/`git push` of private repositories, `gh pr create` and the PRs pane, with the token kept on tmpfs in the box and never in a Snapshot. Teams whose code lives on a self-hosted **Bitbucket Data Center** (`bitbucket.yourcompany.com`, v9.x) had nothing of that: a private clone needed the token embedded in the URL (and thus in the Session's source), pushes and pull requests were out of reach. `docs/research`-style notes (the "Bitbucket connector" design, revisions 1–3) explored Bitbucket Cloud first — Atlassian API tokens, then an OAuth consumer with a click-through grant — before the target turned out to be Data Center, where the picture is different:

- Click-through OAuth exists (incoming application links, with PKCE) but needs a **Bitbucket administrator** to register the application once per instance, with an HTTPS redirect URL by default. That is not something a user can do alone, and the whole point of the Connector is that a user can.
- What a user *can* do alone is create an **HTTP access token** on the profile page (`/plugins/servlet/access-tokens/`), with the permissions and expiry of their choice.
- Data Center's REST is `/rest/api/latest/...` (start/limit paging, `X-AUSERNAME` on every authenticated response, `Authorization: Bearer <token>`), clone URLs are `https://host/scm/KEY/slug.git` and `ssh://git@host:7999/KEY/slug.git`, and git over HTTPS authenticates with the **real username** and the token as password. Nothing of the Cloud code path applies, and there is no `gh` for it.

## Decision

**A `bitbucket` Connector kind that is a login, not an MCP server.** `CONNECTOR_KINDS` gains `"bitbucket"`; its `CONNECTORS` entry has no MCP URL, and `connectorHasMcp(kind)` lets the Control Plane skip such entries when it builds the agent's MCP server list (`config.ts`) while still turning them into `BoxCredential`s. Everything else about Connector entries stays: they live in the MCP servers registry (one card, **Connect**/**Reconnect**/**Disconnect**, the per-Session switch decides which Sessions get the login), the token is a secret `Authorization` header, several entries mean several hosts or accounts.

**Host-aware.** `McpConnector.host` and `BoxCredential.host` (`"github.com"` for GitHub) carry the Bitbucket instance, since there is one per company and the Sandbox may be logged in to more than one. `ConnectorStartRequest` gains `via: "token"` with `host` and `token`.

**One paste, verified.** `ConnectorDialog` asks for the host, links to that host's HTTP access tokens page with the permissions to pick (Project → Read, Repository → Write), and takes the token in a password field. `POST /api/connectors/bitbucket/start` with `via: "token"` runs `verifyBitbucketToken` (`apps/control-plane/src/bitbucket.ts`): a REST call with the Bearer token, the caller's username from `X-AUSERNAME`, then `/users/{name}` for the display name; a wrong host, a Bitbucket Cloud address, a rejected token, a TLS or DNS failure each get a specific message and nothing is stored. On success the flow is already `done`: account and host go on the Connector, the token into the secret header. There is no polling or browser round-trip — the "flow" object is kept only so the dialog and API stay the same shape as GitHub's.

**`bb` in the Sandbox image, `hosts.yml` on tmpfs.** [`talayolabs/bb`](https://github.com/talayolabs/bb) is a `gh`-like CLI for Bitbucket Data Center written for this (HTTP-token login, `auth git-credential`, `api`, `pr create/list/view/checks/comment/approve/request-changes`), bundled into one file and installed in the image from a pinned commit (`ARG BB_REF`). The Daemon's `BbCredentials` mirrors `GhCredentials`: on each `mcpSet` it writes `$BB_CONFIG_DIR/hosts.yml` (`/dev/shm/sessionboxer/bb`, mode 0600 in a 0700 dir) with one section per host, keeps sections the user logged in by hand in the box, and removes the file when nothing is left. The image sets `credential.helper = !bb auth git-credential` system-wide (in addition to `gh` for github.com): `bb` answers only for hosts it knows and prints nothing otherwise, so git falls through to `gh` or to its prompt for any other host. Snapshots and stopped containers keep nothing, as for `gh`.

**Clones.** `planClone` recognises Data Center remotes (`/scm/KEY/slug[.git]`, `/projects/KEY/repos/slug[/browse…]`, `ssh://[git@]host[:port]/KEY/slug[.git]`), rewrites SSH and browser URLs to the HTTPS clone URL, and — when a Bitbucket credential for that host is enabled — sets `BB_HOST`, `BB_TOKEN` and `BB_GIT_USER` for the clone so `bb auth git-credential` answers before the Daemon has written `hosts.yml`. Without a credential a private clone fails with git's error plus a hint to add a Bitbucket entry for that host, as for GitHub.

## Consequences

- `bb pr merge` does not exist: Bitbucket Data Center refuses merges authenticated with an HTTP access token (the merge commit needs a user identity). The agent is told to leave merging to the user (`bb pr view --web`).
- The PRs pane is still GitHub-only: detecting `…/projects/KEY/repos/slug/pull-requests/12` URLs and polling `/activities` through `bb api` (or directly from the Control Plane while the box is stopped) is the next step, behind a `PrProvider` interface as sketched in the design note; `bb` already exposes the data.
- Bitbucket Cloud (`bitbucket.org`) is explicitly refused by the dialog: its REST 2.0, OAuth consumers and `x-token-auth` git user would be another provider, not another host.
- Tokens are as long-lived as the user made them; `McpConnector.expiresAt` stays `null` because Data Center does not report the expiry to the token's bearer. When one expires the box gets 401s and the card's **Reconnect** takes a new paste.
- The `gh` half of `git`'s credential configuration is unchanged; the generic `bb` helper adds one process start per credential lookup on non-Bitbucket hosts (a few tens of milliseconds of Node).
- Behind a TLS-inspecting proxy (WARP, Zscaler) the box already trusts the extra CAs (ADR-0015); the Control Plane's `verifyBitbucketToken` runs with the same trust, so the token check passes wherever the browser does.
