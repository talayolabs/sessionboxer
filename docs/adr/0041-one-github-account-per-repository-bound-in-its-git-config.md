# One GitHub account per repository, bound in the directory's git config

Several GitHub entries can be connected (ADR-0027) and all of the enabled ones are written into the box's `gh` configuration, so `gh auth status` lists them. But git's credential helper (`gh auth git-credential`) and every `gh` command answer with the one *active* account — the first enabled entry — so a session holding a work repository and a personal one pushes to both as the same login, and a private repository only the second account can see fails to clone. With several repositories per session (ADR-0037) the user wants each repository to belong to an account.

## Decision

**The binding is a property of the repository, not of the session.** `SessionRepo.account` (and `RepoSpec.account` on the way in, `UpdateRepoRequest` for changes, `session_repos.account` in SQLite) holds a GitHub login or `null`. A spec that leaves it out means *auto*: for a github.com URL `pickGitHubAccount` asks `GET /repos/{owner}/{repo}` once per enabled GitHub credential and binds the first that may push, else the first that sees the repository, else the first configured; with one credential no request is made. The chosen login is stored, so what *auto* picked is visible in the chip and stays put when entries are added later. `null` is a real choice ("Active login (no binding)"): the directory falls back to the box's active account as before. Copied host folders never get an account. An explicit login must belong to a connected GitHub entry (`withGitHubAccounts`, 400 otherwise); choosing an entry that is off for the session turns it on, because a binding without its credentials would only produce errors.

**Cloning uses the bound account's token** (`planClone(url, credentials, account)`, `GH_TOKEN` for that one `git clone`), and a login that is bound but not enabled is a clear error rather than a silent clone as somebody else.

**Inside the box, the directory decides.** When the Daemon receives the repository list (`repos/set`, which now carries `account` per entry) it writes into each repository's own `.git/config`: `sessionboxer.githubAccount = <login>` and `credential.https://github.com.helper` reset to `sessionboxer <login>`. `git-credential-sessionboxer` (in the image) answers `get` for github.com only, by running `gh auth token --hostname github.com --user <login>` at that moment; the token goes to git over the credential protocol and nowhere else. `gh` itself is wrapped: `/usr/local/bin/gh` reads `sessionboxer.githubAccount` from the current directory's git config and, unless `GH_TOKEN`/`GITHUB_TOKEN` is already set or the command is `gh auth …`, runs the real `gh` with `GH_TOKEN` of that login. Unbinding removes both keys, so the system-wide `gh auth git-credential` helper applies again. The config names a login and never a token; Snapshots, `repos.json` (which also lists `account`) and logs carry the same. The Daemon's own `gh api` calls for PR watching run from `/`, outside every repository, since they pick their account explicitly.

**Pull requests follow the repository.** When a PR of a repository that is bound is attached, its `viaAccount` starts as that login; the existing fallback (try each account until one sees the PR, remember it) is unchanged, so a wrong binding degrades to today's behaviour rather than failing.

## Consequences

- With *n* GitHub entries, creating a session with an *auto* repository costs *n* `GET /repos` requests per repository (8 s timeout each, in parallel); nothing with one entry or an explicit choice.
- A repository added by hand in the Terminal has no binding and behaves as before; `git config sessionboxer.githubAccount <login>` in it is enough to bind it (the helper key too, for git), which the agent can be told.
- `gh` commands run from `/workspace` itself or outside any repository still use the active account; `--repo owner/name` does not change which account answers. `gh auth switch` still works and changes only unbound directories.
- Not done here: an owner → account map in the GitHub entry so *auto* needs no probe; SSH remotes; Bitbucket, whose entries are one per host already and whose `bb` helper is untouched.
