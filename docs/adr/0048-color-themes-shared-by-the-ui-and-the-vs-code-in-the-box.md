# Color themes shared by the UI and the VS Code in the box

The UI had one look, a dark one, hard-coded in a dozen CSS variables plus some seventy stray hex values, and the VS Code in the Code pane came up in its own default. A user who prefers light, or a Nord everywhere, had no switch; and even with one, an editor in a different palette inside the same window looks like a foreign body. The ask was a theme picker whose choice the embedded VS Code follows, live.

## Decision

**One palette per theme, in the protocol package, and everything is derived from it.** `packages/protocol/src/themes.ts` defines `Theme` — sixteen UI colors (backgrounds, borders, text, accent, user/agent bubbles, ok/warn/error, scrollbar) and seven syntax colors — for eleven built-in themes: Sessionboxer Dark (the look until now) and Light, GitHub Dark and Light, Catppuccin Mocha and Latte, Solarized Dark and Light, Dracula, Nord, One Dark; all MIT palettes. The web derives its CSS custom properties from that object (`themeCssVariables`, set on `<html>`, plus `color-scheme`, `data-theme` and the PWA `theme-color`), and xterm, Mermaid, the code highlighter, scrollbars and the noVNC background read the same values through `useTheme()`. The same module also renders each theme as a **VS Code color theme** (`vscodeTheme`): workbench colors mapped from the sixteen, `tokenColors` from the seven, so the editor's sidebar, tabs, status bar and code are literally the UI's values. `vscodeThemeExtensionFiles()` turns the set into a built-in extension, `sessionboxer-themes`, that the Sandbox image generates at build time into `/opt/openvscode-server/extensions` (and the Control Plane also syncs into a box at start, like the daemon, so an older image's box gets it on Resume).

**The theme is a browser preference.** It lives in `localStorage` (`sessionboxer.theme`) as either `{ mode: "fixed", theme }` or `{ mode: "system", light, dark }` — the latter follows `prefers-color-scheme` with a theme of the user's choosing for each side. It is applied before React renders, so there is no flash of the wrong palette, and chosen under Global settings (cards with swatches, a "follow the system" switch) or from the quick select at the sidebar's foot. It is deliberately not in `config.json`: it is a matter of the screen in front of the user, and a phone paired to the same Control Plane may well want the other one.

**VS Code follows through the box's Machine settings.** In a web VS Code the *user* settings live in the browser (IndexedDB), out of the box's reach; the *Machine* settings — `~/.openvscode-server/data/Machine/settings.json`, "Remote" settings in VS Code's terms — are the server's, VS Code reads them when a window connects, watches the file and applies edits to open windows, and their window-scoped values override the user's. So the Daemon's `codeTheme` RPC (`POST /sessions/:id/code-server/theme`) writes `workbench.colorTheme` there: plain JSON is rewritten as a whole, a hand-edited JSONC file is touched on that one line only, the write is atomic. The Code pane sends the theme when it starts the server (`codeStart` takes a `theme`), when it finds one already running, and whenever the UI's theme changes while the pane is live; the workbench's own default (`sessionboxer.js`) is Sessionboxer Dark for the split second before the settings arrive. It works with no server running too — the file is simply read at the next start — and a box whose image predates the extension gets a clear error asking for Stop → Resume.

## Considered Options

- **Only a UI theme, VS Code left to its own settings**: the user could pick a VS Code theme once through its picker, but nothing would keep the two in step, and the palettes would never match exactly.
- **The theme in `config.json` (one for all devices)**: simpler to reason about, but a dark laptop and a light phone are common, and the setting has no server-side effect other than the one the browser triggers anyway.
- **Pushing the theme through the built-in `sessionboxer` extension (`workspace.getConfiguration().update(…, Global)`)**: also live, but it needs a connected window (the remote extension host only runs while one is open), so a theme picked with the pane closed would be lost; the settings file needs nothing running.
- **Writing the server's `User/settings.json`**: what one would try first; the file exists but a web VS Code does not read it for user settings — verified: no effect, while `Machine/settings.json` applies within a few seconds.
- **Shipping the upstream theme extensions (Dracula, Nord…) from Open VSX**: real syntax detail, but their workbench colors are not the UI's, and the box would need Open VSX at start; generating from the palette keeps the match exact and offline.

## Consequences

- Needs an image rebuild for the extension and the default; until then the Control Plane's sync puts the extension into a resumed box.
- VS Code in a box is one instance: two browsers on the same Session with different themes flip it back and forth — last writer wins. A theme picked inside VS Code's own picker is overridden by the Machine setting; the UI is where the theme is chosen (VS Code says so in its settings editor: "this setting is overridden by remote settings").
- The seven syntax colors give the generated themes a coarser grain than a hand-tuned VS Code theme; more token roles can be added to `ThemeSyntax` without touching anything else.
- Verified live: the eleven themes and the system mode in the UI (variables, xterm, Mermaid, scrollbars, `theme-color`), persistence across reloads; VS Code started with the UI's theme, switched live to Nord, Dracula, GitHub Light, Solarized Light and back while the pane was open, kept after Stop → Resume; the file-opening extension unaffected.
