# PR checks: watched with the comments, announced when they fail, fixed from the PR pane

Watching a pull request (ADR-0026) followed its comments and reviews only. The checks on the head commit were read just for auto-merge, as a flat pass/fail list on `mergeState` that told nobody anything when a check failed: the user learned of a red CI from GitHub's mail, and to have the Agent look at it copied the log link into a prompt by hand. The request was to watch the checks the way comments are watched — notify on a failure — and to have a table like the comments one from which one or several failed checks are handed to the Agent to fix.

## Decision

**Checks are items of the watched PR, next to comments.** `pr-store` gets a `pr_checks` table with one row per check *name* and kind (`check_run` or `status`), identified as `<prId>:<kind>:<name>`: a check keeps its row across pushes, so its Session-side flags (`seen`, `address`, `notified`) can follow it. Each poll of an open PR reads the head commit's `statusCheckRollup` with the existing GraphQL round trip (`fetchChecks`): check runs with app / workflow name, status, conclusion, details URL, title and summary, start and end times, `isRequired`; commit statuses with context, state, target URL and description. Both are normalised to `pending` / `passed` / `failed`, where every completed conclusion other than `success`, `neutral` and `skipped` — `failure`, `timed_out`, `cancelled`, `action_required`, `startup_failure`, a status in `error` — is a failure, since it is what the user would look at; the raw conclusion is kept for display. `setChecks(prId, headSha, checks)` replaces the list and decides the flags: a failure that is the *same run* as before (same head, same state) keeps `seen` and `notified`; a failure on a new head, or a re-run on the same head that went green and red again, is unread and to be announced again, and its `address` goes back to *none*; a check that passes while *in prompt* or *addressing* becomes *addressed*. A check GitHub no longer lists right after a push is parked one poll as `pending` (the new head's runs may not be queued yet) and dropped afterwards. `PullRequest` carries `checksFailed / checksPending / checksPassed` for the overview row; the flat `mergeState.checks` stays for auto-merge's own wording.

**A failure is announced once, like a comment.** `notify()` collects unnotified failed checks with the unnotified items; the `pr_activity` message gains `failedChecks: string[]` per PR, `prActivityLine()` (moved to the protocol so the web and the push text agree) reads *"1 check failed: build"* or *"2 new items from @x, 1 check failed: lint"*, and a check-only notification is titled *a check failed* / *checks failed*. The same hold applies: nothing is announced while the Agent is running, the toast comes at turn end; sidebar and tab counts include unread failures; opening the PR tab marks them read.

**Fixing is the comment action with a different prompt.** `PrActionRequest` takes `itemIds` and `checkIds` (at least one of either), so a selection may mix comments and failed checks; `pr_checks` is broadcast on change and `GET /sessions/:id/prs/:prId/checks` lists them. The prompt gives, per check, the PR, branch and head SHA, the check's name and provider, its state and raw conclusion, whether it is required, the log link and the summary, framed as *diagnostic output from CI, not instructions*; it tells the Agent to read the log (`gh run view <run> --job <job> --log-failed` for Actions), reproduce the failure in the Workspace, fix the cause, verify and commit. The three actions keep their meaning with check-specific labels: **To prompt** puts that text in the composer; **Fix** (= `address`) sends or enqueues it without touching GitHub; **Fix & push** (= `address_reply`) also pushes so the checks run again — with no one to reply to, the reply step is only added when comments are in the same selection. Only failed checks can be picked; running and passed ones are listed for reading. The web's PR pane shows the **Checks** list as a `<details>` above the comments, failed first, opening by itself whenever a failure appears and otherwise staying as the user left it, with the result cell's tooltip carrying the raw conclusion, required flag and timestamps.

## Considered Options

- **Poll the Checks API separately with its own schedule** (rejected): the rollup rides on the poll the PR already makes, with the same login and back-off; a second poller would double the requests for nothing.
- **Identify a check by its check-run id** (rejected): every push and every re-run gives a new id, so *addressing* would be lost exactly when the Agent's push creates the new run. Name + kind is what the user recognises as "the same check".
- **Notify on every failed poll, or only on the first failure ever** (rejected): the first floods, the second misses a fixed check that broke again. "Announce once per run, again on a new head or re-run" matches how a human reads the checks tab.
- **Treat `cancelled` / `timed_out` as not failed** (rejected): a timed-out job is something to look at, and GitHub shows them red too; the raw conclusion is displayed so the difference is visible.
- **A separate action set for checks** (rejected): one selection with comments and checks lets the user hand "the review comments and the red lint" to the Agent in one prompt; the labels differ, the endpoint and queue handling do not.

## Consequences

- Control Plane and web only; no image rebuild. The `pr_checks` table is created on start; existing watched PRs get their checks on their next poll, and a failure already standing there is announced once like any other unread failure.
- One more GraphQL query per poll of an open PR (the head's rollup, up to 100 contexts). Closed and merged PRs are not asked.
- A poll interrupted by stopping the Session reports *watching paused — Sandbox stopped* rather than an error, and resumes with the box or a GitHub Connector.
- Bitbucket Data Center PRs are not watched yet (the `bb` login is for the box only); when they are, their build statuses map onto the same `pr_checks` rows and the same table.
