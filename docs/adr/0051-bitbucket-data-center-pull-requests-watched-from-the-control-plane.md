# Bitbucket Data Center pull requests: watched from the Control Plane with the Connector's token, builds as checks

The PRs pane followed GitHub pull requests only (ADR-0026, ADR-0050). The Bitbucket Data Center Connector (ADR-0038) gave the box a login for `git` and `bb`, but a Bitbucket PR the Agent opened was just a URL in the chat: no comments, no build results, no notification when one failed. The request was the same watching — comments, failed checks announced, the Checks table with **Fix** — for Bitbucket Data Center. Bitbucket Cloud (`bitbucket.org`) is a different product and API and is out of scope.

## Decision

**A pull request has a provider and a host.** `PullRequest` gains `provider: "github" | "bitbucket"` and `host` (both with defaults, `github` / `github.com`, so existing rows and older clients read unchanged); `PrRef` carries them; `parsePrUrl` reads `https://host[:port][/context]/projects/KEY/repos/slug/pull-requests/12[/overview|/diff][?…][#…]` as `{ bitbucket, host, owner: KEY, repo: slug, number }` and refuses `bitbucket.org`; `prUrl` builds the canonical page for either provider; `findPrUrls` finds both in Agent output. The `#12` / `KEY/slug#12` shorthands and the *local* flag come from the Workspace repositories through `parseRepoUrl`, which reads GitHub URLs and the Data Center's `scm/KEY/slug.git`, `projects/KEY/repos/slug` and `ssh://git@host:7999/KEY/slug.git` remotes; hosts compare without their port since the SSH clone port and the web port differ. Project keys are matched case-insensitively, as Data Center does.

**Bitbucket is polled from the Control Plane with the Connector's token, box or no box.** GitHub polls run as `gh api` inside the box so the Agent's own login is used and conditional requests stay free; Data Center has no login in the box other than the Connector's token and no useful ETags, so `pollBitbucket` reads straight from the Control Plane (`bitbucketTokenTransport`: `Authorization: Bearer`, trusting the same CAs as everything else) with the Bitbucket credentials the session has for the PR's host — the account bound to the Workspace repository first, then the others until one can read the PR — and records which in `viaAccount`. Three reads per poll: the PR (`rest/api/latest/projects/…/pull-requests/{id}`: title, `OPEN` / `MERGED` / `DECLINED` and draft as `open` / `draft` / `merged` / `closed`, refs, author, reviewers' `NEEDS_WORK` / `approved` as the review decision, `fromRef.latestCommit` as the head), its activities (`…/activities`, newest first, all pages) and, while open, the head commit's build statuses (`rest/build-status/latest/commits/{sha}`, the commit-wide list; the repository-scoped `…/commits/{sha}/builds` reads one status by key) plus, when there are any, the required-builds merge checks of the repository (`rest/required-builds/latest/projects/…/conditions`) to mark the builds the target branch requires. Without a credential for the host the row says *no Bitbucket login for host* and how to add one; a stopped session keeps being watched, since nothing runs in the box.

**Activities become the items the pane already shows.** Activities are read oldest first; each `COMMENTED` one carries a comment tree (root with nested `comments`), and a comment appears in several activities (ADDED, then REPLIED / UPDATED repeat it), so a comment counts once, under the thread of the first activity that shows it, and `DELETED` ones are dropped. A root with an anchor path is a `review_comment` with `path:line`, the others `issue_comment`s; replies share the root's id as `threadId` and name their parent in `inReplyTo`; a `BLOCKER` comment (a task) is prefixed **Task**; `threadResolved` / `RESOLVED` mark the thread resolved; `APPROVED` and `REVIEWED` (needs work) activities are `review` items. Item links point at `…/pull-requests/12/overview?commentId=…`. Ids reuse the existing `<prId>:<kind>:<id>` scheme with Bitbucket's numeric comment ids in `githubId`, whose name stays for compatibility.

**Build statuses are checks of kind `build`.** Each status key's newest entry is one `PrCheckItem` (`kind: "build"`, `githubId: null`): `SUCCESSFUL` → passed, `FAILED` and `CANCELLED` → failed (the raw state lower-cased as the conclusion), `INPROGRESS` and `UNKNOWN` → pending; `name` or the key as the name, the `parent` plan as the source, the build's URL, description and test counts as the summary, `dateAdded` and `duration` as the times, `required` when the key or its parent is among the target branch's required builds. From there everything is ADR-0050's: `setChecks` decides seen / notified / address across heads and re-runs, `notify()` announces a failure once, `pr_checks` is broadcast, the Checks table and **To prompt** / **Fix** / **Fix & push** work unchanged. The prompt builder reads the provider: for Bitbucket it names Bitbucket, describes the checks as build statuses, points at `bb pr checks` and, for replies, `bb pr comment <id> --reply-to <comment>`, and never mentions `gh` or `gh run rerun`; GitHub prompts are as before.

**Auto-merge stays GitHub's.** Data Center does not let an HTTP access token merge (ADR-0038), so `autoMerge: true` on a Bitbucket PR is a 400 and the web hides the Auto-merge section for them. The pane otherwise names the provider where it said GitHub — *Open on Bitbucket (host)*, *Poll Bitbucket now*, *no Bitbucket login for host can read this PR*, *build status* as a check's source when it has no parent.

## Considered Options

- **Run the polls through `bb api` in the box, as GitHub's run through `gh api`** (rejected): the box only ever has the Connector's token, which the Control Plane holds anyway, and it would tie watching to a running box for no gain; the box path is kept for GitHub where the Agent may have its own login.
- **Bitbucket Cloud alongside** (rejected, out of scope): a different REST API (`api.bitbucket.org/2.0`, workspaces, app passwords / OAuth), no Data Center activities or build-status endpoints; nothing here would be shared but the table.
- **Store the context path in the host** (rejected for now): the Connector's host has no path either, so a Data Center under `https://host/bitbucket/…` is not reachable through the Connector at all; a PR URL with a context path parses, but the REST calls and the canonical page are built without it. Supporting it means a base URL on the Connector first.
- **Treat `UNKNOWN` as failed** (rejected): Data Center reports it for a build it lost track of; announcing it as a failure would wake the user for nothing, and it is shown as *running* until the CI says more.
- **Identify a build by `key` + `buildNumber`** (rejected): as with GitHub check-run ids, a re-run has a new number and *addressing* would be lost when the Agent pushes; the key is what the user recognises as "the same build".

## Consequences

- Control Plane and web only; no image rebuild. `pull_requests` gains `provider` and `host` columns (defaults for existing rows); `pr_checks.kind` accepts `build`; older UIs reading the same API see Bitbucket PRs as PRs with a `github.com` link only if they predate the `provider` field, which the defaults make harmless.
- Three requests per poll of an open Bitbucket PR (plus one for the merge checks while builds exist), none conditional; the same minute / five-minute cadence as GitHub's.
- Verified against a scripted Data Center (fixtures for the PR, activities with nested replies, repeated and deleted comments, paged responses, build statuses and merge checks): URL parsing, attach and shorthands, items, checks, notification once and again on a new head or failed re-run, prompt wording, idle / busy / stopped delivery, credential fallback and the no-login hint, merged PRs, legacy GitHub rows. No live Data Center was available; the endpoint shapes follow Atlassian's REST documentation and `bb`'s own use of them.
