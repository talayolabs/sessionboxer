# Forks with another Agent, and handoffs written by the origin's Agent

A fork starts a new Session with its own box from a Snapshot: same files and tools, and either the conversation up to that point (the Agent remembers it, since its persisted session comes along in the image) or an empty one (ADR-0009, then *Start a new one*). Both kept the origin's Provider. Users wanted to move a piece of work to another Agent — Claude Code to Devin when the one is out of quota or the other suits the task — and to "compact" a long conversation into a fresh one without losing what was learnt. The two are the same problem: an Agent's memory is its Provider's session store (Claude's JSONL, Devin's sessions.db, Codex's rollout files) and cannot be loaded into another Agent, so the memory has to be carried as *text*.

## Decision

**The Fork dialog picks the Agent, and the conversation choice says how its memory travels.** `ForkSessionRequest.provider` (default: the origin's) chooses the fork's Provider; `conversation` is one of three:

- **Continue it** — the chat is copied through the Snapshot and the Agent resumes its own session. Only for the origin's Provider: with another one the Control Plane answers 400 (*Devin cannot continue Claude Code's conversation; start a new one or hand off*) and the dialog disables the option and says why.
- **Start a new one** — empty chat, the Daemon boots with new-conversation semantics (`SESSIONBOXER_NEW_CONVERSATION`, as before) so the origin's persisted session in the image is ignored. Any Provider.
- **Hand off** — the origin's Agent, which holds the whole conversation, is asked in a *hidden turn* to write a handoff document; the fork is then provisioned as a new conversation with that document as its first message. Any Provider, including the origin's own (a fresh session of the same Agent: the "compact into a new Session" case).

**The handoff is written by the Agent that knows, from a fixed brief.** `handoffRequestPrompt(from, to)` asks for a Markdown document between `<handoff>` and `</handoff>` with seven sections — goal, state of the work, decisions, open items, files and places, how to run and test, gotchas — concrete rather than brief, with no file changes and no secret values, naming the successor (*a fresh Claude Code session* / *Devin, a different coding agent*) so the writer knows what it can assume. `extractHandoff` takes what is between the markers (or the whole reply when the markers are missing but the text is long enough to be a document; a short unmarked reply such as *You've hit your session limit* is a refusal), caps it at 60k characters on a line break, and `handoffMessage` wraps it for the fork: who wrote it and where it came from (Session title, snapshot ordinal), that the machine is exactly as left and the conversation is not available, the document, then the user's own first message if one was given or *read it, check the workspace against it, carry on with the open items*.

**Hidden turns are a Control Plane concern.** The request is sent through the normal `prompt` path and the persisted `user_prompt` event carries `origin: "handoff_request"` (next to the existing `"e2e"`); the fork's first message carries `origin: "handoff"`. The Daemon knows nothing of origins (`DaemonPromptParams` is the plain prompt): for a connected origin the Control Plane labels the next `user_prompt` the Daemon echoes, for a pending one the label travels with the pending prompt. `isHiddenTurn` groups both hidden origins so a handoff turn, like a verification turn, does not pump the queue and does not start a verification; *Run now* skips it when looking for the last request. A later *Continue it* fork copies it with the rest (the Agent remembers it, so the transcript says so — as a marker). The transcript shows the request as a marker (*Writing a handoff for a fork…*) and the fork's first message folded under *Handoff from the origin's Agent* — it is long and written for the Agent, but the user can read what the successor was told.

**One handoff at a time, and it can fail without leaving a ghost.** `fork()` with `handoff` requires the origin idle with its Daemon connected (409 with the reason: still working, stopped — resume first, in error, already writing one for another fork; 503 not reachable yet), creates the fork's row at once (so the UI shows it *creating* while the origin writes) and runs `forkWithHandoff`: a `handoffs` map entry from origin id to the fork's settle function; the turn's `turn_ended` with `end_turn` settles it with the last Agent message, `agent_error` or another stop reason with an error; stopping or deleting the origin, or the origin going to *error*, settles it with an error too. On success the document becomes the fork's pending first prompt and the fork is provisioned; on failure the fork goes to *error* with the reason (*The handoff could not be written — Claude Code wrote no handoff, it replied: You've hit your session limit · resets 2pm (UTC). Delete this Session and fork again*).

**Settings follow the Provider.** Model and options are a Provider's; a fork with the origin's Provider inherits them (and Inspect LLM), a fork with another one starts from that Provider's defaults (Inspect LLM on for Claude Code, off for the others). The Provider readiness check (`providerReady`) runs against the *fork's* Provider, so forking to an Agent without a token is refused with its setup hint; the dialog shows the same warning up front. The dialog gets every Provider's model and option catalogue (as cached from previous Sessions of that Provider); the `forked` event records `conversation` and, when it differs, `fromProvider`, so the marker can say *Claude Code there, another Agent here*.

## Considered Options

- **Compaction instead of a handoff** (rejected): `/compact` is Claude's and keeps the summary in Claude's own session store, which is exactly what another Agent cannot read. The handoff is the compaction written as a message; for the same Provider it is a "compact into a fresh session" with a document the user can read.
- **The Control Plane writes the handoff from the transcript** (rejected for now): the transcript has the words but not the Agent's understanding (why a choice was made, what it tried and dropped, what it was about to do); asking the Agent gets that, at the price of one turn and one 409 when the origin is busy. Could be added as a fallback for stopped or errored origins.
- **Let "Continue it" with another Agent replay the transcript as text** (rejected): a fake continuation — the new Agent would seem to remember while it read a flattened log; the handoff says clearly what it is.
- **Show the handoff request and document as ordinary chat messages** (rejected): the request is boilerplate and the document is long; markers and a folded block keep the transcript readable and still tell the truth about what was sent.
- **Refuse the handoff when the reply lacks the markers** (rejected): Agents sometimes drop the markers and still write the document; a long unmarked reply is taken as one, only a short one is a refusal.

## Consequences

- No image rebuild; Control Plane, protocol and web (the Daemon change is removing a field it never used). Forks recorded before this have `conversation` and `fromProvider` unset and read as *continue* with the same Provider.
- A handoff costs the origin one hidden turn (tokens, and it must be idle); the fork's first turn starts with a long message, so its context starts a few thousand tokens in.
- The document is the Agent's account, not a checked one: the fork is told to compare it with the workspace before acting. Secrets are asked to be left out but not scrubbed; the box's tokens live on tmpfs and are not in the Snapshot anyway (ADR-0009).
- One fork can be handed off from an origin at a time; a second request while one is being written is refused rather than queued.
