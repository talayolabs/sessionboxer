# Usage limits: seen, counted down, and continued

A Claude subscription meters usage in windows — a rolling 5-hour "session", a week, and for some models an extra weekly window — and when one is used up Claude Code refuses the turn with a sentence (*You've hit your session limit · resets 2pm (UTC)*) and nothing else. Sessionboxer showed that sentence as an ordinary Agent message, or as a red *agent_error* line, and the Session went idle as if the Agent had answered: no sign that the work stopped for lack of credit, no idea when it comes back, and the user had to notice, wait, and type the prompt again. Codex (ChatGPT plans) and Devin (ACUs) refuse in the same way with their own words. Users asked for a clear sign, a countdown, a *Continue* and an *Auto-continue* that polls until the credit is back, and the windows themselves as bars.

## Decision

**Usage is a normalised part of the Session: `Session.usage` (`SessionUsage`).** `windows` are the Provider's metered windows — `id`, `label`, `used` as a fraction, `resetsAt` or null — `updatedAt`, a `limit` when the last turn was refused (`message`, `resetsAt`, `hitAt`, `retry`), and the `autoContinue` flag. It is stored as JSON in `sessions.usage` (the row defaults to `{}`, which parses to empty), travels with the Session over REST and the WebSocket like everything else, and a fork starts with an empty one (its own Agent reports its own windows; it is not blocked by the origin's limit). Never the raw headers, never a credential, never a Provider response body.

**Windows come from where each Provider reports them; nothing is made up.**

- *Claude Code*: Anthropic's API answers every call with `anthropic-ratelimit-unified-<window>-utilization` / `-reset` headers (`5h`, `7d`, `7d_oi`, `7d_opus`, `7d_sonnet`). The LLM recorder in the box (ADR-0032) already sees every response; it now hands the Daemon *those headers alone* (an allowlist — no authorization, no cookies, nothing else) and the Daemon turns them into windows (`claudeUsageWindows`) and puts them in its status, so the bars refresh with the first call of a turn. That is why the bars need Inspect LLM on (the default). The OAuth usage endpoint was rejected as the source: it rate-limits itself (429 with an hour of retry-after) and would fail exactly when the user looks.
- *Codex*: codex-acp does not forward the CLI's `account/rateLimits/updated` notification yet, but its `/status` command answers `**5h limit:** 80% left (resets 14:00)` and `**Weekly limit:** 40% left (resets 14:00 on 26 Sep)`. The Daemon runs `/status` after each turn (`usageCommand`, eight seconds, the ACP prompt cancelled on timeout) and parses it (`codexStatusWindows`) — *left* becomes *used*, the reset time is read in the box's clock.
- *Devin*: nothing reliable to show. The CLI knows *ACUs consumed* / *ACU limit* for its own `/session-stats`, but no endpoint or notification hands them over and the quota error carries no reset time. The bars say so on hover instead of guessing.

**A refusal is recognised per Provider, from an allowlist of phrasings, and only where a refusal can appear.** `classifyUsageLimit(provider, text)` matches Claude's *hit your session/weekly/monthly/fast-mode/Opus/Sonnet limit*, *usage credit limit reached*, *out of credits*, *extra usage limit*; Codex's *hit your usage limit*, `usage_limit_reached`, `quota_exceeded`, `insufficient_quota`; Devin's *Quota exhausted*, `resource_exhausted`, *ACU limit*. It returns the parsed reset when the text says it — *resets 2pm (UTC)*, *resets 11:30am (UTC)*, *resets Sep 25, 2pm (UTC)*, *resets 14:00 on 26 Sep*, *in 2h 15m*, *after 3600 seconds* — else null. The Control Plane applies it to an `agent_error` message (Claude wraps it as *Internal error: …*, Devin as a JSON-RPC error) and to a turn that ended normally whose *only* product was one short Agent message (Claude often answers the refusal as text and ends the turn): a turn that ran a tool call is never taken as refused, a long message neither. The Daemon adds a second, header-based signal for Claude: a response with `anthropic-ratelimit-unified-status: rejected` shortly before the error marks it as a limit with the header's reset time, whatever the wording.

**A refused turn is not an error and leaves the Session idle with a `limit`.** The interrupted prompt is kept for the retry: the turn's own prompt text and attachments when the Agent had not started working (nothing ran), or the plain *Continue where you left off.* when it had (repeating the prompt would redo the work); hidden turns (verification, handoff request) keep nothing — they are re-run by their own features. The queue does not pump while a `limit` stands; it plays on after a successful continue. A scheduled run ending in a refusal is marked failed with *The Provider's usage limit was hit; the Session offers Continue / Auto-continue* (`TurnOutcome: "usage_limit"`) rather than *The Agent reported an error*.

**Continue is one request; Auto-continue is a poll that only runs when it is safe.** `POST /sessions/:id/usage/continue` clears the limit and sends the kept prompt (a second refusal puts the limit back with the same retry). `POST /sessions/:id/usage/auto-continue {enabled}` sets the flag; while it is on and a limit stands, the Control Plane wakes every 10 s (`USAGE_AUTO_CONTINUE_INTERVAL_MS`): it waits while the announced reset is in the future (no point in asking), while the Session is not idle, its Daemon not connected, a handoff, verification or repository change is in flight; then asks the Provider a one-line question in a throwaway ACP session (*Reply with the single word OK.*, discarded) and, if the answer is not itself a refusal, continues. A refusal with a later reset moves the countdown. The poll stops with the flag, with the limit, with a stop or delete, and on Control Plane shutdown; the flag itself is kept so a resumed Session keeps polling.

**In the UI: one bar with the sign, three bars with the windows.** A refused Session shows, above the usage bars, a red bar with a drawn no-entry sign, *Claude Code usage limit reached*, the time left as `days hh:mm:ss` ticking every second (hover: the reset as an RFC 5322 date and what the Provider said), **Continue** (hover: the prompt it will send) and the **Auto-continue** checkbox (hover: what it polls; *waits for the reset* / *polling…* while on). The session list shows the sign in place of the status dot, the phone top bar too. Above the context gauge, three equal bars in a row — the windows in a fixed order (session, week, Fable / Codex's primary and secondary), each green→red like the context gauge, no figures on them; hover gives *Session usage: 11% used · resets in 3 h 48 min (Thu, 24 Sep 2026 19:00:00 +0000)*. A slot with nothing to show is hatched and says why on hover (*Claude has not reported its usage yet…*, *Devin does not report its usage windows (ACUs) to Sessionboxer*).

## Considered Options

- **Poll Anthropic's OAuth usage endpoint from the Control Plane** (rejected): the endpoint rate-limits hard and is undocumented; the headers come with the calls the Agent makes anyway, and say the same.
- **Retry by re-sending the prompt blindly every 10 s** (rejected): each attempt is a turn in the transcript and a refusal each time; a throwaway one-line probe in a separate ACP session costs nothing visible and asks the Provider itself whether it answers.
- **Mark the Session `error` on a refusal** (rejected): `error` is terminal (no prompts, the scheduler gives up, the UI offers Delete); a limit is temporary and the Session must stay usable.
- **Ask the Agent `/usage`** (rejected for Claude): Claude Code's `/usage` renders a screen for a terminal, not for ACP, and would cost a turn; the headers are free.
