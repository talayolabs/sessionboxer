# An in-repo design system: hand-written CSS, Radix for the behaviour

The web UI was one 1,200-line `styles.css` and no component layer: fourteen dialogs each rendered their own `.modal-backdrop`/`.modal` markup with their own Escape listener and backdrop-click test, three menus each had their own outside-click and focus code, tabs were `button.active` lists, tooltips were `title=`, and metrics (radii, font sizes, shadows, z-indexes) were literals repeated across the file. The look is deliberately VS Code's, in the eleven palettes of ADR-0048. The question was which design system to build on so that the UI stays close to VS Code and to the current theme, stays cheap and fast, and keeps working with tiptap, xterm, noVNC, Mermaid and the VS Code iframe. The candidates measured (throwaway Vite builds of a dialog + select + menu + tooltip + tabs + table each; screenshots against vscode.dev; typing latency with Chrome CPU throttling) were: the hand-written CSS formalised, with or without a headless behaviour library (Radix Primitives, Base UI, React Aria Components, Ariakit); VS Code's own controls (`@vscode/webview-ui-toolkit`, deprecated January 2025 with no Microsoft replacement; `@vscode-elements/elements`, Lit web components); shadcn/ui (Tailwind); Fluent UI React v9; Mantine, Park/Ark UI, daisyUI, Open Props.

## Decision

**The look stays hand-written CSS, organised as a small design system in the repository.** Four layers, imported in this order by `main.tsx`: `styles/tokens.css` (the metrics that are the same in every theme: type scale `--fs-*`, radii `--radius-*`, control heights, shadows, the backdrop, the focus ring, and the z-index ladder `--z-*` from raised content to portalled surfaces), `styles/base.css` (element defaults: typography, buttons and their variants, native fields, code, scrollbars, focus-visible), `ui/ui.css` (the shared components: pane and toolbar, panel and form rows, action rows, list boxes, switch, dots/badges/pills/counts, banners and toasts, menu, popover, tooltip, modal, segmented tabs, split settings) and `styles.css` (what is specific to one feature: transcript, composer, terminal, desktop, PRs, context, mobile shell). Colors are not in the CSS at all: `theme.ts` writes the chosen palette on `<html>` before React renders, from `packages/protocol/src/themes.ts`, as it did — the semantic names (`--bg`, `--panel`, `--border`, `--text`, `--accent`, `--ok`…) are the color tokens.

**The same palette generator now also emits VS Code's own token names**, as an additive layer: `vscodeCssVariables(theme)` turns every entry of the workbench color map that `vscodeTheme` writes into the theme JSON (`editor.background`, `focusBorder`, `button.hoverBackground`…) into `--vscode-editor-background`, `--vscode-focusBorder`, `--vscode-button-hoverBackground` — the exact names VS Code exposes to its webviews, dots to dashes, camelCase kept. `vscodeTheme` and `vscodeCssVariables` share one `vscodeColors(theme)`, so the two cannot drift. Nothing in the app's CSS uses these names yet; they are there so CSS written against VS Code's vocabulary (a snippet from a VS Code extension, a webview component) is drawn in the current theme without translation. `@vscode-elements/elements` is **not** adopted as the component library: it covers 62 of the 86 variables it reads from this map but has no dialog, tooltip or toast, renders in shadow DOM (our CSS cannot reach in), needs a 150 kB codicon font, and has one maintainer.

**Radix Primitives, through the single `radix-ui` package, for the five behaviours that are hard to get right by hand, and nothing else.** `apps/web/src/ui/` wraps them thinly: `Menu`/`MenuItem` and `ContextMenu`/`ContextMenuItem` (DropdownMenu, ContextMenu), `Modal` (Dialog), `Tip`/`TooltipProvider` (Tooltip), `Popover`, `Tabs`/`TabList`/`Tab`/`TabPanel`. The wrappers render the classes `ui.css` styles (`.menu`, `.menu-item`, `.modal.panel`, `.tooltip`, `.popover`, `.segmented`…) and add no visual layer of their own; what Radix brings is focus trapping and return, Escape and outside-click dismissal with a nested-layer stack, typeahead and arrow keys in menus and tabs, collision-aware positioning, portals (so a menu floats over the noVNC canvas and the Code iframe), and the aria wiring. Menus and popovers are non-modal (`modal={false}`), so opening one does not lock scrolling or set `pointer-events: none` on the body — the two side effects that showed up as extra style recalculation in the measurements. Native `<select>`, `<input>`, `<textarea>`, `<table>`, the toasts, meters and gauges, badges, breadcrumbs, the layout, the mobile drawer and bottom sheet, and the composer stay hand-written.

**Where Radix is and is not used.** Every modal dialog is a `Modal` (title as its `<h2>`, `dismissible={false}` while a request is in flight). The session "⋯" menu, the Devices pairing menu and the terminal's right-click menu are `Menu`/`ContextMenu`. The Desktop's clipboard panel is a `Popover` anchored to its button, kept open while the user clicks in the desktop (`stayOpen`). The LLM-call dialog's Request/Response/Tree/Diff, the OS picker of the provider connect steps and the section list of the Advanced and Global settings are `Tabs`. Tooltips replace `title=` on the stable chrome — the pane switcher, header buttons — with one `TooltipProvider` at the root. **Not** Radix: the header pane switcher and the phone's bottom tabs (clicking the active tab hides the pane, which is not a one-of-N selection), the mobile version of the session menu (a plain list in the drawer), and any control inside the composer — the composer is its own render boundary (`draft.ts`), and the measurements showed the one way to make Radix cost keystrokes is to re-render hundreds of Radix roots per keystroke.

**Selected state is `aria-selected`, everywhere.** Radix Tabs set it; the hand-written tab-like controls set it too, and the CSS keys on it rather than on an `.active` class, so one rule styles both.

## Considered Options

- **VS Code Elements as the component library**: the closest look for free and a real 1:1 with the `--vscode-*` names, but the gaps above, and Lit's shadow DOM against a codebase whose whole look is one stylesheet; the alias layer keeps the door open for individual elements later.
- **shadcn/ui**: the same Radix underneath, but through Tailwind — a second styling language, a preflight reset to keep away from xterm and Mermaid, and 30–40 kB of CSS for a look we would restyle anyway.
- **Fluent UI v9, Mantine**: complete, but a design language that is not VS Code's, runtime CSS-in-JS (Griffel) or 150 kB+ of styles, and a rewrite of every form.
- **Base UI / React Aria Components / Ariakit** instead of Radix: React Aria is the most thorough on accessibility but 50–60 kB heavier and brings its own hooks model; Base UI was at 1.0.0-beta at the time; Ariakit's positioning needed a workaround in the sample. Radix is the smallest of the mature ones (+35 kB gzip measured for menu + dialog + tooltip + popover + tabs; +31 kB with the native select kept) and the `radix-ui` package makes it one dependency.
- **Hand-written behaviour too**: what we had; each dialog and menu rewrote the same Escape/outside-click/focus code with slightly different bugs (no focus trap, focus lost on close, the terminal menu closing on any key).

## Consequences

- One dependency (`radix-ui`), about 35 kB gzip on a 650 kB gzip main chunk; cold-start script cost measured at +17 ms on a desktop, +73 ms under 4× CPU throttling, in the sample.
- Typing latency unchanged where it matters: keydown→paint 16 ms p50/p95 with and without Radix, at 1× and 4× throttling; per-keystroke JS 0.1 ms in a memoised composer either way. The rule that keeps it so is in the previous section: no Radix root under the composer's store.
- `styles.css` went from 1,234 to about 1,000 lines with the shared rules moved out and literals replaced by tokens; the fourteen dialogs lost their shell markup and Escape effects; the three menus lost their listener code.
- Two small look changes with the normalisation: the OS picker is the standard small segmented control (selected in `--user` rather than `--selected`), and the clipboard panel hangs from its button instead of sitting at the top-right of the screen.
- Not verified in this change: a screen-reader run of the migrated dialogs and menus, and the Electron build (the web bundle is what changed; nothing in it is browser-specific).
- Later: the `--vscode-*` layer allows individual `@vscode-elements` (a badge, a progress ring) or copied webview CSS without per-theme work; the token file is the place for a density or a font-size preference.
