# A Windows VM next to the Linux Sandbox: QEMU/KVM, drawn over RDP

A Session's box was a Linux container, always. Some work needs a Windows desktop (a Windows build of an app, an installer, Office, a driver, a `.NET Framework` service, a browser on Windows), and the request was to pick the operating system per Session: `docker linux`, `qemu windows`, `qemu macos`. Docker cannot run a Windows *desktop* as a container on a Linux, macOS or Windows host — Windows containers are server-core, no GUI, Windows hosts only — so a Windows desktop means a virtual machine. The questions were where the VM runs, where the Agent runs, and how the rest of Sessionboxer (desktop MCP, noVNC, recordings, terminal, VS Code, repositories, snapshots) keeps working.

## Decision

**An `environment` per Session, fixed at creation: `docker-linux` (the default and what every Session was until now), `qemu-windows`, or `qemu-macos` (declared, greyed out).** It sits in `SandboxSettings` next to the resources and Docker toggle, in the New session form as the first control of the Sandbox section, and on the Session as a badge. `PublicSettings.environments` says, per environment, whether this host can create one and why not otherwise; the form disables what is not available and shows the reason.

**The Agent stays on Linux. Windows is a second container next to the Sandbox, and the Sandbox's desktop *is* the Windows desktop.** A `qemu-windows` Session gets its usual Linux Sandbox (Agent, Sandbox Daemon, Xvfb, XFCE, noVNC, terminal, VS Code, desktop MCP, recordings — nothing changes there) plus a sidecar container, `sbx-win-<session>`, on [dockur/windows](https://github.com/dockur/windows) (QEMU with KVM, a TAP network behind the container's own NAT). Both sit on the `sessionboxer` network, so the Sandbox reaches the VM by container name. Inside the Sandbox, `windows-desktop` runs `xfreerdp3` full-screen on the Xvfb display, reconnecting whenever the connection drops (guest still booting, RDP restart): what noVNC shows and what the desktop MCP screenshots, clicks and types into is the Windows desktop, pixel for pixel, through RDP's input channel. `win <command>` runs PowerShell in the guest over OpenSSH (`sshpass` + the guest account; PowerShell is the SSH default shell), `win` alone opens an interactive PowerShell, and `win-scp` copies files either way (`win:C:/Users/agent/…`). The Agent's briefing gets a Windows section that says all this, plus that `/workspace` and the repositories are on the Linux side and reach Windows by copy.

Why not the Agent inside Windows: the ACP adapters, Claude Code, the Devin CLI, Codex, Cursor, the Sandbox Daemon, node-pty, the recorder and the desktop MCP are all built and tested on Linux; running them in the guest would mean a Windows port of the whole box and a second image to maintain, and losing the recordings, the terminal pane and VS Code in the meantime. Driving Windows from Linux keeps one Sandbox image and one MCP, and RDP gives a real input channel (not synthetic events through a guest agent). The costs are listed under Consequences.

**One base disk, installed once; each Session boots a copy-on-write overlay of it.** Installing Windows unattended takes 20–40 minutes and a 6 GB download, so it happens once per host, from **Global settings → Windows → Install**: a `sbx-windows-install` container on dockur/windows fetches Microsoft's evaluation/consumer media for the chosen edition (Windows 11 Pro by default; 11 LTSC/Enterprise, 10 Pro/LTSC, Server 2022/2025 are the other options), installs it with dockur's unattended answer file (account `agent`, a password Sessionboxer generates and keeps in `config.json`), and at the end of setup runs `images/windows/oem/install.bat` — never sleep/lock/blank the screen, no automatic update reboots, OpenSSH Server with PowerShell as its shell, show file extensions and hidden files, then `shutdown /s`. The Control Plane follows the container's log for the status pane, and when it exits with code 0 and dockur's `windows.boot` marker is on the volume (written only once the firmware has booted Windows from the installed disk, which also makes dockur delete the ISO), the base is **ready**; anything else is an **error** with the log's tail, and the half-written volume is removed. The base lives in the `sbx-windows-base` Docker volume (a sparse 64 GB `data.img`, ~10 GB used) with a `windows-base.json` record in the data directory. A Session's VM gets its own volume with the base's small state files (`windows.vars` firmware variables, `windows.mac`, `windows.boot`…) and `data.qcow2`, a qcow2 overlay whose backing file is the base's `data.img` mounted read-only at `/base` in every VM: a Session's disk costs what it writes. Reinstalling or deleting the base is refused while a Windows Session (running or stopped) still builds on it.

**Lifecycle follows the Sandbox's.** Create: VM container + overlay, start it, then the Sandbox (which gets `SESSIONBOXER_WINDOWS_HOST/RDP_PORT/SSH_PORT/USER/PASSWORD`, the last one as a container env var like the provider secrets — stripped from snapshots as those are). Stop: `docker stop` with a 120 s grace period, which dockur turns into an ACPI power button so Windows shuts down cleanly; Resume boots it again (10–30 s to the login-less desktop, RDP reconnects by itself). Delete: VM container and volume gone. The VM carries the Session label, so the death watch that notices a Sandbox exiting notices the VM too. Both containers are created stopped and started in order, so a failure in the middle removes what was made. The VM's Docker memory limit is the guest's RAM plus 1.5 GB for QEMU; RAM, CPUs and disk size come from Global settings → Windows (4 GB, 2, 64 GB by default), RAM and CPUs applied per VM at creation, disk size baked into the base.

**Availability is probed, not assumed.** `qemu-windows` is available when: the Docker host is Linux (`docker info` OSType), a throwaway container on the Sandbox image given `/dev/kvm` finds it and can write it (this catches a missing module, Docker Desktop's VM — no nested KVM on macOS and rarely on Windows — and a Control Plane in a container that cannot see the host's `/dev`), and the base is ready. The KVM verdict is cached; transient Docker errors (image not there yet) are reported but not cached. The Windows Session then gets `/dev/kvm`, `/dev/net/tun` and `NET_ADMIN` on the VM container only; the Sandbox is as unprivileged as before. `qemu-macos` is always unavailable, with the reason: Apple's licence allows macOS VMs on Apple hardware only, where they run on the Virtualization framework (`tart`, `UTM`) rather than QEMU-in-Docker, so it needs a runtime of its own next to Docker and a Mac to develop it on.

**What Windows Sessions cannot do yet, said where it matters.** Snapshots, forks, rebuilds and the automatic snapshot after each turn are refused (409) or skipped for `qemu-windows`: a snapshot is a `docker commit` of the Sandbox, and the Windows disk is outside it. Docker inside the Sandbox is off for them. The form says so next to the environment picker, and the header hides the Snapshot/Fork/Rebuild controls.

## Considered Options

- **The Agent inside Windows** (the ACP adapter, Claude Code and the desktop MCP ported to Windows, the Windows VM being *the* box): the most faithful — the Agent's shell is PowerShell, repositories live where the tools are — but every part of the Sandbox would need a Windows counterpart and a second image; and Claude Code, Codex and the Devin CLI are less at home on Windows than on Linux. Kept as the direction if Windows Sessions get heavy use; the `win` bridge is the interim.
- **QEMU inside the Sandbox container** instead of a sidecar: one container per Session, but the Sandbox would need `/dev/kvm`, `/dev/net/tun` and `NET_ADMIN` (privilege the Agent does not need), the Windows disk would be inside the container's writable layer (snapshots of 10+ GB, and `docker commit` of a running VM's disk is not consistent), and the image would double with QEMU and its firmware. The sidecar keeps the Sandbox as it is and the VM disk in a volume.
- **VNC instead of RDP** to show the guest (dockur exposes QEMU's VNC on 5900 / noVNC on 8006): works before Windows has finished booting, but it is the framebuffer with no clipboard, no resolution negotiation, no audio, and a slower codec; RDP gives all of those and a native input channel. The reconnect loop covers the boot window.
- **Windows containers** (`mcr.microsoft.com/windows`): Windows Server hosts only, no desktop session, no RDP; not a fit for "a desktop the Agent can see".
- **A per-Session full install** (no shared base): simple, but 30 minutes and 6 GB of download per Session; the overlay makes a Session's VM ready in seconds.
- **macOS via `dockur/macos`** on Linux: technically the same trick with OpenCore, but against Apple's software licence; declared in the picker, not implemented.

## Consequences

- The Windows desktop is what the Agent sees and drives; Linux is what it runs in. Paths, files and commands the Agent handles by default are Linux-side; "on Windows" means `win …`, `win-scp`, or the desktop. The briefing spells this out; a repository the Agent must build on Windows is copied there (`win-scp -r /workspace/app win:C:/Users/agent/app`) or cloned from within the guest — a shared folder is the obvious follow-up.
- Requirements for `qemu-windows`: a Linux host (bare metal, a VM with nested virtualisation, or WSL2 with KVM enabled) running Docker Engine, `/dev/kvm`, ~10 GB for the base plus what Sessions write, and the RAM the guest takes on top of the Sandbox's. Docker Desktop on macOS cannot; on Windows only with nested virtualisation exposed to WSL2. A Control Plane in a container (compose mode) works when `/dev/kvm` exists on the host, since the VM containers are siblings, not children.
- Licensing: dockur downloads Microsoft's public media; Windows runs unactivated (a watermark and a few personalisation settings locked) until the user activates it with their own key inside the guest. Sessionboxer does not ship or embed a licence, and says so in the guide.
- The Sandbox image grows by FreeRDP and sshpass (~15 MB) and gains three scripts; nothing runs when the Windows env vars are absent, so Linux Sessions behave exactly as before.
- New REST surface: `GET/DELETE /api/windows`, `POST /api/windows/install|cancel`, `windows_base` broadcasts; `Settings.windows` (edition, RAM, CPUs, disk, password write-only), `PublicSettings.environments`.
- Not done: snapshots and forks of Windows Sessions (would need a qcow2 snapshot of the overlay paired with the Sandbox commit), a shared folder between `/workspace` and the guest, several editions/bases at once, `qemu-macos`, and any Windows verification beyond what the live test in this ADR's commit covered.
