# A macOS VM next to the Linux Sandbox: dockur/macos, OpenCore, drawn over VNC

ADR-0057 gave a Session a Windows desktop: a VM in a sidecar container on dockur/windows, the Linux Sandbox showing and driving it. `qemu-macos` was declared in the picker and greyed out, with the reasoning that Apple's licence allows macOS VMs on Apple hardware only and that on a Mac the right runtime is Apple's Virtualization framework, not QEMU in Docker. The request was explicit anyway: the same shape, on [dockur/macos](https://github.com/dockur/macos) with OpenCore. This ADR records how it works and what is different from Windows — mostly the install, which Apple ships no unattended path for — and where the licence caveat lives.

## Decision

**`qemu-macos` is a real environment: a `sbx-mac-<session>` sidecar on dockur/macos (QEMU with KVM, OpenCore as the bootloader) next to the usual Linux Sandbox, whose desktop is the macOS desktop.** Everything of ADR-0057 carries over: the Agent, its shell, `/workspace`, the terminal, VS Code, recordings and the desktop MCP stay on Linux; the VM is a second container on the `sessionboxer` network, reached by name; the Session's VM boots a copy-on-write overlay of a shared base disk; lifecycle follows the Sandbox's (created stopped, started in order, `docker stop` with a 120 s grace period that dockur turns into an ACPI power-off, deleted with the Session); snapshots, forks, rebuilds and Docker-in-Sandbox are refused for the same reason and the UI says so; availability is probed, not assumed. The shared plumbing was pulled out of `windows.ts` into `vm-host.ts` (`VmHost`: KVM probe, `/dev/kvm` + `/dev/net/tun` + `NET_ADMIN` host config, helper containers on the Sandbox image, start/stop/state/remove, volume sizes, log demux) and `sessions.ts` speaks to either backend through the `GuestVms` interface.

**The Sandbox draws the guest over VNC, not RDP.** macOS has no RDP server; its own Screen Sharing is VNC with Apple's authentication and needs turning on in the guest. dockur exposes QEMU's own VNC server (port 5900) which shows the guest from the first firmware frame, so `sessionboxer-macos-desktop` runs `xtigervncviewer` full-screen on the Xvfb display against `sbx-mac-<session>:5900`, reconnecting whenever the VM restarts. QEMU's VNC gives a plain framebuffer and an input channel — mouse and keyboard through QEMU's virtual USB devices — which is what the desktop MCP needs; there is no clipboard or audio. The guest's screen is 1024×768 (dockur's `WIDTH`/`HEIGHT`), the same as the Sandbox's display, so the view fills it pixel for pixel. `mac <command>` runs a command in the guest over SSH (Remote Login, account `agent`, `sshpass` with the password in the environment), `mac` alone opens a shell, `mac-scp` copies files either way (`mac:/Users/agent/…`). The briefing gets a macOS section: the desktop is a Mac (⌘ shortcuts, the menu bar), the repositories are on Linux and reach the Mac by copy.

**The base is installed *by hand in the VM's screen*, once, driven from Global settings → macOS.** dockur/macos downloads Apple's Recovery image for the chosen release (macOS 11 to 15; 15 by default), generates an OpenCore boot disk with a machine identity (model, serial, board, ROM) and boots it; the rest — Disk Utility, the installer (which downloads the full release from Apple, 13 GB), Setup Assistant, the account, Remote Login — is Apple's interactive flow with no answer file. So `install()` starts the `sbx-macos-install` container on the `sbx-macos-base` volume and the status goes through **installing** (Recovery downloading, OpenCore built) → **setup** once dockur logs `Booting macOS`: the settings page shows the VM's screen (noVNC from the install container's port 8006, bridged by the Control Plane like a Session's desktop, so no host port) with the six steps and the generated password next to it, and the Control Plane tries `ssh agent@sbx-macos-install sw_vers -productVersion` every 20 s from a throwaway Sandbox container. When it answers, **finishing**: a script over SSH turns off sleep, display sleep and the screen saver (the VNC view would go black), sets auto-login for `agent` (a Session's VM must boot to the desktop with nobody at the keyboard), then shuts the guest down; dockur exits with it, and an exit with the provisioning done and `data.img` on the volume is **ready** (`macos-base.json` records release, product version, size). A VM that powers off before that is an **error** that keeps the disk, and *Install* again continues on it (the installer's own restarts do not end the container; a user closing the VM does). *Cancel* stops the container and ends the same way (the disk, if any, stays for the next *Install*; *Delete* wipes it); a Control Plane started while `sbx-macos-install` runs follows it again, and one that finds a half-installed record with no install running reports that error too. The password is generated once (letters and digits: it gets typed into Setup Assistant), stored write-only in `config.json` like the Windows one, and shown on the settings page on demand.

**A Session's VM: the base's small files plus a qcow2 overlay.** dockur/macos keeps a release's files under `/storage/<version>/` while the disk is being made: `data.img` (the guest disk, raw, sparse), `boot.img` (the OpenCore disk), `macos_hd.rom`/`.vars` (OVMF firmware and its NVRAM), `base.dmg` (Recovery) and the identity files. `create()` copies everything but `data.*` and `*.dmg` to the root of the Session's volume — OpenCore with the *same* machine identity, the NVRAM as the base left it — and makes `data.qcow2` there, a qcow2 with the base's `data.img` as backing file at `/base/<version>/data.img`, the base volume mounted read-only at `/base` in every VM. dockur finds the disk at the root (`DISK_FMT=qcow2`), reads its first blocks through the backing file, sees a partitioned disk and neither switches to the release folder nor downloads Recovery. A Session's disk costs what it writes. Reinstalling or deleting the base is refused while a macOS Session (running or stopped) builds on it.

**Availability is KVM plus AVX2.** Same probe as Windows (Linux Docker host, a throwaway container that can open `/dev/kvm`), plus `avx2` in the helper's `/proc/cpuinfo`: macOS 11+ needs it and dockur refuses to boot without. Then the base must be **ready**; the reason otherwise names the state (installing, waiting for setup, missing). The Session's VM container gets `/dev/kvm`, `/dev/net/tun` and `NET_ADMIN`; the Sandbox stays as unprivileged as before.

**The licence caveat is stated, not enforced.** Apple's macOS software licence permits running macOS in a VM on Apple-branded hardware; dockur/macos runs it under QEMU on whatever Linux/KVM host it finds, and so does this environment. Sessionboxer downloads nothing of Apple's itself (dockur fetches Recovery and the installer from Apple's servers, as the user's own Mac would), ships no macOS bits, and says in the guide and on the settings page that using `qemu-macos` on non-Apple hardware is the user's call under Apple's terms. The option is off by default in the sense that nothing happens until the user installs a base.

## Considered Options

- **Apple's Virtualization framework on a Mac (`tart`)**: the licensed route and cheap clones through APFS, but a runtime beside Docker (the Sandbox in Docker Desktop, the VM on the host), Apple silicon only, at most two VMs, no Linux or Windows host, and no Mac here to develop and test on. Declined by the user in favour of dockur/macos; stays the obvious alternative if licensing matters more than host reach.
- **Unattended install** (a scripted Recovery, `startosinstall`, a pre-made disk image): Apple's Recovery has no answer file, `startosinstall` needs a downloaded installer app and an existing macOS, and shipping a ready disk image would mean distributing macOS. The interactive install once per host, with the screen and the steps in the settings page and SSH as the "done" signal, is the honest version.
- **Screen Sharing (Apple's VNC) or RDP** instead of QEMU's VNC: Screen Sharing needs turning on in the guest and Apple's auth in the viewer, shows nothing until macOS is up, and there is no RDP server for macOS. QEMU's VNC shows the guest from the first frame and needs nothing in it.
- **A fresh identity per Session** (new serial/MAC in each overlay's OpenCore): closer to "a new Mac each time", but the NVRAM and the installed system are tied to the base's identity and a change would trigger Apple's activation/iMessage checks and possibly a re-setup. The base's identity is copied; several Sessions with the same serial is harmless offline and for Apple-account-free use, which is what the base is set up for.
- **QEMU inside the Sandbox**: as for Windows, the privilege, the 20+ GB disk in the container layer and the image size argued for the sidecar.

## Consequences

- The Mac desktop is what the Agent sees and drives; Linux is what it runs in. `mac …`, `mac-scp` or the desktop mean "on the Mac". Keyboard shortcuts through the MCP are the Mac's (⌘ is the Super/Windows key on the Sandbox's keyboard).
- Requirements for `qemu-macos`: a Linux host with `/dev/kvm` **and AVX2**, Docker Engine, ~20 GB for the base plus what Sessions write, 4 GB of RAM per VM by default on top of the Sandbox's, and about an hour of the user's attention once for the install (plus Apple's 13 GB download). Docker Desktop on macOS cannot (no KVM); on Windows only through WSL2 with nested virtualisation.
- Licensing: see above; the guide says it in one paragraph, without hedging.
- The Sandbox image grows by TigerVNC's viewer (~3 MB) and three scripts; nothing runs unless `SESSIONBOXER_MACOS_HOST` is set, so Linux and Windows Sessions are untouched.
- New REST surface: `GET/DELETE /api/macos`, `POST /api/macos/install|cancel`, `GET /api/macos/screen` (WebSocket to the install VM's noVNC), `macos_base` broadcasts; `Settings.macos` (release, RAM, CPUs, disk, password write-only); `PublicSettings.environments["qemu-macos"]`.
- Not done: snapshots and forks of macOS Sessions, a shared folder, clipboard between the box and the guest, several releases at once, resizing the guest's screen with the Sandbox's, and any verification beyond what the commit that introduced this ADR reports.
