# Provider sign-in from Settings, in the user's own browser

Connecting a Provider meant a terminal: install its CLI, run its login, find the token or file it wrote, paste it (ADR-0002, 0007, 0046, 0054). The point of every Provider login is the browser — the user is already signed in to claude.ai, chatgpt.com, cursor.com or app.devin.ai there, or Chrome has the password — so that is the part to keep, and the rest can be done for them. [MonoCode](https://github.com/hardbeat920/monocode), reviewed for this, spawns the CLI's login on the machine the app runs on and reads the CLI's own credential files for "signed in as …"; it never detects a login up front (a Provider is "available" when its binary is on PATH) and only learns a login is missing when a turn fails.

What makes this possible without a terminal is that none of the four CLIs needs a callback to the machine it runs on. Checked in the image and on a host:

- `claude setup-token` prints an OAuth URL (`claude.com/cai/oauth/authorize?code=true&…`, PKCE) and waits at *Paste code here if prompted*; the page shows the code; the CLI prints the long-lived `sk-ant-oat01-…` token.
- `devin auth login --force-manual-token-flow` prints `app.devin.ai/auth/cli/continue?state=…`, waits at *Paste the code from the sign-in page*, then writes `credentials.toml`.
- `codex login --device-auth` prints `auth.openai.com/codex/device` and a one-time code (`XXXX-XXXXX`, 15 minutes) for the user to type into the page, polls, then writes `~/.codex/auth.json`.
- `agent login` (Cursor) prints `cursor.com/loginDeepControl?challenge=…`, polls until the page is done, then writes `auth.json`.

## Decision

**The Control Plane runs the Provider's own login CLI on a pty and hands the URL to the browser the user is in.** `POST /api/providers/:provider/login` starts a flow (`ProviderLoginFlow`: `status`, `url`, `pasteCode`, `userCode`, `account`, `error`, `expiresAt`, and nothing secret); the Settings page polls it, opens `url` in a new tab as soon as it is there — the tab is in the user's browser, with their sessions and saved passwords, whichever machine the Control Plane is on — and then does what the Provider's shape needs: a **Paste the code** field for Claude Code and Devin (`POST …/login/:id/code`, typed into the pty when its prompt is up, kept until then if it arrives early), the CLI's one-time code shown for Codex, nothing for Cursor. When the CLI exits 0 the Control Plane takes what it produced — the token in the output for Claude Code, the file in the scratch home for the other three — validates it with the same rules as a manual paste (`normalizeCodexAuthJson`, `normalizeCursorLogin`, the API-key-shaped field of Devin's TOML) and stores it under `providerSecrets` like a paste would. Flows live 15 minutes, one per Provider (a new one cancels the old), `DELETE …/login/:id` cancels; the CLI gets 2 minutes to print its URL and 90 seconds to redeem a code.

**The CLI runs on this machine when it is installed here, else in a throwaway container from the Sandbox image; in both cases in a scratch home.** `claude`, `devin`, `codex`, `cursor-agent`/`agent` are looked up on PATH plus the usual per-user bin dirs (`~/.local/bin`, `~/.claude/local`, Homebrew). On the host the process gets `HOME`, `XDG_*`, `APPDATA`, `CODEX_HOME` pointing at a fresh directory under the temp dir (removed when the flow ends), so the user's own `~/.claude.json`, `~/.codex/auth.json`, … are never read or rewritten by Sessionboxer, and the browser openers the CLIs shell out to (`xdg-open`, `open`, …) are shadowed by no-op shims — the CLIs ignore `BROWSER` and would otherwise open a second tab on the host, which is the wrong browser when the Control Plane is a server. Where the CLI runs does not matter to the login: the browser part is always the user's. The Sandbox fallback is what makes this work from a phone against a server that has no CLIs installed; it never sees a browser or a credential store, it only gets the pasted code.

**"Signed in as …" comes from the host's own files, but only as a label — with one exception.** `GET /api/providers/:provider/host-login` reads the Provider's credential file in the real home when the Control Plane runs on the user's machine (Claude: `~/.claude.json` `oauthAccount`, MonoCode-style; Codex: the JWT claims of `auth.json`; Cursor: login or API key; Devin: the account fields of `credentials.toml`) and reports `account` plus whether it is `importable`. Codex, Cursor and Devin are: their file or key is exactly what the manual path pastes, so **Use this login** (`POST …/host-login/import`) stores it. Claude Code is not: `~/.claude/.credentials.json` holds an access token that expires in hours and a refresh token the host CLI rotates, so copying it would break boxes whenever the host refreshes (ADR-0002's reason for the one-year `setup-token`); the label is shown and the button starts the `setup-token` flow.

**Secrets stay where they were.** The flow never contains a credential, public settings never return one, raw CLI output is never logged, and token-shaped values are redacted from the errors a flow can end with. Nothing from the browser — cookies, passwords, profile — is read or copied anywhere; the browser is only ever given a URL.

**The manual path stays** under *Or do it by hand* in the connect wizard, for CLIs whose login changes shape before a Sessionboxer release catches up, and for headless setups where neither a CLI nor Docker is at hand.

## Considered Options

- **Copying the host's Claude credentials into the box** (what MonoCode reads for its usage meter): short-lived and rotated, see above. Rejected; the long-lived setup token stays the Claude credential.
- **Running the login inside the Session's Sandbox and finishing it in the Desktop pane's Firefox**: nothing is signed in there, no saved passwords, and Cursor's flow needs the CLI reachable from the page. That is the case ADR-0054 rejected too; the browser has to be the user's.
- **Only the host's CLI, no container fallback**: simpler, but a Control Plane on a server would need every CLI installed for a feature the Sandbox image already ships them for. The fallback is kept; the ADR is explicit that it has no access to anything of the user's.
- **A Claude Code `claude auth login` on the host and reading the result**: same short-lived credential as above, and writes into the user's real `~/.claude`.

## Consequences

- `node-pty` becomes a Control Plane dependency (prebuilt for macOS and Windows; compiled on Linux, as the Daemon already does).
- Verified with the four CLIs on a Linux host: each prints its URL (and Codex its code) within seconds in a scratch home and opens no tab of its own; the fake-process suite covers URL and OSC-8 parsing, terminal stripping, Claude's redraws, code before prompt, rejected code, a token in the output of a CLI that exited non-zero (error, nothing stored, token redacted), exit 0 without a login, Devin/Codex/Cursor result files, cancellation and flow replacement. **A sign-in completed against a real account has been run for none of the four in this commit**; the first real one per Provider is the test of the page-side of each flow.
- Windows hosts spawn `.cmd` shims through `cmd.exe /c`; the browser-opener shims are not applied there (the CLIs use `start`), so a Windows host may open the URL twice. Not verified on Windows or macOS.
