# The Agent runs inside the Windows VM; Linux keeps the orchestration and the desktop

ADR-0057 put a Windows VM next to the Linux Sandbox and kept the Agent on Linux: it saw and drove Windows over RDP, but its shell, repositories, MCP servers and `localhost` were the Linux box's, and "on Windows" meant `win <command>` or `win-scp`. The request that followed was that the Agent *live* in the VM — and, in particular, that an MCP server configured for a Session experiences Windows (its paths, environment, processes, `localhost`), not Linux. This ADR moves the Agent in and says what stays on the Linux side.

## Decision

**For `qemu-windows` Sessions the ACP Agent process runs inside the Windows VM; the Sandbox Daemon stays on Linux and starts it over SSH.** `AgentManager` spawns through an `AgentTransport`: the Linux transport is the `spawn()` it always was; `WindowsAgentTransport` runs `ssh agent@sbx-win-<session> <launcher> <acp command>` (with `sshpass -e`, the password in the environment, never an argument), and the ACP JSON-RPC stream is the SSH channel's stdio. Nothing in the ACP client changes: `session/new`, `session/load`, prompts, permission requests, MCP passing and the Cursor/Codex/Claude specifics are the same code, the child process is just further away. Before each start the transport waits for the VM to answer over SSH, ends any Agent still running from a previous start (`taskkill` of the launcher's `cmd.exe` tree), creates `C:\workspace`, copies the Provider's files in (Claude `settings.json` and `CLAUDE.md`, Codex `config.toml`/`AGENTS.md`/`auth.json`, Cursor `cli-config.json`/`auth.json`, Devin `config.json`/`mcp_config.json`) and writes the Agent's environment — provider tokens, `ANTHROPIC_BASE_URL` pointing at the Daemon's LLM inspector when Inspect LLM is on, git identity — as `%USERPROFILE%\.sessionboxer\agent-env.cmd`. The launcher, `%USERPROFILE%\.sessionboxer\sessionboxer-agent.cmd` (generated by the Daemon and copied in at bridge setup, so nothing Session-specific is baked into the base image), `call`s that file and deletes it, puts Node, npm's global bin, Git, uv, the Devin CLI and the Cursor CLI on `PATH`, `cd`s to `C:\workspace` and runs the ACP command with untouched stdio. Files the Provider rewrites while it works (Codex's and Cursor's `auth.json`) are pulled back after each turn so the refreshed token is stored as before.

**User-configured stdio MCP servers start in Windows, because the Agent does.** ACP hands the MCP list to the Agent at `session/new`, and the Agent spawns them: with the Agent in the VM, `npx`, `uvx`, a `.cmd` shim or an `.exe` from Global settings runs on Windows with `C:\workspace` as its cwd, the guest's environment and processes, and the guest's `localhost`. The transport only adapts the command line: a bare command that is neither an `.exe`/`.cmd`/`.bat` nor a known executable (`node`, `uvx`, `git`, …) is run through `cmd /c`, so npm's `.cmd` shims (`npx`, a globally installed server) resolve on Windows as they would in a shell; `env` entries pass through. HTTP/SSE servers are URLs and need no change.

**The desktop MCP stays on Linux and is reached over an authenticated bridge.** Screenshots, mouse and keyboard act on the RDP rendering of the Windows desktop in the Sandbox's X display, so the MCP process (xdotool, ffmpeg, the recorder and captions) keeps running there. The Daemon listens on a bridge port on the Sandbox's network address; for the Agent in the VM the `desktop` MCP entry becomes `node %USERPROFILE%\.sessionboxer\sessionboxer-bridge.js desktop`, a 40-line client that reads `bridge.json` (host, port, a per-boot random token), connects, sends `desktop <token>` and pipes stdio both ways; the Daemon side spawns the desktop MCP per connection and pipes it to the socket. Devin's `mcp_config.json` gets the same entry. The bridge accepts only connections presenting the token and only the two registered services; the token lives in the VM's user profile and in the Daemon's memory.

**Repositories are cloned and manipulated inside the VM, by the Daemon, with git credentials answered over the same bridge.** `Repos` gained a `RepoHost`: the Linux host runs git locally in `/workspace`; `WindowsRepoHost` runs `git.exe` in the guest through PowerShell over SSH, with paths under `C:\workspace`. The Control Plane seeds a Windows Session's repositories through a new Daemon RPC, `_sessionboxer/repos/seed`, instead of `docker exec git clone`: a git source is cloned in the guest with `-c credential.helper='!node …\sessionboxer-bridge.js credential <account>'`, and that helper — running on Windows — asks the Daemon over the bridge, which answers from the Session's connected accounts (the same `git-credential-sessionboxer` the Linux box uses); the token never touches the guest disk. A host-folder source is put into the Sandbox's `/workspace/<name>` mirror as before and pushed into the VM as one tar, unpacked by Windows' own `tar.exe`. The Session stays `creating` until the repositories are in the VM; the Agent starts, and the first prompt goes, only then, so it finds them. Adding and removing repositories, the repository state at turn end (branch, dirty, ahead, unpushed) and the `repos.json` manifest all go through the host. The Linux `/workspace` becomes a mirror, refreshed on demand: when Pull to folder asks for the manifest or the raw-file endpoint (videos, images and PDFs the Agent mentions) is hit, the Daemon first pulls the directory's git-listed files (and `.git`) back from the VM as one tar, so sync and downloads read what Windows has; uploads go the other way (`/workspace/.sessionboxer/uploads` in the box, copied into `C:\workspace\.sessionboxer\uploads` in the VM, and the prompt refers to the Windows path).

**The Terminal pane opens PowerShell in the VM.** The Daemon's terminal manager runs `sshpass -e ssh -t … powershell -NoLogo -NoExit -Command "Set-Location C:\workspace"` in the node-pty instead of `bash`, so a Terminal tab is an interactive PowerShell in Windows with the working directory of the Agent. `win`, `win-scp` and the Linux terminal remain reachable (the box's own shell is a `docker exec` away) but are no longer what the Agent is told to use.

**The Windows base image installs the Agent's toolchain at OEM time, pinned.** `images/windows/oem/install.bat` — run by dockur's unattended setup at the end of the base install — now installs Node.js 22 (MSI), Git for Windows (LF checkouts, symlinks, no credential manager, `core.longpaths`), uv/uvx, OpenSSH Server from Microsoft's Win32-OpenSSH MSI (the in-box capability cannot be added that early after setup: DISM fails with 0xc0040009) with `cmd.exe` as its default shell (so the launcher's command line is parsed by cmd, and PowerShell is invoked explicitly where wanted), `@anthropic-ai/claude-code`, `@agentclientprotocol/claude-agent-acp` and `@agentclientprotocol/codex-acp` at the same versions as the Sandbox image, the Devin CLI from its published Windows bundle (manifest → zip → SHA-256 check → `%LOCALAPPDATA%\devin\cli`), and the Cursor CLI's Windows package (`%LOCALAPPDATA%\Programs\cursor-agent`), plus `C:\workspace` and the user `PATH` for all of them; the screen/lock/update policies from ADR-0057 stay. No credential is in the image: tokens arrive with each Agent start through `agent-env.cmd` and the Provider files, on the Session's own overlay disk. Versions are set at the top of the script; a base installed before this change lacks the tools and must be reinstalled from Global settings → Windows VMs.

**What does not move: VS Code.** openvscode-server runs on the Linux side and would show only the mirror of the Workspace, so the Code pane says VS Code is not available for Windows Sessions yet and points at the Agent, the Terminal and the desktop; file links in the chat do not open it for them. The form, the header badge's tooltip and the briefing say where things run. `qemu-macos` is untouched: its Agent stays on Linux (`GuestVms.agentInGuest` is `false`), the `mac`/`mac-scp` bridge as in ADR-0059; the same transport shape applies when macOS follows.

## Considered Options

- **Keep the Agent on Linux and bridge only the MCPs into the VM** (a per-server SSH wrapper): MCPs would run on Windows but the Agent's own shell, file edits and git would stay Linux-side, and every tool result would be about a different machine than the desktop it sees; the request was the opposite.
- **The whole Daemon and the desktop MCP native in Windows** (ADR-0057's first option): the same for MCPs, plus pixel-exact screenshots and every key combination; at the price of a Windows port of the Daemon, node-pty, the recorder (gdigrab), the desktop MCP (Win32 input) and a second build to keep in step. The transport keeps one Daemon and one MCP; native desktop tools can come later behind the same bridge entry.
- **A shared folder (virtiofs/SMB) instead of a mirror**: dockur's VM has no shared folder into a sibling container, SMB from the Sandbox would need a server in the box and Windows' guest network, and consistency during a turn would be worse than a pull at turn end. The tar-based pull is simple and lets everything on the Linux side read files as before.
- **Baking the launcher and the bridge client into `C:\OEM`**: fixed paths and one less copy per start, but any change to them would need a base reinstall; generating them per Session from the Daemon keeps the base image a toolchain and puts Session logic where it is versioned.

## Consequences

- For a Windows Session the Agent, its stdio MCP servers, git and the Terminal run in Windows; paths in tool calls, the briefing and the repository manifest are `C:\workspace\…`. Linux keeps the Daemon, the desktop MCP and recordings (over RDP), the raw-file, sync and upload endpoints (on the mirror), the LLM inspector (listening on the Sandbox's network address for the VM), and the Control Plane's view of everything.
- One more thing per start: an SSH connection and a few scp copies (Provider files, environment, launcher) — seconds; a fresh Session waits for the VM to answer over SSH (a minute or two after boot) before its Agent starts, and repositories clone at the guest's speed.
- Requirements as ADR-0057, plus a base reinstalled with this OEM script (~40 minutes; it now also downloads Node, Git, the CLIs). Bases from before are refused by nothing but fail at the first Agent start with a clear log line; the guide says to reinstall.
- Security: the guest password is only ever in `SSHPASS` for `ssh`/`scp` processes in the Sandbox and in the Session's terminal env; provider tokens reach the VM in `agent-env.cmd`, deleted by the launcher at start and holding only for the seconds between; git credentials never reach the VM (answered per request over the bridge); the bridge takes a random token and two services only. Nothing of this is in the base image, the Sandbox image or a snapshot (Windows Sessions have none).
- The desktop over RDP behaves a little differently from X11: the Agent's shell runs in the SSH service session, so a GUI program started from it is invisible on the desktop (the briefing says to open programs from the Start menu), and typing at xdotool's default 12 ms per key drops characters on the way through the RDP client — the MCP types at 40 ms for VM desktops (`SESSIONBOXER_TYPE_DELAY_MS`, set by the entrypoint for Windows and macOS Sessions).
- Not done: VS Code for Windows Sessions (a remote-SSH server in the guest or a native openvscode-server there), `gh` in the VM (the briefing says git push/pull work, `gh` does not), native desktop tools (Win-key combinations RDP keeps), snapshots and forks (unchanged from ADR-0057), and the same move for `qemu-macos`.
