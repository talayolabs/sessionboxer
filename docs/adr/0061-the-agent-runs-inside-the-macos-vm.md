# The Agent runs inside the macOS VM, the way it runs inside the Windows one

ADR-0059 put a macOS VM next to the Linux Sandbox and kept the Agent on Linux, seeing and driving the Mac over VNC and reaching it with `mac <command>`; ADR-0060 then moved the Agent into the Windows VM and left a note that the same transport shape applies when macOS follows. This ADR is that step: for `qemu-macos` Sessions the Agent, its stdio MCP servers, git and the Terminal run in the Mac, and the Linux side keeps what it kept for Windows.

## Decision

**The Windows guest plumbing became one `Guest` with two flavours, and `qemu-macos` uses the POSIX one.** `packages/sandbox-daemon/src/guest.ts` now has an abstract `Guest` — the SSH/scp/tar transport, `guestPath` containment, `waitReady`, `putFile`/`pushDir`/`pullDir`, the bridge services back to Linux — and two subclasses that only spell paths and shells: `WindowsGuest` (backslashes, `cmd`/PowerShell, `tar.exe`, `.cmd` shims) is what ADR-0060 described; `MacGuest` uses forward slashes under `/Users/agent`, `bash -c` with a base64-encoded script for the Daemon's own commands, `zsh -l` for the Terminal, BSD `tar`, `mkdir -p`/`test -e`/`rm -rf`. `GuestAgentTransport` and `GuestRepoHost` (the former `WindowsAgentTransport` and `WindowsRepoHost`, unchanged in what they do) take either. The Daemon picks the flavour from its environment: `SESSIONBOXER_WINDOWS_HOST` or `SESSIONBOXER_MACOS_HOST`, set by the Control Plane's `sandboxEnv()` of the VM backend.

**The ACP Agent is spawned as `ssh agent@sbx-mac-<session> ~/.sessionboxer/sessionboxer-agent.sh <acp command>`.** The launcher (generated by the Daemon and copied in at bridge setup, like the Windows `.cmd`) puts `/usr/local/bin` and `~/.local/bin` first on `PATH`, sources and deletes `~/.sessionboxer/agent-env.sh` (provider tokens, `ANTHROPIC_BASE_URL` for the LLM inspector, git identity — written by scp right before the start, gone seconds later), records its process group so the next start can end a previous Agent (`kill -- -<pgid>`), `cd`s to `/Users/agent/workspace` and `exec`s the command with untouched stdio: the ACP stream is the SSH channel. Provider files go to the macOS locations — `~/.claude/settings.json` and `CLAUDE.md`, `~/.codex/config.toml`, `AGENTS.md`, `auth.json`, `~/.cursor/cli-config.json`, `auth.json` (Cursor reads `AGENTS.md` from the working directory upwards, so the briefing is put at `/Users/agent/AGENTS.md`), `~/.devin/config.json`, `mcp_config.json` — and the ones the Provider refreshes (Codex's and Cursor's `auth.json`) are pulled back after each turn. The briefing is `images/sandbox/macos-briefing.md`: zsh and BSD tools, the Workspace, `open -a` from the shell showing on the desktop (the SSH session is the logged-in user's), ⌘ as `super` through VNC, recordings and the raw-file paths.

**User-configured stdio MCP servers run in the Mac; the desktop MCP stays on Linux.** With the Agent in the guest, the MCP list it gets at `session/new` is spawned there: `npx`, `uvx`, a binary — resolved by the guest's `PATH`, with `/Users/agent/workspace` as cwd and the Mac's `localhost`. No command rewriting is needed on POSIX (Windows needed `cmd /c` for `.cmd` shims); `env` entries pass through. The `desktop` entry becomes `node ~/.sessionboxer/sessionboxer-bridge.js desktop` against the same authenticated bridge as Windows (host, port and per-boot token in `bridge.json`), so screenshots, mouse, keyboard and recordings keep acting on the VNC rendering in the Sandbox's X display. HTTP/SSE servers are URLs and unchanged.

**Repositories live in `/Users/agent/workspace/<name>`, cloned by the guest's git with credentials over the bridge.** `GuestRepoHost` runs `git` in the Mac over SSH; `sessions.ts` asks the VM backend for the path (`GuestVms.repoPath(name)`: `C:\workspace\x` on Windows, `/Users/agent/workspace/x` on macOS) instead of assuming Windows; the credential helper is `!node ~/.sessionboxer/sessionboxer-bridge.js credential <account>`, answered by the Daemon from the Session's accounts, so no token reaches the guest disk. Host-folder sources go through the Linux mirror and one tar, unpacked by BSD `tar`; the Linux `/workspace` is the mirror the raw-file, sync and upload endpoints read, refreshed by a `tar` pull from the Mac on demand; uploads are copied into `/Users/agent/workspace/.sessionboxer/uploads` and the prompt names that path. The web accepts `/Users/agent/workspace/…` wherever it accepted `C:\workspace\…` (attachments, file links).

**The Terminal pane is `zsh -l` in the Mac.** `terminals.ts` runs the guest's `terminalCommand()` in node-pty: `ssh -t … 'cd /Users/agent/workspace; exec zsh -l'`. `mac` and `mac-scp` stay in the Sandbox image as Linux-side conveniences (`docker exec` into the box) but are no longer what the Agent or the user is told to use.

**The base gets the toolchain when it is provisioned, and the Sandboxes get an SSH key.** `finish()` in `macos.ts` — the step that runs over SSH once the freshly installed guest answers — now also installs, pinned to the Windows base's versions: Node 22.23.3 from the official tarball for `uname -m` (arm64 or x64) into `/usr/local` (made writable by `agent` so `npm -g` needs no sudo); git through Apple's Command Line Tools, `softwareupdate --install` of the label it lists (`/usr/bin/git` on a fresh macOS is a stub that asks to install the CLT, so there is no lighter choice; Homebrew is not used, its formulae move); uv 0.12.13 from Astral's pinned installer into `~/.local/bin`; `@anthropic-ai/claude-code` 2.1.272, `@agentclientprotocol/claude-agent-acp` 0.77.0 and `@agentclientprotocol/codex-acp` 1.1.9 with `npm install -g`; the Devin CLI 3000.10.27 through its pinned `setup.sh` (checksummed bundle, `~/.local/bin/devin`); the Cursor CLI 2026.09.23-86fc751 from its macOS package under `~/.local/share/cursor-agent`. `~/.zprofile`, `~/.zshenv` and `~/.bash_profile` get the `PATH` line (a non-interactive `ssh vm cmd` runs zsh, which reads `.zshenv` only). The script is idempotent (every step checks what is there), its lines stream into the install log, and `SBX_PROVISIONED` at its end is what the Control Plane waits for. The `agent` password and the Sandbox key arrive on the script's stdin — never on a command line — and the script also appends an ed25519 public key to `~/.ssh/authorized_keys`: the pair is generated by `ssh-keygen` in a throwaway Sandbox container the first time a base is provisioned and stored write-only in Settings (`macos.sshKey`, `macos.sshPublicKey`); each Session's Sandbox gets the private half in its environment, the Daemon writes it to tmpfs (`0600`) and removes it from its environment, and every `ssh`/`scp` of the Daemon uses `-i` — `sshpass` only remains for the Control Plane's provisioning itself and for `mac`. `macos-base.json` records the toolchain generation (`TOOLCHAIN`); a base without it or with an older one shows **Reprovision** on the settings page and refuses Sessions until it ran.

**Reprovision boots an installed base once more, unattended.** `POST /api/macos/reprovision` starts `sbx-macos-install` on the base volume exactly like an install (auto-login is set — `sysadminctl -autologin set` fails over SSH on macOS 15 with `SACSetAutoLoginPassword error:22`, so provisioning writes the classic `/etc/kcpassword` itself when it does — and Remote Login is on, so the Mac boots to the desktop and answers on SSH within a minute or two), skips the Setup steps, runs the same `finish()` and lets the guest power off. The base disk is written, so it is refused while any macOS Session (running or stopped) builds on it; a failed reprovision leaves the base as it was, with the error and log next to **ready**. So bases installed before this ADR are not reinstalled: they are reprovisioned in place, ~10–30 minutes, mostly Apple's CLT download.

## Considered Options

- **Keep the Agent on Linux and only bridge MCPs into the Mac**: refused for Windows in ADR-0060 for the same reasons; the desktop the Agent sees and the machine it works on would differ.
- **A separate `MacGuest`/`MacAgentTransport` copy of the Windows classes**: half of `guest.ts` duplicated for a dozen path and shell differences; the abstract `Guest` keeps the SSH, bridge, mirror and transport logic in one place and the flavour classes small.
- **Homebrew for the toolchain**: one command for git, node and uv, but non-deterministic pins (formulae move, `node@22` floats), a long bootstrap and Xcode CLT anyway. Official tarballs and installers, pinned, as on Windows.
- **Password auth per command (`sshpass`) as ADR-0059 did**: works, but every Agent start, scp and git call would carry the password in a process environment; a key pushed once at provisioning removes it from the Session's hot path.
- **A toolchain in the Sandbox image pushed into the guest per Session**: Node and the CLIs are hundreds of MB; a Session would take minutes longer to start and Apple's CLT cannot be pushed anyway.

## Consequences

- For a macOS Session the Agent, its stdio MCP servers, git and the Terminal (zsh) run in the Mac; paths in tool calls, the briefing and the repository manifest are `/Users/agent/workspace/…`. Linux keeps the Daemon, the desktop MCP and recordings (over VNC), the raw-file, sync and upload endpoints (on the mirror), the LLM inspector and the Control Plane's view of everything — as for Windows.
- An existing macOS base must be **reprovisioned** once from Global settings → macOS VMs (no reinstall; the Setup Assistant password stays). Apple's licence caveat from ADR-0059 is unchanged: dockur runs macOS on non-Apple hardware, Sessionboxer ships nothing of Apple's, and using `qemu-macos` there is the user's decision under Apple's terms.
- Provisioning reaches nodejs.org, astral.sh, registry.npmjs.org, static.devin.ai, downloads.cursor.com and Apple's software update servers from the guest; the last is the slow and the fragile one (the same CDN the installer uses).
- Security: the password is on stdin of the provisioning script and in `SSHPASS` of the Control Plane's throwaway ssh containers and of `mac`; the private key is in the Sandbox's environment at start, then only on its tmpfs; provider tokens are in `agent-env.sh` for the seconds between scp and launcher; git credentials never reach the guest; the bridge takes a random token and two services. Nothing of this is in the base disk except the public key in `authorized_keys`.
- `open`, `osascript` and other GUI-touching commands from the SSH session act on the logged-in desktop because it is the same user's session (unlike Windows' service session), so the Agent can open apps without Spotlight; the briefing says so. QEMU's VNC passes ⌘ as `super`; some Linux-side combinations may still be taken before they reach the Mac.
- Not done: VS Code for macOS Sessions, `gh` in the guest, native desktop tools, snapshots and forks (ADR-0059), a clipboard.
