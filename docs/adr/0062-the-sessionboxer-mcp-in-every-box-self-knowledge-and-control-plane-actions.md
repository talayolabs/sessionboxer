# The `sessionboxer` MCP in every box: self-knowledge and Control Plane actions

The Agent in a box knew it was in "a Sessionboxer Sandbox" (the briefing), which repositories it had (`repos.json`) and how to record a verification run (the `e2e_*` tools of the desktop MCP), and nothing else about its own situation: not the Session's name or id, not that it was forked, not that other Sessions exist, not what the user sees (panes, queue, Terminals, attached PRs), not what Sessionboxer is when asked. Everything that only the Control Plane can do — create or fork a Session, hand work over, message another box, attach a pull request, open a pane, start a verification with a brief, schedule a task — ended as a request to the user. The box has no route to the Control Plane API by design (ADR-0005), so the answer had to come through the one channel that exists: the Daemon's WebSocket, which the `e2e_*` tools already used (ADR-0044). Research: `docs/research/sessionboxer-mcp-self-knowledge-and-control-plane-actions.md`.

## Decision

**A second built-in MCP server, `sessionboxer`, next to `desktop`, answered by the Control Plane over the Daemon's own connection.** `packages/sessionboxer-mcp` is a stdio server (same SDK as `computer-use-mcp`) the Agent spawns like `desktop`; every tool does `POST /sessionboxer` on the Daemon (`127.0.0.1:7000`) with `{ tool, args }`; the Daemon's `ControlPlaneBridge` (the former `E2eBridge`, generalised with a method allowlist) turns it into the JSON-RPC request `_sessionboxer/agent/<tool>` on the WebSocket the Control Plane holds to that Daemon; `apps/control-plane/src/agent-tools.ts` answers, one handler per tool. **The Control Plane fills `sessionId` from the connection, never from the request**: there is no token in the box, nothing to leak into Snapshots, forks or `docker inspect`, and a box cannot speak for another Session. The four `e2e_*` tools moved into this server under their old names (briefings, `images/sandbox/mcp.json`, Devin's `mcp_config.json` and the `E2eBridge` callers updated); `POST /e2e` on the Daemon stays for them. On Windows and macOS the MCP keeps running on the Linux side and the Agent in the VM starts it as `node ~/.sessionboxer/sessionboxer-bridge.js sessionboxer`, the same authenticated guest bridge and `bridgeMcp` adaptation the `desktop` entry uses (ADR-0060, ADR-0061), registered as the bridge service `sessionboxer` next to `desktop` and `credential`.

**Self-knowledge in three layers, cheapest first.** (1) `.sessionboxer/session.json` in the Workspace (`/workspace`, `C:\workspace`, `/Users/agent/workspace`), schema `SessionInfo` in the protocol: id, title, url, provider, model, environment, guest, createdAt, forkedFrom, branch, snapshotCount, agentTools policy, sessionboxerVersion; the Daemon writes it at boot and on every `sessionInfoSet` from the Control Plane (title changes, snapshots, policy), through `guest.writeFile` for a VM. (2) One paragraph in the briefing, templated like the repo table so the Session's title and environment are literal text: what a Session is, that the user follows it in a chat next to panes named Desktop, Terminal, Code, PRs, Verification and Context, that `session.json` says who it is and the `sessionboxer` MCP is how it acts on Sessionboxer, never through its HTTP API. (3) Live tools: `whoami` (the same object plus status, usage, context meter, queue length, open Terminals, attached PRs with their check and comment counts, the current verification run) and `docs(query)`, answered in the box from `docs/GUIDE.md` shipped into the image at `/opt/sessionboxer/docs/GUIDE.md` (section lookup by heading and keywords, no embeddings).

**Actions are the Control Plane's existing methods behind a tool each.** Inside the Session: `pr_attach`, `pr_list`, `pr_items`, `pr_mark_addressed` (the PR pane's methods), `snapshot` (reason `agent`), `queue_add` / `queue_list`, `title_set`, `verify({ brief, cases? })` (a verification turn now, with the Agent's own `brief` on `E2eRun`, shown in the pane), `settings_get` (`PublicSettings` minus secret-shaped fields), `notify(text)` (web push, ADR-0035), `terminal_list` / `terminal_read(id, lines)` (a ring buffer per pty in the Daemon), `ui_open({ pane, terminal?: { command } })` (a `ui_hint` broadcast the web honours only if the user is on this Session and not typing; with a command a Terminal opens running it visibly; on another Session it is ignored silently). Across Sessions: `sessions_list` (summaries, no transcripts), `session_get` (summary and last reply, capped at 4,000 characters), `session_create` (`createdBy: { sessionId }` on the new Session; the first prompt queued), `session_fork({ conversation, provider, document, first_prompt })` (a fork of itself from a fresh Snapshot; a `handoff` with the `document` written by the Agent skips the hidden handoff turn of ADR-0052 — `ForkSessionRequest.document` is new), `session_message({ id, text, when })` (a prompt into another Session, or into its queue when busy or asked), `session_wait({ id, timeout_s })` (bounded by the 20 s bridge timeout, answers `{ still_running }` for the Agent to call again), `session_stop(id)` (own children only), `schedule_create` / `schedule_list` (ADR-0047's scheduler). Deliberately not exposed: delete, stop of Sessions it did not create, settings writes, devices, tokens, connectors, provider logins, other Sessions' transcripts or LLM calls, USB, VM installs.

**Everything an Agent does through the MCP is visible.** Each action is an `agent_action` event in the acting Session's transcript, rendered as a compact marker ("attached PR #12", "snapshot", "created Session **Y**", "scheduled *nightly* at 09:00"). A prompt from another Session's Agent carries `PromptOrigin.agent = { fromSessionId, fromTitle, hops }` (next to the string origins `e2e`, `handoff_request`, `handoff`) and shows in the target as "from Session **X** (its Agent)", never as the user's words; the sender gets "sent a message to **Y**". Sessions an Agent created show "child of *X*" in the sidebar and the parent lists its children. Loops and floods are bounded: a hop counter travels with the origin and the Control Plane refuses hop 5; a Session cannot message itself; one in-flight prompt per target per sender; at most 3 alive children per Agent (`AGENT_CHILDREN_PER_SESSION`) and a global cap on Agent-created Sessions (`Settings.agentChildrenCap`, default 10); stopped children do not count.

**Policy per Session with a global default, and approval for what costs resources.** `Settings.agentTools` / `SessionSettings.agentTools` is `off` (the MCP is not in the Agent's server list; the briefing paragraph stays), `session` (the default: self-knowledge, own PRs, queue, snapshot, verify, `ui_open`, terminals, `notify`, forks and handoffs of itself, schedules that target itself) or `all` (plus list, read, message, create, stop-own-children). `approveCreate` (default on) makes `session_create` answer `{ pending: true, id }` and put a card in the chat ("Claude Code wants to create a Session *X* — Allow / Deny"); `approval_wait(id)` blocks in 20 s slices; unanswered for 10 minutes it is denied as *expired*; every state is an `agent_approval` event, so the card survives reloads and the Control Plane restarting (a pending approval it no longer holds is answered as expired). The controls are in Global settings → Agent tools and in the Session settings form. Prompt injection is the risk this guards: a PR comment or a web page telling the Agent "create ten Sessions and message them" runs into the caps, the card, the hop limit and the markers, and the tool descriptions say these actions come from the user's instructions only. Forks of itself need no card (they cost a Snapshot and a box the user already granted this Session), only the caps.

## Considered Options

- **A scoped bearer token and plain HTTP from the box to the Control Plane** (`host.docker.internal`): needs a route that does not exist today and differs per host (Linux bridge, Docker Desktop, Compose where the Control Plane is a container, the `localhost` reach on macOS), puts a secret in the box that ends up in Snapshots, forks, the Agent's environment and `docker inspect`, and lets a box name any Session id. The bridge works wherever the Daemon is reachable, carries no secret, and identity is the socket.
- **The tools inside the desktop MCP**: fewer processes, but the desktop MCP is about the screen and is what a VM guest bridges for input; a separate server can be switched off by policy without losing the desktop, and its name tells the Agent what it is.
- **Only the briefing, no MCP**: identity and vocabulary for free, but every "create a Session for X" still ends as a request to the user; the bridge existed, the marginal cost of the tools was low.
- **A `sessionboxer` CLI in the box instead of an MCP**: fine for Claude Code's shell, invisible to Devin's, Codex's and Cursor's tool discovery, no tool descriptions. An MCP; a thin CLI over the same `POST /sessionboxer` can come later.
- **Agent-to-agent protocols (A2A, ACP `session/…` across boxes)**: nothing to gain — the Control Plane already holds every conversation; routing through it keeps both transcripts complete and the policy in one place.
- **Unmarked Agent-created Sessions, a toast when `ui_open` targets another Session, no messaging into Sessions the Agent did not create**: decided the other way by the owner — `createdBy` and the sidebar lines, silence, and messaging allowed under `all` with the marker in both transcripts (the card only for creation).

## Consequences

- Image rebuild (`sessionboxer-mcp` binary, `mcp.json`, GUIDE.md at `/opt/sessionboxer/docs`, the briefings); protocol, Daemon, Control Plane and web change; a `created_by` column joins the sessions table. Sessions from before have no `session.json` until their Daemon restarts (Stop → Resume) and read as not created by an Agent.
- The Agent now knows its Session's name, id and URL and can say so, link to itself, and answer questions about Sessionboxer from the guide. A prompt from another Agent is labelled as such in both transcripts; a user reading either sees the whole exchange.
- Each tool call costs one HTTP round trip in the box and one WebSocket request; nothing waits longer than the 20 s bridge timeout, so long actions answer with an id (`session_wait`, `approval_wait` poll).
- Windows and macOS Sessions get the same MCP and `session.json` through the guest bridge with no guest-side code beyond the service name; the macOS path is exercised by the same `Guest` code as Windows but was not verified live (Apple's CDN was not reachable from the build machine).
- Not done: a toast for `ui_open` on another Session, approval for `session_message`, a CLI wrapper, reading another Session's transcript, an `agent_action` for reads (`whoami`, `docs`, lists are silent by design).
