# Automations: triggers, actions and limits, run by the Control Plane

Scheduled tasks (ADR-0047) were the one way Sessionboxer acted without a prompt from the user: a cron expression, one of two actions. The owner asked for two more kinds of unattended work — follow every open pull request of a repository or account and, when one opens or changes, have an agent review it or run Auto QA and publish the video — and for these to live on one page with the schedules, the way Devin's Automations do. Research: `docs/research/automations-follow-prs-and-react-to-events.md`.

## Decision

**An automation is `{ trigger, action, limits }`; schedules are one trigger among three.** `AutomationTrigger` is `schedule` (cron, time zone, missed-run policy — exactly what a schedule had), `pr_event` (which PR follows to listen to, which events, filters for drafts / forks / authors / base branch / title / labels) or `manual` (Run now only). `AutomationAction` is `prompt` (a Session, or *the Session the PR is attached to*), `new_session` (the template of before, plus *clone the PR head first*), `auto_review`, `auto_qa`, `attach` and `notify`. `AutomationLimits` caps Sessions at once, runs per day, runs per PR per day, a debounce after pushes and the time a run may take. Prompts and titles take `{pr.number}`, `{pr.title}`, `{pr.url}`, `{pr.repo}`, `{pr.headSha}` and `{event}`. The shapes are zod in the protocol, so the API, the web and the `sessionboxer` MCP share one definition.

**Two tables replace two tables, and the old ones migrate once.** `automations` (trigger, action and limits as JSON; `next_run_at`, `last_run_at`, `last_status`) and `automation_runs` (trigger `cron` / `manual` / `catch_up` / `pr_event`, status `queued` / `running` / `succeeded` / `failed` / `skipped`, the PR event and head, the followed PR and its URL and title, the Session, queued / started / finished, a detail line, the error, and a typed `result` — a review's verdict and findings, a QA run's score and video). On the first start after the upgrade `AutomationStore` copies every `schedules` row into `automations` with the same id and a `schedule` trigger, every `schedule_runs` row into `automation_runs`, and drops the old tables. The last 500 runs are kept per automation (100 before; PR events are more frequent).

**`Automations` is the `Scheduler` with the trigger made explicit.** The same 30-second tick, the same compare-and-set claim on `next_run_at`, the same missed-run policy, the same tracking of a run to `onTurnSettled()` and the same failure paths (Session error, deletion, stop, timeout — now the automation's own `timeoutMinutes`). What is new is a small extension surface for the stages that follow: `runForPr()` for the followed-PR poller to call once it has matched, deduplicated and capped an event; `recordSkipped()` for a run that did not happen and why; `runners` (one `ActionRunner` per action the engine does not run itself: `auto_review`, `auto_qa`, `attach`) and `settledHooks` (what a settled Session produced, before the row closes). An action without a runner fails its run with a message rather than silently succeeding.

**The old names stay for a release.** `/api/schedules*` answers with the `Schedule` shape, computed from the automations whose trigger is a schedule (`scheduleOf`), and accepts the old create / update bodies (`automationOfSchedule`). `schedule_create` and `schedule_list` do the same for the agent; `automation_create`, `automation_list` and `automation_runs` are the full tools, with the same policy rule as before extended to the new actions (a prompt to itself, `attach` and `notify` work under *This Session only*; anything that prompts another Session or starts one needs *All Sessions*). `#/schedules` lands on `#/automations`. The `schedules` / `schedule_runs` WebSocket messages became `automations` / `automation_runs`; the web is their only consumer and ships with the Control Plane.

**One page, three steps.** `#/automations` lists every automation with its status badge, trigger, action, next / last run and today's count against the cap; `#/automations/<id>` opens one with its history. The form discloses progressively — *When* (trigger), then *Do* (action; the choices depend on the trigger: only a PR trigger offers review, QA, attach and *the attached Session*), then *Limits* — because a schedule that prompts a Session needs three fields and a PR review needs fifteen. The Session's **Scheduled** pane keeps its name and shows the automations that prompt that Session. Pull requests are deliberately not on this page: following a PR is its own thing (a separate `#/prs` page, stage 1) and an automation merely listens to follows.

## Considered Options

- **Keep `schedules` and add a `pr_automations` table, unified only in the UI**: two schedulers, two run histories, two MCP tool families, and every later trigger (a webhook, a Slack message) would add a third. One table with a discriminated `trigger` column costs a one-time migration.
- **A nullable `session_id` on `pull_requests` for followed PRs instead of new tables**: the PR data is per-Session today (seen state, Address, auto-merge); following is per provider account and repository. Stage 1 adds `pr_follows` / `followed_prs` / `pr_events` and links an attached PR to its followed row rather than bending the existing table.
- **Running actions inside `Automations` rather than through `runners`**: review and QA need the PR poller, the connectors and the E2E engine; keeping them in their own modules keeps `automations.ts` about triggering, tracking and history.
- **Dropping the `/api/schedules*` routes at once**: the desktop app and any script the owner wrote against them would break for no gain; the aliases are forty lines.

## Consequences

- No image rebuild for this stage; an existing `db.sqlite` migrates on the next start and the old tables are gone afterwards (a downgrade would find no schedules).
- A schedule's run history shows one more column (the PR) and `queued` as a status the old UI never had; the `Schedule` alias maps `queued` to `running`.
- The next stages fill in what this one only shapes: followed PRs and `pr_event` triggers (stage 1), `auto_review` (stage 2), `auto_qa` with the video on the PR (stage 3), signed webhooks as an accelerator of the poller (stage 4).
