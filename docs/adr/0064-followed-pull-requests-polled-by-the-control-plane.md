# Followed pull requests, polled by the Control Plane, feed automations

A pull request in Sessionboxer was something a Session had: pasted into a prompt or opened by the agent, attached to that Session and polled from its box (ADR-0027, ADR-0050, ADR-0051). The owner wants to see every open PR of a repository or account with no Session involved — to read the failing checks and comments by hand — and to have automations (ADR-0063) react when one opens or changes. This ADR covers the following, the polling and the events; the review and QA actions come in later ADRs.

## Decision

**A follow is a scope, not a PR.** `pr_follows` rows are `{ provider, host, account, kind: repo | mine | requested, owner?, repo? }`, unique on that key. `repo` lists the open PRs of one repository (`GET /repos/{o}/{r}/pulls`, Bitbucket `…/pull-requests?state=OPEN`), `mine` and `requested` are search-backed (`is:pr is:open author:@me` / `review-requested:@me`; Bitbucket's `/dashboard/pull-requests?role=AUTHOR|REVIEWER`). A follow reads with one connected login's token, from the Control Plane only — never through a box. The `sessionboxer` MCP gets `pr_follow` and `pr_followed_list`; the agent follows, it does not get the token.

**Followed PRs are their own tables, not `pull_requests` with a nullable `session_id`.** `followed_prs` is unique on `(provider, host, owner, repo, number)` and holds the PR head (`head_sha`, `head_ref`, `head_repo`, `is_fork`), reviewers, labels, the review decision, sync state and ETags; `followed_pr_sources` links a PR to the follows it came in through (a PR seen by two follows is one row; it is deleted when its last follow goes); `followed_pr_items` and `followed_pr_checks` are the same shape as the Session tables and share their store code (`PrItemsStore`, the base `PrStore` now extends). `pull_requests` is untouched: attaching a followed PR to a Session (`POST /api/prs/:id/attach`) creates a normal attached PR there, and the followed row lists its `attached` Sessions.

**Three polling tiers, one queue per login.** Every enabled follow's list is polled once a minute (repository lists with `If-None-Match`, so an unchanged list costs no rate limit; search has no ETags and is one request a minute), every open PR's detail (comments, reviews, threads, checks) every five minutes and at once when the list shows a new head or `updatedAt`, and a full detail refresh every thirty minutes. Requests of one account run serially through one queue so the `Retry-After` and `x-ratelimit-remaining` headers throttle everything behind them; a `403`/`429` sets `retry_at` and the follow shows *rate limited*; a `401`/`404` marks the follow or PR *unauthorized* / *not found* until the next successful read. Closed and merged PRs stay seven days, then are purged.

**Events are derived by diffing snapshots, and they are the only thing automations see.** After each read the poller compares the new state with the stored row and inserts `pr_events` (`opened`, `synchronize`, `comment`, `review_submitted`, `check_failed`, `ready_for_review`, `merged`, `closed`, `review_requested`), unique on `(followed_pr_id, type, head_sha, ref)` so a re-read never fires twice. `opened` waits for the first detail read (`pending_opened`) so the event carries the head SHA and the trigger's filters have the author, draft and fork flags; a PR older than a day when its follow is created gets no `opened`. Each event is offered to every enabled automation whose `pr_event` trigger lists the follow (or no follow — all of them) and the event type, and passes the filters: drafts skipped, forks *review only* (the review action may run, nothing that checks the head out with secrets does), authors *not self* (the connected login's own PRs and comments do not trigger it, so an automation's own review cannot retrigger it), an optional base branch, title pattern and labels. Then the limits: a debounce window collapses a burst of pushes into one run, a run for the same PR still queued or running is deferred (and re-offered when it ends), `maxConcurrent`, `maxRunsPerDay` and `maxRunsPerPrPerDay` skip the run with the reason in the history. The `attach` action attaches the PR to the Sessions of the trigger's choice and finishes at once; `notify` pushes; `prompt` with `sessionId: "attached"` prompts the Sessions the PR is attached to; the review and QA actions are Stage 2 and 3.

**A page of its own.** `#/prs` lists the follows as chips and the PRs needs-attention first; `#/prs/<id>` shows one PR with its chips, checks (copyable, with the summary and log link), comments and reviews grouped by thread (the same components as the Session pane), events and automation runs, and the actions *Attach to Session*, *Start Session* (a new Session on `head_repo` at `head_ref`, PR attached, with the user's prompt or a brief) and *Run automation…*. There is no *Address* here on purpose: that needs an agent, which needs a Session.

## Considered Options

- **Nullable `session_id` on `pull_requests`**: every query, the seen state, Address and auto-merge are per Session; a PR followed and attached twice would be three rows with different semantics in one table. Separate tables with a link cost one join.
- **Webhooks first**: the Control Plane is usually not reachable from the internet (GUIDE → Remote access). Polling is the source of truth; `POST /api/hooks/*` (Stage 4) will only pull a follow's poll forward.
- **Polling from the boxes with `gh api`, like attached PRs**: a follow has no box. The Control Plane has the Connectors' tokens already (Bitbucket PRs and auto-merge use them); GitHub follows use them the same way.
- **Events fired straight from the diff without persisting them**: a restart mid-poll would fire twice or never; the unique key on `pr_events` is the dedupe and the page's Events list is free.
- **Following a PR runs an automation**: the owner wants the list for manual investigation as well; following and reacting stay separate, an automation names the follows it listens to.

## Consequences

- New tables `pr_follows`, `followed_prs`, `followed_pr_sources`, `pr_events`, `followed_pr_items`, `followed_pr_checks`; new routes under `/api/prs`; WebSocket messages `pr_follows`, `followed_prs`, `followed_pr_items`, `followed_pr_checks`, `pr_events`; MCP tools `pr_follow`, `pr_followed_list`.
- A repository followed with a login that can read it costs one conditional request a minute plus one detail read per changed PR; a search follow costs one search request a minute (GitHub allows 30). A PR both attached and followed is polled twice for now; Stage 4 dedupes.
- `automations.ts` gained a `{ done }` result for actions that complete without a Session (attach), `followExists` and `prHeadRepo` hooks the followed-PR service fills in.
- The Session-level PRs pane and every attached-PR API are unchanged.
