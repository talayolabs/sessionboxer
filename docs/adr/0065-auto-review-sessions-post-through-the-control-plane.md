# Automatic reviews: a Session reads the PR head, the Control Plane posts the review

ADR-0064 gave the Control Plane followed pull requests and their events; ADR-0063 the automations that react to them. The owner wants a review to appear on a PR when it opens or gets new commits, with no prompt from him. Agents can already post through `gh` from their box (ADR-0027), but a review Session runs unattended on code nobody looked at, sometimes from a fork: the Connector token must not be in that box, the review must be one identifiable comment (not a stream of `gh` calls), and the same head must not be reviewed twice.

## Decision

**The head is fetched as the platform's PR ref, never as the fork's branch.** `RepoSource.ref` may be a full refspec — `refs/pull/{n}/head` on GitHub, `refs/pull-requests/{n}/from` on Bitbucket Data Center (`prRefspec`, `isPrRefspec`). The seeding code (Control Plane `git clone` into the box, the Daemon's host-side clone for VM Sessions) clones the base repository, `git fetch origin <refspec>` and checks it out as the local branch `pr/{n}`; a plain ref is still `git clone --branch`. Same-repository PRs keep cloning the head branch so a Session can push to it. A fork PR's review Session gets **no Connector in its MCP list** (so no credential in the box) **and no Docker**; the base repository must therefore be readable without a token, which is the case for public repositories — a private base with a fork PR fails the clone and the run says so.

**The review Session is an ordinary Session with one tool it can only use here.** `auto_review` starts a Session (Provider and model from the action, `e2eVerify` off, Agent tools at least *This Session only*) on the head, attaches the PR to it, and prompts it: the PR, the base, the head, `git diff` to read, what to look for, and the PR's description fenced in `<pr-description>` and named as the author's words, not instructions — the same trust boundary as the *Address* prompt of attached PRs. The extra instructions of the automation go in the prompt. The Session ends its review by calling **`pr_review_submit`** (verdict, summary, inline findings with path, line, side and severity). The Control Plane resolves the calling Session through the bridge, finds the *running* `auto_review` run whose `session_id` it is, refuses any other caller ("not an Auto review run") and a second call of the same run, and posts with the follow's token. A Session that ends without calling the tool fails the run ("no review was posted"). The transcript gets an `agent_action` marker ("review posted: 3 findings, comment → link").

**Posting is one review, shaped by the Control Plane.** The verdict is capped by `action.maxVerdict` (`comment` by default): a verdict above the cap is posted as a `comment` and the body says which verdict the Agent wanted. GitHub: one `POST /repos/{o}/{r}/pulls/{n}/reviews` pinned to the head `commit_id`, with the findings whose path is in `GET …/pulls/{n}/files` as inline comments; if GitHub refuses a position (422) the review is posted again with every finding folded into the body. Bitbucket: one comment per finding anchored to `{ path, line, lineType: ADDED, fileType: TO, diffType: EFFECTIVE }` (an anchor Bitbucket refuses is folded), one general comment with the summary, and `PUT …/participants/{userSlug}` with `APPROVED` / `NEEDS_WORK` when the verdict says so. Every body starts with `**Sessionboxer review** · n findings (h high) · head \`sha7\` · verdict · [Session] · [Automation]` and ends with `<!-- sessionboxer:automation={id} run={id} head={sha} -->`. The run's `result` is `{ type: "review", verdict, findings, high, url }`; `notifyOn` (`findings` by default) decides whether a push notification goes out.

**Delta reviews and loops.** `automation_pr_state (automation_id, followed_pr_id)` keeps `last_reviewed_sha`, the run and the review's URL. With `deltaOnly` (default) the next run on a new head is told to review `git diff {last}..HEAD` and to fall back to the whole change when that commit is gone (rebase, force-push); the posted body says "Covers the changes since `sha7`". A review never retriggers its own automation: the follow's login is the reviewer, and the `review_submitted` / `comment` events it causes are the login's own activity, which the trigger skips unless *include own* is on (ADR-0064); the dedupe on `(automation, PR, event, head)` keeps one head at one review per automation. The *not self* author filter now means "opened by one of this Control Plane's Sessions" (an attached PR row with `attached_by = agent`), so the user's hand-made PRs under the same login are still reviewed while the Agents' own PRs are not.

## Consequences

- The box of a review Session never holds the Connector token; a fork's code runs with no credentials and no Docker. Posting is one request (or one per finding on Bitbucket) from the Control Plane, so a prompt-injected Agent can at most submit a bad review, capped to a comment, which the marker attributes to the automation.
- `pr_review_submit` outside a review run is an error; the tool description and the prompt both say so, and `gh` in the box still works for everything else, as before.
- GitHub inline comments need the line to be part of the diff; the fold-back keeps the review from being lost when the Agent's line is off. Bitbucket Data Center's participant status needs the token's user slug (the Connector's login); when the server refuses it the comment stands and the run's detail says so.
- `followed_prs` gains a `body` column (the description the prompt fences), added with `ALTER TABLE` on existing databases.
- Auto QA (ADR-0066, Stage 3) follows the same pattern: a Session on the head, a tool that hands the result to the Control Plane, which publishes.
