# Auto QA: a Session records the PR on the desktop, the Control Plane posts the result and the video

ADR-0044 verifies each turn end to end: the Agent plans cases from the user's request, runs them on the Sandbox desktop while recording, and finishes with an `.mp4` the Auto QA pane plays. The owner wants the same for a pull request that opens or gets new commits, with the video on the PR, and no user turn to verify.

## Decision

**The brief replaces the turn.** `auto_qa` starts a Session on the PR head (the same checkout as ADR-0065: base repository, PR ref for forks, no Connector in a fork's box), opens a verification run on it at once with a **brief** — the PR named, base and head, the owner's setup notes from the action (`instructions`: how to start the app, which account), and the PR's description fenced in `<pr-description>` as the author's claims, not instructions — and sends one prompt that points the Agent at the `e2e-verification` skill's new **pull request mode**: decide from `git diff` against the base, plan 2–5 cases from what the PR claims and shows, bring the app up before `start_recording`, keep the recording under `maxMinutes` (10 by default), **never fix, commit or push** (a failed case is a finding about someone else's PR), never comment on the PR itself. The run is the one the `verify` tool would open (`brief` set), so the turn's end closes whatever the Agent left open, as today. `e2eVerify` is off for the Session so no second run follows.

**The Control Plane reads the run and publishes.** When the turn settles, the `auto_qa` settled hook reads the Session's verification run: verdict (`passed` / `failed` / `skipped` / `aborted`), the last attempt of each case with its note, the summary and the video's Workspace path. The video is copied out of the box before *stop after* takes the box away, to `~/.sessionboxer/qa-videos/{runId}.mp4` (200 MB cap), served at `GET /api/automations/runs/{runId}/video` with Range support, so the Automations and Pull requests pages play it after the Session is gone. Then one comment goes on the PR under the follow's login: `**Sessionboxer Auto QA** · QA 3/4 passed (1 failed) · head sha7 · [Session] · [Automation]`, one line per case with ✅ / ❌ / ⏭️ and the Agent's note, the Agent's summary, and the marker `<!-- sessionboxer:automation= run= head= qa= -->`. On GitHub with `publish: github_attachment` (default) the comment is posted by the **host's** `gh pr comment <url> --body-file - --attach video.mp4` (GitHub CLI 2.99+, the pinned download is 2.101) as the follow's token in `GH_TOKEN`, so GitHub renders a player; when that gh is older, missing, or fails, the comment goes through the REST API with a link to the Sessionboxer video instead and the run's detail says so. Bitbucket Data Center and `publish: link_only` always link. A skipped run (nothing desktop-observable) posts nothing unless `commentOnSkip`.

**The run's result is data, not prose.** `{ type: "qa", passed, total, skipped, videoUrl, commentUrl, e2eRunId }` on the automation run; the Pull requests page badge and the Automations history show it, `automation_pr_state` records the head so the same head is not QA'd twice by one automation, and a push notification goes out when not every case passed. The automation run *succeeds* whenever the QA run reached a verdict — failing cases are the result, not a failure of the automation; it *fails* when the Session ended with the run still open or without one.

## Consequences

- The QA Session has Docker by default (apps need databases); the `forks: review_only` default keeps fork PRs out of Auto QA unless the owner allows them, and a fork's box still gets no Connector.
- The video attachment depends on the host's `gh`; the link fallback always works but needs the Control Plane reachable from where the PR is read (a tunnel, ADR on remote access) — the comment says so.
- The skill file changes (pull request mode), so the Sandbox image must be rebuilt for the Agent to read the new rules; the prompt carries the essential ones in the meantime.
- Recording length is a rule the Agent follows, not a hard cut; the run's time limit (`limits.timeoutMinutes`) is the hard stop.
