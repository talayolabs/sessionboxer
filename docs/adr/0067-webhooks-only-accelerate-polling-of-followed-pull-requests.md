# Webhooks only accelerate the polling of followed pull requests

ADR-0064 follows pull requests by polling, because the Control Plane usually sits behind a laptop's NAT and nothing may depend on inbound requests. When a tunnel with a stable hostname is up (the Sessionboxer tunnel, "Own server over SSH"), a webhook can shave the minute of latency off — and it must not become a second source of truth, a second trust model, or a requirement.

## Decision

**A delivery is a hint, nothing more.** `POST /api/hooks/{provider}/{followId}` sits outside the access-token middleware and is verified with a per-follow secret instead: `X-Hub-Signature-256` (GitHub) or `X-Hub-Signature` (Bitbucket Data Center), `sha256=` + HMAC-SHA-256 of the raw body, compared in constant time; bodies over 1 MB are refused. Once verified, the payload is read only for *which* PRs it is about — `repository.full_name` plus `pull_request.number`, `issue.number` (when the issue is a PR), `check_run` / `check_suite.pull_requests[].number`; Bitbucket `pullRequest.id` and its `toRef.repository` — and those PRs are marked for a detail read now; a PR the follow does not know yet (opened) or a payload without a PR makes the follow's list due now. Nothing from the payload is stored, shown, or turned into an event: events still come from diffing polled snapshots, so a forged or replayed delivery costs one extra poll at most, and a missed delivery costs a minute. `ping` marks the hook seen and answers `202`.

**Registration where the login can, paste-in elsewhere.** `POST /api/prs/follows/:id/hook` (optional body `{ url }`: the public base URL — a tunnel; the Control Plane's own URL by default) generates a secret and, for a GitHub `repo` follow, registers the hook with the follow's login (`POST /repos/{o}/{r}/hooks`, events `pull_request`, `pull_request_review`, `pull_request_review_comment`, `issue_comment`, `check_run`, `check_suite`; needs admin on the repository — the OAuth App's `repo` scope covers it, fine-grained tokens need the Webhooks permission). For Bitbucket Data Center and for `mine` / `requested` follows (their PRs span repositories) the answer carries the URL and the secret for the user to paste into the repository's webhook settings. `DELETE` removes a registered hook and forgets the secret; unfollowing does the same. The secret never leaves the Control Plane except in that one answer for hand configuration.

**Healthy hooks slow the list tier, never stop it.** A follow whose hook delivered in the last hour is `healthy` and its list is polled every 5 minutes instead of every minute (`PrFollow.webhook`: `none` / `registered` / `healthy`, shown on the Pull requests page and in the follow's *Webhook…* dialog). Detail reads still happen on the list's say-so and on the 30-minute refresh.

**One poller per PR for checks.** A PR both followed (ADR-0064) and attached to a live Session (ADR-0027) was having its checks read by two timers. The followed poller now leaves the fast checks tier to the Session-level poller while that Session's box is up, and the Session-level poller tells it (`PullRequests.onChecksChanged` → `FollowedPrs.pollHint`) when checks changed, so `check_failed` events reach automations as fast as before with the requests of one poller. Conditional requests already made the duplicate cheap on GitHub (304s do not count); this removes it altogether and keeps Bitbucket, which has no ETags on builds, at one read.

## Consequences

- The hook URL embeds the follow id; deleting the follow makes deliveries `404`, so a stale hook on the platform is harmless. A rotated tunnel hostname needs the hook re-registered (turn off, turn on with the new URL) — the Cloudflare quick tunnel changes its hostname at every start and is not worth a hook.
- The research document's optional S3/R2 publication of QA videos and a GraphQL list variant stay out: the Control Plane-hosted video with a link (ADR-0066) covers the default, and request counts stay well under the limits with conditional requests and the hook-slowed list tier.
- Bitbucket Data Center's hook signature header and payload shape follow Atlassian's documented `X-Hub-Signature` / `pullRequest.toRef.repository` format; a Bitbucket that signs differently makes the delivery a `401` and the follow simply keeps polling.
