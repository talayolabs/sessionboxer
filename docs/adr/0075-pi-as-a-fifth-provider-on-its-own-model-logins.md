# pi as a fifth Provider, on its own model logins

[pi](https://github.com/earendil-works/pi) (`@earendil-works/pi-coding-agent`, Node 22+) is an open-source coding agent that runs on the user's own model accounts: `/login` in its TUI signs in with Anthropic, OpenAI, GitHub Copilot, OpenRouter, Vercel AI Gateway and others (OAuth or API key, written to `~/.pi/agent/auth.json`), and it reads the usual provider environment variables (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, `AI_GATEWAY_API_KEY`, …). pi has no ACP mode of its own (the maintainers declined one); its RPC mode (`pi --mode rpc`, JSON lines on stdio) is bridged to ACP by [pi-acp](https://github.com/svkozak/pi-acp), the adapter Zed's registry lists. So, as with Codex (ADR-0046) and Cursor (ADR-0054), what Sessionboxer does with an Agent applies; what is specific is the credential (one or several model logins rather than one subscription) and that pi's MCP servers come from its own configuration file, not from the ACP client.

## Decision

**Provider `pi`, label "pi"**, alongside `claude-code`, `devin`, `codex` and `cursor`. The image installs `@earendil-works/pi-coding-agent@PI_VERSION` and `pi-acp@PI_ACP_VERSION` with `npm install -g` (root-owned, on PATH, amd64 and arm64 alike: both are plain JavaScript). The Daemon starts `pi-acp`, which spawns `pi --mode rpc --no-themes` from the Workspace (the session file it resumes with on `session/load` is appended). A `~/.pi/agent/settings.json` in the image sets `defaultProjectTrust: "always"` (pi otherwise asks before loading a project's `.pi/` extensions and `mcp.json`, a question RPC mode cannot answer; the Sandbox is the isolation, as for the other Providers), `quietStartup: true` and `enableInstallTelemetry: false`; the Agent process also gets `PI_SKIP_VERSION_CHECK=1` and `PI_TELEMETRY=0`, so the box makes no call to pi.dev. The Sandbox briefing sits at `~/.pi/agent/AGENTS.md`, pi's user-level instructions file, read for every project.

**The credential is pi's `auth.json`, API keys, or both, pasted once.** Settings → Providers has two fields under `providerSecrets.pi`: `PI_AUTH_JSON`, the JSON object `/login` writes (one entry per model provider: `{ "anthropic": { "type": "oauth", … }, "openai": { "type": "api_key", "key": "…" } }`; `~/.pi/agent/auth.json`, `%USERPROFILE%\.pi\agent\auth.json` on Windows), accepted when it parses as such an object with at least one entry (else a 400 that says what to do) and stored compacted; and `PI_API_KEYS`, `NAME=value` lines (`export NAME=value` and quoted values accepted, blank and `#` lines skipped), one per model provider. Both are write-only: `GET /api/settings` carries `providerSecretsSet.pi.{PI_AUTH_JSON,PI_API_KEYS}` and `piLogin`, the provider ids the file covers and the names of the keys — never a value. A pi Session is refused until one of the two is configured. Sessionboxer's `claudeApi` setting (Claude Code's base URL and key) is not reused: pi's keys stay under `providerSecrets.pi`. The Connect dialog shows no **Sign in with pi**: pi's login lives in its TUI (`/login`) and the CLI has no login command a browser flow could drive, so the Provider is paste-only like Codex before ADR-0058 — with **Use this machine's pi login** when the Control Plane runs where pi is logged in (`readHostLogin` reads `~/.pi/agent/auth.json`, or `$PI_CODING_AGENT_DIR/auth.json`).

**The login travels over the Daemon RPC.** On every connection the Control Plane sends `_sessionboxer/pi/auth/set` `{ authJson, apiKeys }` before the MCP set that starts the Agent. The file goes on tmpfs through the `AuthFile` helper, as Codex's and Cursor's do — `/dev/shm/sessionboxer/pi-auth.json`, mode 0600, `~/.pi/agent/auth.json` a symlink to it, so `docker commit` carries a dangling link and the rest of `~/.pi/agent` (settings, sessions for `session/load`) stays on disk; a file pi rewrites (an OAuth refresh) is moved back onto tmpfs and reported with `_sessionboxer/pi/auth/changed`, and the Control Plane keeps it when it is that Session's own, newer than what it holds (a later `expires`), then pushes it to the other running pi Sessions. The API keys are handed to the Agent process as environment only — never a container environment variable, so not in `docker inspect`, a snapshot or the logs (the Daemon logs the names). pi reads both at start, so the Agent restarts in place when the login arrives or changes (after the turn if one is running; the response says whether it was applied at once); forgetting the login in Settings removes the file and the keys from every running pi box.

**MCP servers reach pi through its own `mcp.json`.** pi-acp stores the `mcpServers` of `session/new`/`session/load` but does not pass them to pi (its README says so, and it advertises `mcpCapabilities: { http: false, sse: false }`). pi 0.99 has MCP built in, read from `~/.pi/agent/mcp.json` (global; a project's `.pi/mcp.json` needs trust) in the Claude-Code-like `{ "mcpServers": { name: { command, args, env } | { url, headers } } }` shape, tools named `mcp__<server>__<tool>`. So, like Devin's `mcp_config.json` (ADR-0007), the Daemon writes that file before each Agent start — the built-in `desktop` and `sessionboxer` servers (through the bridge in a Windows/macOS guest) plus the Session's own stdio and HTTP servers — on tmpfs (`/dev/shm/sessionboxer/pi-mcp.json`, mode 0600, the path in `~/.pi/agent` a symlink), since a server's `env` and `headers` can hold a secret, and restarts pi when the set changes, like the other Providers. Every entry is marked `exposure: "direct"`: pi's default, `codemode`, hides MCP tools behind a JavaScript sandbox and a `tool_search`, and the model must see `desktop` and `sessionboxer` as plain tools. SSE servers are left out with a log line (pi rejects them; most offer streamable HTTP at `/mcp`). pi 0.99.0 is the first release with built-in MCP, which is why the pins (`pi 0.99.2`, published 2026-09-30, and `pi-acp 0.0.34`, 2026-09-24, which adds the thinking-level option and Windows `.cmd` spawning) are younger than the week the project usually waits for; the alternative — the last older pi, 0.87.1 — has no MCP at all, so `desktop` and `sessionboxer` could not reach it.

**Model and thinking from ACP config options.** pi-acp advertises two `select` options per session: the model (category `model`, ids `provider/model-id`, every model of the configured providers) and `thought_level` (pi's `/thinking`: `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, as the model supports); the Daemon maps the first to the model picker and the second to the Agent options, and `session/set_config_option` applies them. Instructions are delivered the way Codex's, Cursor's and Devin's are: prepended to the first prompt of each conversation (pi-acp has no system-prompt hook).

**Usage.** pi-acp sends `usage_update` with `used` and `size` (the context occupancy pi reports after each reply) — the context gauge and the per-turn context delta work. Nothing about usage windows or quotas crosses ACP (pi runs on whichever provider account), so the usage bars are hatched with a pointer to the provider's console, like Devin's and Cursor's; `usage.ts` classifies rate-limit / quota / credit errors in pi's replies as a usage limit so the usual banner appears. pi compacts on its own (`/compact`, `autocompact`) but pi-acp reports no compaction events, so the compaction details stay empty.

**Guests.** pi and pi-acp are Node packages: the Windows base (`images/windows/oem/install.bat`) and the macOS base (`macos.ts` `finish()`, toolchain 2) install the same pins with `npm install -g`, next to codex-acp; the Daemon pushes `settings.json`, `mcp.json`, the briefing (`AGENTS.md`) and `auth.json` into `~/.pi/agent` of the guest before each start and pulls `auth.json` back after each turn, as for Codex and Cursor.

### What pi exposes over ACP (pi-acp 0.0.34 on pi 0.99.2, verified over stdio in the image)

- Protocol version 1; `agentCapabilities.loadSession: true`; `mcpCapabilities: { http: false, sse: false }`; `promptCapabilities: { image: true, audio: false, embeddedContext: false }`; `sessionCapabilities: { list, delete }`.
- One auth method, `pi_terminal_login` (type `terminal`, "Launch pi in the terminal"): not usable in a box; `session/new` without a credential fails with *Authentication required: Configure an API key or log in with an OAuth provider.* and that method in `error.data.authMethods` — a clean refusal, never a hang.
- `session/new`, `session/load` (through pi-acp's `~/.pi/pi-acp/session-map.json`, mapping ACP session ids to pi session files), `session/list`, `session/delete`, `session/prompt` with streamed `agent_message_chunk`, tool calls with diffs, `usage_update { used, size }`, `available_commands_update` (`compact`, `autocompact`, `export`, `session`, `name`, …), `config_option_update`; two config options, `model` and `thought_level`; `stopReason: end_turn`; permission requests when pi asks.

### What it does not expose

- MCP servers from the client (`mcpServers` on `session/new`/`session/load` are ignored) — the Daemon's `mcp.json` is the way in.
- No system-prompt hook (instructions go on the first prompt), no modes, no usage windows or quota, no compaction events, no cost; no `authenticate` that could complete in a box; no SSE MCP servers.
- Inspect LLM stays Claude Code only.

## Considered Options

- **`@frmhd/pi-sdk-acp-adapter`**: smaller and less used; pi-acp has `session/load`, usage updates and the model/thinking options.
- **Patching pi-acp to pass ACP `mcpServers` to pi**: a pinned fork to carry; pi reads `mcp.json` natively and Devin already has the write-the-file pattern.
- **A project `.pi/mcp.json` in the Workspace**: lands in the repositories and needs trust; the global file is read for every project and stays out of git.
- **An older pi with `@earendil-works/pi-mcp` as an extension**: the package only exists from 0.99.0 (built-in MCP), so no age-compliant combination has MCP.
- **Reusing `claudeApi` for pi's Anthropic key**: a Claude Code setting (base URL, proxy); pi's keys are several and belong to the Provider.
- **A browser sign-in**: pi has no login command; `/login` is interactive in its TUI, and the OAuth flows paste a code back into that TUI.

## Consequences

- Needs an image rebuild (about 60 MB) and a reprovision of the Windows and macOS bases for pi there; existing Sandboxes keep working as before (a Daemon that predates this answers "method not found" to the auth push and is logged as such).
- The login is only as private as the Control Plane's settings store and the box's tmpfs: the file and the keys are in memory in the box, never in a layer, a snapshot or `docker inspect`.
- Verified without a model account: `pi-acp` in the image initialises over stdio as listed above and refuses `session/new` with *Authentication required* until a login is present. With a mock OpenAI-compatible server on the host and a `models.json` provider pointing at it (written into the box by hand; the API key as `PI_API_KEYS`): the key reaches the Agent process only (not the container, `docker inspect`, `GET /api/settings` or the logs), `mcp.json` on tmpfs lists `desktop` and `sessionboxer`, a Session of the Provider starts, the model picker lists the mock model and the *Thinking* option, a prompt streams a reply in which the model lists its 70 tools as `mcp__desktop__*` / `mcp__sessionboxer__*`, the context gauge shows pi's occupancy, stop → resume keeps the conversation (`session/load`), delete removes the box. A Claude Code Session still boots to its "needs a login" idle state. Windows and macOS: typecheck and build of the guest code only.
