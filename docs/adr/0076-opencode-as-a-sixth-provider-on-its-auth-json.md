# OpenCode as a sixth Provider, on its auth.json

[OpenCode](https://opencode.ai) (`anomalyco/opencode`, formerly `sst/opencode`) is an open-source coding agent that runs on the user's own model providers — Anthropic (including a Claude Pro/Max login), OpenAI (ChatGPT), Google, OpenCode Zen, OpenRouter and some 75 others through Models.dev — and speaks ACP natively: `opencode acp` is stdio JSON-RPC (protocol version 1) that starts a private OpenCode server for the process and serves sessions on it.

## Decision

**Provider `opencode`, label "OpenCode"**, alongside `claude-code`, `devin`, `codex` and `cursor`. The image downloads the single prebuilt binary of the npm platform package `opencode-ai` depends on (`opencode-linux-x64` / `opencode-linux-arm64`, `OPENCODE_VERSION`, the same bytes `npm i -g opencode-ai@<version>` would unpack) into a root-owned `/opt/opencode` and links `/usr/local/bin/opencode`; the Daemon spawns `opencode acp`. The update check is off twice over: `OPENCODE_DISABLE_AUTOUPDATE=1` in the Agent's environment and `autoupdate: false` in the config file the image ships. The Windows base (`images/windows/oem/install.bat`) and the macOS base (`macos.ts` `finish()`) install the same version from the `opencode-windows-x64` / `opencode-darwin-{x64,arm64}` packages, so the guest transport runs the same `opencode acp` there.

**The credential is OpenCode's `auth.json`, or an OpenCode Zen API key, pasted once.** The user runs `opencode auth login` on their own machine for each model provider they want and pastes or imports the file it writes, `~/.local/share/opencode/auth.json` on every OS (OpenCode uses XDG paths on macOS and Windows too): a JSON object from provider id to a record of `type` `oauth` (`access`, `refresh`, `expires`), `api` (`key`) or `wellknown` (`key`, `token`). A key from opencode.ai/auth pasted alone is stored as the file `{ "opencode": { "type": "api", "key": … } }`. Settings normalises and validates the file (every record complete), shows which providers it covers and of what kind, and never the file. `providerSecrets.opencode.OPENCODE_AUTH_JSON` is write-only, `providerSecretsSet.opencode.OPENCODE_AUTH_JSON` and `opencodeLogin` (provider ids, kinds, OAuth expiries) are the public side.

**The login travels over the Daemon RPC.** On every connection the Control Plane sends `_sessionboxer/opencode/auth/set` before the MCP set that starts the Agent. The file goes on tmpfs the way Codex's and Cursor's do (`AuthFile`): `/dev/shm/sessionboxer/opencode-auth.json`, mode 0600, `~/.local/share/opencode/auth.json` a symlink to it, so `docker commit` (Snapshots) and the image never hold a token, while the rest of `~/.local/share/opencode` — the sessions and storage `session/load` needs — stays on the container disk. OpenCode refreshes OAuth tokens in place and rewrites the file; the Daemon's watcher sends `_sessionboxer/opencode/auth/changed` with the new contents, the Control Plane stores it when it is newer (a later expiry) and hands it to every other OpenCode Session. Forgetting the login in Settings removes the file from every running box. OpenCode's server lists its providers when it starts, so the Daemon restarts the Agent in place when the login arrives or goes (`setAgentEnv`, like Cursor). In the guests the file is copied in before each Agent start and pulled back after it, like Codex's.

**No `Sign in with OpenCode`.** Every OpenCode login is per model provider and either a browser OAuth that calls back to the CLI's local port (Anthropic, OpenAI, OpenCode Console) or an API key typed into an interactive prompt; neither is the paste-a-code shape the browser flow of ADR-0058 drives. `provider-login.ts` has no recipe for it (`RECIPES` is partial now; `hostLogin` says `signIn: false` and the dialog shows the CLI steps directly), while **Use this machine's OpenCode login** still imports the host's `auth.json`. The Daemon never calls ACP `authenticate`: OpenCode's only method, `opencode-login`, means "run `opencode auth login` in the terminal", and OpenCode does not refuse `session/new` without a login anyway (its free Zen models answer, a paid provider's model fails the turn with that provider's error); Sessions of the Provider are refused by the Control Plane until a login is configured, with the hint saying what to paste.

**Instructions, MCP, permissions, modes.** OpenCode has no system-prompt hook over ACP, so the Session's instructions are prepended to the first prompt like Codex's and Cursor's; the Sandbox briefing is `~/.config/opencode/AGENTS.md`, which OpenCode reads as its global instructions (the project's own `AGENTS.md` comes on top). MCP servers go through ACP: OpenCode registers the client's `mcpServers` of `session/new` and `session/load` (stdio, HTTP and SSE) on its server, so the user's servers and the built-in `desktop` and `sessionboxer` ones reach it without a config file. Permissions: the shipped config says `"permission": "allow"`, and the Daemon's standard answer to `session/request_permission` (allow always, else allow once, else reject) covers anything OpenCode still asks. Its ACP config options are `model` (every `provider/model` of the logged-in providers plus the free Zen ones, a flat list named `Provider/Model`, which the generic `ModelOption` capture puts in the composer's model picker and `session/set_config_option` applies) and `mode` (`build`, or `plan`, which disallows its edit tools); the mode stays `build` and is not offered in the picker, the way the Daemon owns the other Providers' permission modes (Cursor is kept in `agent`).

**Usage.** OpenCode sends ACP `usage_update` notifications with per-turn tokens (input, output, cached), which the transcript's usage figures take, but no provider windows: the usage bars are hatched with a pointer to the model provider's dashboard. A refused turn is classified from the provider error OpenCode relays (quota exceeded, insufficient credits, rate limit) without a reset time. Compaction details are not available over ACP (OpenCode compacts inside its own server; the transcript only shows the result).

### What `opencode acp` 1.18.32 advertises over ACP

Recorded from `initialize` and `session/new` of the binary in the image, without a login:

- `protocolVersion: 1`; `agentInfo { name: "OpenCode", version: "1.18.32" }`.
- `agentCapabilities`: `loadSession: true`; `mcpCapabilities { http: true, sse: true }`; `promptCapabilities { embeddedContext: true, image: true }`; `sessionCapabilities { close, fork, list, resume }`.
- `authMethods`: one, `opencode-login` ("Login with opencode": run `opencode auth login` in the terminal). `session/new` succeeds without a login and the free OpenCode Zen models answer; a model of a provider that is not logged in fails the turn with that provider's error.
- `session/new` → `configOptions`: `model` (category `model`, current `opencode/big-pickle` — the free model without a login) and `mode` (`build`, `plan`); no `modes` object (the mode is a config option).
- `session/prompt` → `stopReason: "end_turn"`; `session/update` of kinds `agent_message_chunk`, `tool_call`, `tool_call_update`, `usage_update` (input/output/total/cached tokens).
- Not exposed: usage windows or quotas, compaction details, the OAuth login flows (only the CLI's).

## Considered Options

- **A list of API keys by environment variable (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, …) instead of the file**: OpenCode reads them, but the file is what `opencode auth login` produces, holds the Claude Pro/Max and ChatGPT logins most users have, and refreshes. A key is accepted in the same field (as an OpenCode Zen record).
- **Writing the MCP servers into a per-Session `opencode.json`**: unnecessary, OpenCode takes them from the ACP client; the config file in the image only turns off the update check, sharing and the permission prompts.
- **Running `opencode auth login` from the box**: the OAuth callbacks need the provider's site to reach the CLI's local port; pasting the file is the same effort as for Codex and Cursor.
- **Letting Sessions start without a login**: OpenCode works without one, on the free OpenCode Zen models (`opencode/big-pickle` and the other `-free` models are listed, and answer, with no `auth.json`). Kept the refusal of the other Providers anyway: a Session that silently runs on a third party's free tier instead of the user's own account is a surprise, and the hint says what to paste.
- **`session/load` only**: kept, as OpenCode advertises it and replays the conversation; the Daemon's transcript replay remains the fallback when a load fails.

## Consequences

- Needs an image rebuild (about 120 MB) and, for VMs, a Windows or macOS base reprovision to get `opencode` in the guest; existing Sandboxes keep working as before (a Daemon that predates this answers "method not found" to the auth push and is logged as such).
- The login is only as private as `~/.sessionboxer/config.json`, same as the other tokens; it is never in public settings, events, `docker inspect`, Snapshots or logs.
- Verified without an OpenCode account: the handshake above in the image; the login reaching the box over RPC as a 0600 file on tmpfs behind the symlink and gone again when forgotten; and the full path against a mock OpenAI-compatible endpoint configured as a custom provider — a Session starts, a prompt gets a reply in the transcript, the Agent is offered the `desktop` and `sessionboxer` MCP tools, Stop/Resume keeps the conversation (`session/load`). Not verified: a real model provider, the OAuth refresh round trip, Windows/macOS guests (typecheck and build only).
