# fx as a seventh Provider, on an fx login

[fx](https://fx.sh) is Vercel Labs' coding agent: a single static Zig binary (about 8 MB, Apache-2.0) for Linux and macOS on x86_64 and arm64, with no Windows build. Its ACP server is built in: `fx acp` speaks stdio JSON-RPC with `session/new`, `session/load`, `session/resume`, `session/list`, `session/close`, `session/prompt`, `session/cancel`, `session/set_config_option` and `session/set_mode`, permission requests, config options (provider, model, mode, effort) and MCP servers from the client. It runs on one model provider at a time: Vercel's AI Gateway (an OAuth login from `fx login`, an API key from `fx setup` or `AI_GATEWAY_API_KEY`), a ChatGPT subscription (`fx login codex`) or a Grok subscription (`fx login grok`). This ADR adds it the way ADR-0054 added Cursor; where that ADR made a choice, this one mirrors it.

## Decision

**Provider `fx`, label "fx"**, alongside `claude-code`, `devin`, `codex` and `cursor`. The image downloads the release archive fx's own installer (`fx.sh/setup.sh`) would fetch, `https://releases.fx.sh/<version>/fx-linux-<x86_64|aarch64>.tar.gz`, pinned to **`v0.0.11`** (published 2026-09-21; the version path carries the `v`) by `TARGETARCH`, and checks it against the sha256 observed at pin time, since the release publishes none: `0438a067df1e2b0e2d85f1e018795b7fe5a4b5fafb37f4a590a733917e53943b` (linux-x86_64), `0067d2156ac31956f52bb0b7b69722733d2756a373f47c4456681b1490b458fe` (linux-aarch64); the macOS archives are `8f13c5e6d3d977ea1313fc1ae54d96d42e3c5847bbdc99998b99023b08bf183e` (macos-x86_64) and `b8fe13452673a26ff474dbe79925bdeb5a8582fcb0db89d06502f2e250945a` (macos-aarch64). The binary sits root-owned under `/opt/fx`, linked as `/usr/local/bin/fx`; the Daemon runs it with `FX_AUTO_UPGRADE=0`, so a Sandbox runs the version the image was built with (fx otherwise downloads updates in the background), and the image ships `~/.fx/settings.json` with `auto_upgrade: false` for the terminal.

**The credential is one of fx's login files, or an AI Gateway API key, pasted once.** The user runs `fx login` on their own machine and pastes or imports `~/.fx/auth.json` (a Vercel OAuth session); `fx login codex` writes `~/.fx/chatgpt-auth.json` and `fx login grok` `~/.fx/grok-auth.json`, pasted in the same field, and an AI Gateway API key (vercel.com → AI Gateway → API keys) is accepted too. Settings stores it write-only as `providerSecrets.fx.FX_LOGIN`; the Control Plane validates the paste (an API key's character set, or a JSON object with `access_token` and `refresh_token`), compacts the JSON, and publishes only `providerSecretsSet.fx.FX_LOGIN` and `fxLogin: { kind: "api-key" | "vercel" | "codex" | "grok", expiresAt }`, read from the file's shape (`token_type` marks the Vercel file; `account_id` the subscription ones, told apart by the access token's issuer). `AI_GATEWAY_API_KEY` in the Control Plane's environment overrides the stored login, like the other Providers' keys.

**The login travels over the Daemon RPC, into a volume fx cannot tell from a plain `~/.fx`.** On every connection the Control Plane sends `_sessionboxer/fx/auth/set` before the MCP set that starts the Agent, and again whenever the stored login changes (forgetting it removes the file from running boxes). Codex's and Cursor's files sit on tmpfs behind a symlink; fx refuses that: before it reads a login file it checks, without following symlinks, that `~/.fx` is a directory and the file a regular file with exactly one link and mode 0600 (`session_presence.zig`, "Saved credential storage is unavailable" otherwise), and it rejects a symlinked `settings.json` or `sessions/` too ("Failed to load startup state"). So an fx Sandbox mounts a per-Session named volume (`sbx-fx-<id>`) over `/home/agent/.fx`: Docker populates it from the image (`settings.json`, `AGENTS.md`) on first use, it survives Stop/Resume (the saved sessions `session/load` needs), it is never part of a `docker commit` (Snapshots carry no secret) and it is removed with the Session. The Daemon writes the pasted file there as a regular 0600 file at the path fx reads (`auth.json`, `chatgpt-auth.json` or `grok-auth.json`, the other two removed), deletes the three on shutdown, and a Codex or Grok file gets `FX_PROVIDER=codex|grok` in the Agent's process so it is used without the `settings.json` entry `fx login codex` would have written (a Vercel file leaves the provider to fx: the Gateway, or a custom model connection the user put in `settings.json`); an API key becomes `AI_GATEWAY_API_KEY` in the Agent's process only. Nothing reaches `docker inspect` (the volume name only), the container's environment, a Snapshot, events or logs; at rest the file is in Docker's volume store on the host, root-only, for as long as the Session exists, which is the one place this Provider is less private than Codex and Cursor. fx refreshes the tokens of a login file in place; the Daemon's watcher reports the rewritten file as `_sessionboxer/fx/auth/changed`, the Control Plane stores it when it is a newer login of the same kind and pushes it to every live fx Session.

**Sign in with fx from Settings (ADR-0058) uses the Vercel device flow.** `fx login vercel` with `FX_NO_OPEN_BROWSER=1` prints `Open https://vercel.com/oauth/device?user_code=XXXX-XXXX` and `Code: XXXX-XXXX`, then polls Vercel until the page is confirmed; that fits `provider-login.ts` as Codex's `--device-auth` does (the dialog opens the URL in the user's browser and shows the code; the page prefills it). The stored result is `~/.fx/auth.json` from the scratch home. `fx login codex` and `fx login grok` are not driven: they write other files and are pasted instead.

**MCP, instructions, permissions.** fx takes the client's MCP servers in `session/new`/`session/load` (stdio, HTTP and SSE) and starts them itself — the built-in `desktop` and `sessionboxer` servers and the user's reach it this way, and fx refuses the session when one fails to start (`Required MCP server '…' failed to start`), which is what the others do too. fx also rejects a stdio server whose `command` is not an absolute path ("MCP server command must be an absolute executable path"), so the Daemon resolves a bare command (`sessionboxer-computer-use-mcp`, a user's `npx`) on its own `PATH` before `session/new`; in the macOS VM the built-in servers already run through `/usr/local/bin/node`, a user's stdio server there must name an absolute path. Session instructions are delivered as a system prompt: fx accepts `_meta.fx.systemPrompt` (an array of text content blocks, appended to its own system prompt) in `session/new`, so `instructionsDelivery("fx")` is `system-prompt` and the Daemon sends `{ fx: { systemPrompt: [{ type: "text", text }] } }` instead of claude-agent-acp's `{ systemPrompt: { append } }`. The Sandbox briefing is installed as `~/.fx/AGENTS.md`, fx's user-level instructions file (it also reads the repository's `AGENTS.md`). fx's ACP modes are `ask` (permission mode `ask`) and `code` (`auto`, a model reviews the calls); neither is "approve everything", so the Daemon leaves the mode alone and sets `FX_PERMISSION_MODE=full-access` on the process (fx's `yolo`, which skips its permission gate; the Sandbox is the isolation), and still answers any `session/request_permission` fx sends (`allow_always`, then `allow_once`, then the first option) so a turn never hangs. On macOS the same environment and files travel into the VM through the guest transport (ADR-0061): `~/.fx/AGENTS.md` and the three login paths, pulled back when fx rewrites them.

**Model picker and usage.** `session/new` returns `configOptions` `provider` (gateway/codex/grok), `model` (the Gateway catalog, or the models of the subscription login), `mode` and `effort` (auto/low/medium/high/xhigh); the Daemon captures them as it does for the others, so Model and Effort appear in the composer and in New session. The set depends on the credential: a custom model connection (the mock endpoint used for verification) advertised only `provider`, `model` and `mode`, so the composer then shows the model alone. `provider` and `model` both carry `category: "model"`, and `provider` comes first; the model picker is the option whose id is `model` (the Daemon now prefers that id over the category), while `provider` is not shown: it follows from the pasted login. fx reports the context window as `usage_update` (`used`/`size`, shown as the context bar) but no rate windows, and its model calls do not pass through the box, so the usage bars are hatched with a pointer to the AI Gateway dashboard (`fx credits` in the terminal shows the balance); a refusal mentioning insufficient credits or a usage limit is classified as a limit hit like the others.

**Windows: unavailable.** There is no fx build for Windows, so `providerUnavailableIn("fx", "qemu-windows")` returns the reason; the New session Agent dropdown disables fx with that hint when QEMU · Windows is the environment, and session creation and forks refuse with a 400. The Windows base (`images/windows/oem/install.bat`) is unchanged. The macOS base gets fx in `finish()` (`~/.local/share/fx/<version>/fx`, linked as `~/.local/bin/fx`, `TOOLCHAIN` bumped to 2 so existing bases show "Reprovision").

## Considered Options

- **`AI_GATEWAY_API_KEY` only**: simple and secure, but a key needs the Gateway's dashboard and a prepaid balance; `fx login`'s file is what most users have and the only way to use a ChatGPT or Grok subscription. Both are accepted, as for Cursor.
- **Writing the MCP servers to `~/.fx/mcp.json`**: unnecessary, fx takes them from the client (and under ACP it does not read the profile-level file at all).
- **Switching the ACP mode to `code`**: `code` is fx's `auto` permission mode, where a model reviews the tool calls, not full access; `FX_PERMISSION_MODE=full-access` is the documented override and matches what `permission_mode: "full-access"` in settings.json would do.
- **Running `fx login` from the box**: fx polls Vercel itself, so the ADR-0058 flow in a scratch home works from the Control Plane's machine or a throwaway box; nothing has to call back into the Sandbox.
- **Three separate fields for the three login files**: one field, with the kind read from the file's shape, keeps Settings as simple as Cursor's and still shows which login it holds.

## Consequences

- Needs an image rebuild (about 8 MB more); existing Sandboxes keep working as before (a Daemon that predates this answers "method not found" to the auth push and is logged as such). A macOS base needs Reprovision before it can start Sessions again.
- The login is only as private as `~/.sessionboxer/config.json`, same as the other tokens; it is never in public settings, events, `docker inspect`, Snapshots or logs.
- What fx advertises over ACP (`v0.0.11`, `initialize` with an `AI_GATEWAY_API_KEY` present): protocol version 1; `loadSession: true`; `promptCapabilities` image and embedded context (no audio); `mcpCapabilities` HTTP and SSE (stdio is implied); `sessionCapabilities` list, resume and close; `authMethods: []` (there is no ACP `authenticate`: the login is in the file or the environment). `session/new` returns `configOptions` provider / model / mode / effort and `modes` `ask` (default) and `code`. Without a credential `initialize` fails with "fx needs access to Vercel AI Gateway. Run fx login …, fx setup …, or set AI_GATEWAY_API_KEY": no session can start, which the UI shows as the usual "needs a login" error. fx does not expose usage windows, compaction details or the raw model calls (Inspect LLM stays Claude Code only); `session/load` replays the saved conversation; images in prompts are accepted (5 MiB padded base64 each, 8 MiB per message).
- Verified without an fx account: typecheck and build; `fx acp` in the rebuilt image initialises as above and refuses without a credential (an invalid or fake login file gets the same refusal; a fake `AI_GATEWAY_API_KEY` reaches `session/new` and fails the turn with HTTP 401); the login reaches the box as a 0600 regular file in the `~/.fx` volume (or as the Agent's environment alone), absent from `GET /api/settings`, the events, `docker inspect` and the Snapshot image. A full turn through Sessionboxer against a mock OpenAI-compatible endpoint (an fx custom model connection in the Sandbox's `settings.json`, something the Provider does not set up for users): the Session started on the volume, the model got the briefing and the `desktop` and `sessionboxer` servers' instructions in its system prompt plus fx's `mcp_select_tool`/`mcp_features` tools, the reply streamed into the transcript, Stop then Resume reached `session/load` (the saved conversation came back and a second turn carried the first), Delete removed the container and both volumes. Not verified: a turn on a real Gateway, ChatGPT or Grok login; the Vercel device-flow dialog end to end (the command and its output were checked, not a completed sign-in); a macOS or Windows VM. The web UI was checked in a browser against the running Control Plane: the Settings → Providers fx card with its help popover, the New session Agent dropdown with all seven Providers, the mock Session's transcript, the composer model picker (`mock-1`) and the hatched usage bars with their pointer; Codex, Cursor, pi and OpenCode cards unchanged, no console errors.
