# MCP Apps inline in the transcript, through a transparent per-server MCP tee

[MCP Apps](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) (`io.modelcontextprotocol/ui`, 2026-01-26) is the MCP extension by which a server's tool can carry a view: `tools/list` marks the tool with `_meta.ui.resourceUri` (a `ui://` URI), `resources/read` on that URI returns an HTML document (`text/html;profile=mcp-app`) with `_meta.ui.csp` (the domains it needs) and the host shows it in a sandboxed iframe, speaking JSON-RPC to it over `postMessage`: the view gets the tool's arguments and its full result (`content`, `structuredContent`, `_meta`, `isError`), can call its server's tools and read its resources through the host, ask for a size, fullscreen, to open a link, to say something as the user, or to update the model's context. `talayolabs/plotable` is such a server (its `publish` tool renders `structuredContent` as a chart). This ADR makes Sessionboxer a host, feature C of `docs/research/canvas-and-html-apps-in-the-chat.md` §5.

The Agent (Claude Code, Codex, Cursor, pi, OpenCode, fx) owns the MCP connections; Sessionboxer sees ACP `tool_call` / `tool_call_update` only. In `claude-agent-acp` the `rawOutput` is the SDK's `tool_result` content blocks: `structuredContent` and `_meta` are dropped, `tools/list` (so `_meta.ui.resourceUri`) and `resources/read` never reach us. A second, independent connection from the Daemon to the server would not do either: a stateful stdio server (Plotable keeps its artifacts in its own process) would be two servers, and the view would read the wrong one.

## Decision

**A transparent per-server tee, not a gateway.** `packages/mcp-tee` (`sessionboxer-mcp-tee <name>`, on `@modelcontextprotocol/sdk`) is what the Agent is pointed at in place of each activated user MCP server: stdio towards the Agent, stdio, HTTP or SSE towards the real server, whose command, args, env, URL and headers stay in the tee's process (the Daemon hands them over on a loopback WebSocket at `ws://127.0.0.1:<daemon port>/mcp-tee/<name>`, accepted from loopback only; the Agent's `mcp.json` / ACP MCP list names only the tee and the server's name). Every JSON-RPC message is forwarded unchanged in both directions — no tool is renamed, no schema altered, no tool added, consistent with `docs/research/runtime-debugging-utilities.md` §3 and unlike a merged gateway, where names would have to be prefixed. The one edit is on the Agent's `initialize` request: `capabilities.extensions["io.modelcontextprotocol/ui"] = {}` is merged in so servers answer with their app metadata. Built-in servers (`desktop`, `sessionboxer`) stay direct: they have no views and are ours. Windows and macOS guests keep the direct configuration they had (the tee is a Linux Sandbox process; the guest bridge is unchanged), so there is no inline view in those Sessions yet.

**The Daemon keeps a mirror of what went through.** The tee copies to the Daemon, as it goes, the `initialize` result, `tools/list` results (tool definitions with `_meta.ui`), every `tools/call` request and its complete result, `resources/read` results and `notifications/*/list_changed`. The Daemon's `McpTeeHub` keeps per server: the tool list, the `ui://` resources (read through the tee on first need, cached by server and URI, a sha256 of each logged) and the exact results of the Agent's calls. An exact result is matched to its ACP `tool_call` by server, tool name, arguments and time window — Claude's `_meta.claudeCode.mcpServer.name` and `toolName` `mcp__<server>__<tool>` are used when present, never required — and feeds `tool-telemetry.ts` as the call's `mcp_execution`, so telemetry reports the real `isError` and `structuredContent` rather than the content blocks ACP kept. A call to a tool with a view raises an `mcp_app_call` Session event (`toolCallId`, server, tool, arguments, `resourceUri`) the transcript renders on.

**The view's own calls ride the same connection.** The Daemon sends the tee `tools/call`, `resources/read` and `tools/list` of its own, with ids in its own namespace (`sbx-tee:<n>`) so they never collide with the Agent's; the tee routes their responses back to the Daemon only. Daemon RPC `mcpApps/resource` (server, uri → html, `_meta.ui`, sha256), `mcpApps/toolResult` (toolCallId → the exact result and the tool definition), `mcpApps/callTool` and `mcpApps/readResource` (both bound to a `toolCallId`: a view reaches its own server only, cross-server calls are refused, and a tool whose `visibility` excludes `"app"` is not callable from a view) and `mcpApps/tools/list`; the Control Plane proxies them under `/api/sessions/:id/mcp-apps/*` with the normal authentication and error mapping.

**The view runs in the spec's sandbox proxy, on an opaque origin.** `apps/web/src/McpAppCard.tsx`, rendered by `Transcript.tsx`'s `ToolCall` when the call has a view (the `<pre>` fallback stays for every other tool), never puts the HTML in the React DOM nor on the Sessionboxer origin: it mounts an `<iframe sandbox="allow-scripts" srcdoc>` (no `allow-same-origin`, so an opaque origin) whose document is our sandbox proxy (`mcp-app-sandbox.ts`). The proxy says `ui/notifications/sandbox-proxy-ready`; the card answers `ui/notifications/sandbox-resource-ready` with the HTML and the CSP; the proxy creates the inner view iframe (`srcdoc`, opaque too, `sandbox="allow-scripts allow-forms"`) with `<meta http-equiv="Content-Security-Policy">` built by the spec's construction from `_meta.ui.csp` ahead of the view's HTML — `default-src 'none'`, `script-src`/`style-src 'self' 'unsafe-inline'` plus `resourceDomains`, `connect-src 'self'` plus `connectDomains`, `img-src`/`media-src 'self' data:`, `frame-src 'none'` unless `frameDomains`, `base-uri 'self'` unless `baseUriDomains`, `object-src 'none'`; on an opaque origin `'self'` matches nothing, so a view with no domains has no network at all and `window.origin` is `"null"` — and relays every other message. Both sides verify messages by `event.source` (the proxy's `contentWindow`, the parent window, the inner frame's `contentWindow`), not by origin, which is `null` throughout. A second loopback origin serving the proxy with real CSP headers (the spec's reference host) is not done: the `srcdoc` route needs no extra port and works behind the tunnel and the desktop app alike; the `<meta>` policy is as binding as a header for a document that has no other way to be reached. The card speaks the host side of the protocol: `ui/initialize` answers with `serverTools`, `serverResources`, `openLinks`, `logging`, `message` and `updateModelContext` capabilities, the theme (Sessionboxer's variables mapped to the spec's `--color-*` / `--font-*` names, re-sent as `ui/notifications/host-context-changed` on a theme change), the display mode and container size; after `ui/notifications/initialized` the view gets `ui/notifications/tool-input` and, once the Daemon has it, `ui/notifications/tool-result` with the exact result (`tool-cancelled` when the call failed without one); `ui/notifications/size-changed` sets the height up to 900 px in a wrapper the user can also drag, with a Fullscreen button and `ui/request-display-mode`; `tools/call` and `resources/read` go to `/api/sessions/:id/mcp-apps/*`; `ui/message` stages the text in the card with a button that puts it in the Composer (nothing is sent on the view's say-so); `ui/open-link` shows the URL with a button that opens it in a new tab; `ui/update-model-context` is kept per card and shown on request; `ui/resource-teardown` is sent when the card unmounts.

**External domains are approved once per server.** A view whose `_meta.ui.csp` names `connectDomains`, `resourceDomains`, `frameDomains` or `baseUriDomains` runs under the restrictive policy (no domains) until the user allows them: the card says which domains the server's view wants and why it is restricted; **Allow** stores the lists as `appDomains` on the server's registry entry (`McpServerDef.appDomains`, `POST /api/mcp-apps/approve`, the global registry — per-Session copies carry the entry over as they do everything else on it), and the view is remounted with the approved policy. A server that is not in the registry (a Utility's MCP facet) cannot be approved and stays restricted. `appDomains` is not part of what the Daemon or the tee get (`McpServerSpec`), it is a host-side decision.

## Consequences

- A user MCP server is one more process in the Sandbox (the tee), and a Daemon that is not up means the server does not start — the tee waits for its spec. The Agent sees the same server, tools and schemas it did; what the model sees changes only in that servers now also return app metadata (`_meta.ui`), which Claude ignores.
- Telemetry on MCP tools becomes exact (`mcp_execution` carries the server's `isError` and `structuredContent`), for every Provider, not only where ACP relays them.
- The mirror is in memory, per Daemon: a resource is read again after a Sandbox restart (the cache is a cache), and the result of a call made before a restart is gone, so an old card shows the view without its result.
- `srcdoc` means no HTTP CSP header and no `allow-same-origin`: a view that needs a real origin (service workers, `localStorage`, cookies) will not work; none of the spec's examples does. A view that needs an external domain is restricted until approved.
- Guests (Windows/macOS) and views: not yet. The tee would have to run on the guest or the Daemon would need the guest bridge to carry the tee's loopback socket; both are later work.
