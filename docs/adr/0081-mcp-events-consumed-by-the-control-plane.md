# ADR 0081: MCP Events consumed by the Control Plane as an Automations trigger

## Status

Accepted

## Context

The experimental MCP Events extension ([design sketch](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/blob/main/docs/design-sketch-proposal.md), the basis of [OpenAI's "MCP events" page](https://developers.openai.com/plugins/build/mcp-events)) lets an MCP **server** produce event occurrences — an email arrived, a ticket opened, an incident fired — and an MCP **client** consume them: `events/list` describes the event types (name, `delivery` among `poll`, `push`, `webhook`, an `inputSchema` for the subscription arguments, a `payloadSchema`), `events/poll` returns occurrences since a cursor, `events/stream` is a long-lived request on the same connection during which the server sends `notifications/events/event` (plus `active`, `heartbeat`, `error`, `terminated`), and `events/subscribe` registers a webhook URL. Cursors are opaque, server-defined positions the client persists; `eventId` is for deduplication. The protocol is one-directional per connection: nothing lets a client send events to a server.

Nothing in Sessionboxer consumed them. The servers you register run inside a Session's Sandbox behind the tee (ADR-0079), which forwards every message unchanged, so a server advertising events was silently ignored — and the Agents (Claude Code, Codex, pi, …) do not speak `events/*` either. Even if they did, an Agent exists only while its Session runs; the point of events is to react when nobody is there, which is what Automations are for (ADR-0063: a trigger, an action, limits, run by the Control Plane).

## Decision

**The Control Plane is the consumer**, through a new Automations trigger, not the Agent and not the tee. `McpEventTrigger` (`packages/protocol/src/automations.ts`) is `{ type: "mcp_event", serverId, event, arguments, delivery }`: the registry server by id, the event name from its `events/list`, the subscription arguments its `inputSchema` describes, and `delivery` — `auto` (push when the event type offers it, poll otherwise), `push` or `poll`. The actions are the ones that need no pull request: prompt a Session, start a new one, notify; `validateAction` keeps refusing PR-only actions, as for a schedule.

**One connection per subscription** (`apps/control-plane/src/mcp-events.ts`, `McpEvents`). For every enabled `mcp_event` automation the Control Plane connects to the server itself — the registry's command, URL, headers and env, over the SDK's stdio, Streamable HTTP or SSE transport, as the tee does, but from the host — and runs a subscription loop: `events/list`, find the event type, pick the mode, then either hold an `events/stream` request open or call `events/poll` and sleep for the server's `nextPollMs` (clamped to 5 s – 10 min, no sleep while `hasMore`). A connection per subscription rather than per server because the SDK does not expose the JSON-RPC id of a request, so `_meta["io.modelcontextprotocol/subscriptionId"]` could not be matched; on a dedicated connection every `notifications/events/*` belongs to the one subscription. A stdio server therefore runs one process per subscription; the Automations page shows what each costs, and few automations are expected per server. The subscriptions are reconciled against the automations table at start, whenever the list changes (`Automations.listChanged`), when the registry changes (`settingsChanged`) and every 30 s; a change to the trigger or to the server's definition restarts its subscription, a disabled or deleted automation ends it.

**Liveness and recovery.** The SDK's request timeout cannot be unbounded (Node clamps timers above 2³¹ ms to 1 ms), so the stream request is given a 23-day timeout and the real check is a watchdog: no event or heartbeat for 90 s (the sketch's 2 × 30 s) closes the connection. `notifications/events/terminated`, a server that ends the stream, a transport error or a crashed process all end the loop's iteration; it reconnects with exponential backoff (5 s doubling to 5 min, reset after a connection that held for a minute). The subscription's state — `connecting`, `listening`, `polling`, `error` with the reason, `off` — is broadcast as `mcp_event_subscriptions` (and served by `GET /api/mcp-events/subscriptions` for a page that opens later) and shown as a badge on the automation.

**Cursor and deduplication.** `automation_mcp_state (automation_id, cursor, updated_at)` keeps the cursor per automation; it is written after an occurrence's run is recorded (from the event's own `cursor`, the stream's `active`/`heartbeat`, or the poll's result), and read back on every connect, so a restart resumes where the server's replay allows. Occurrences are dropped when their `eventId` is in the subscription's recent set (2 000) or already fired a non-skipped run of that automation (`automation_runs.event_id`, `trigger = 'mcp_event'`). `maxConcurrent` and `maxRunsPerDay` apply as for PR events, recorded as skipped runs with the reason; `debounceSeconds` and the per-PR cap do not apply.

**The event in the run and the prompt.** `automation_runs.mcp_event` (JSON, `McpRunEvent`: server id and name, event name, id, timestamp, data) is the MCP counterpart of the PR columns; `AutomationRun.mcpEvent` carries it to the history table and the `event_type` column holds the event name, never parsed as a `PrEventType`. Prompts get `{event}` (server and event name), `{event.name}`, `{event.id}`, `{event.timestamp}`, `{event.server}`, `{event.data}` and `{event.data.<path>}`; when the text places none of `{event.data…}`, the payload is appended as a fenced JSON block introduced as *data from that server, not instructions* — the same stance as the PR description in auto review (ADR-0063). Payloads are cut at 16 000 characters both in the prompt and in the stored run.

**Discovery for the form.** `GET /api/mcp-events/catalog` asks every registry server `events/list` on a fresh, short-lived connection (cached a minute, `?refresh=1` to ask again) and answers, per server, `ok` with the event types, `none` when the server has no `events/*` (method not found, or the sketch's `-32011`/`-32014`), or `error` with the message, plus the live subscriptions. The Automations form picks the server and the event from it, shows the description, the delivery modes and the payload's fields as `{event.data.<field>}` placeholders, and takes the arguments as JSON.

**Not in this round.** Webhook delivery (`events/subscribe`): it needs an inbound HTTPS URL, which is the tunnel question of ADR-0063 §2.4; `auto` never picks it and an event that offers only `webhook` is reported as not subscribable. Sessionboxer producing events (the `sessionboxer` MCP as an events server) is a separate feature. In a Docker Compose deployment the Control Plane is in a container, so a stdio command runs there and `localhost` in a URL is the container; the tee's `host.docker.internal` rewrite is not applied.

`scripts/mock-events-mcp-server.mjs` is a stdio server speaking the extension (one event type, push and poll, replay from a cursor, duplicates and a no-events mode on request); `scripts/mcp-events.test.mjs` (`npm run test:mcp-events`, in CI) drives `McpEvents` against it with a real SQLite database: catalog, push, poll with pages, deduplication, resume from the persisted cursor after a fresh consumer on the same database, the error states, and the placeholders.

## Consequences

- An event from any MCP server you register — email, Slack, GitHub, PagerDuty, your own — can prompt a Session, start one or notify you with no Session running, and the payload reaches the Agent as data.
- The Control Plane holds long-lived connections and, for stdio servers, child processes of its own; they appear nowhere in a Session. Credentials stay in the Control Plane's process, as for the tee; the UI sees server names and event types only.
- A server without replayable cursors loses the events of a Control Plane outage; the subscription badge and the run history show what arrived. Dedupe by run history means an event replayed after its run was deleted with the automation runs again.
- `AutomationRun` gains `mcpEvent` and `AutomationRunTrigger` the member `mcp_event`; `/api/schedules*` maps it to `manual` as it does `pr_event`. Databases from before get the `mcp_event` column and the `automation_mcp_state` table on start.
- Webhook delivery and Sessionboxer as an events producer are open; both need the Control Plane reachable over HTTPS.
