# GitHub Copilot CLI as a Provider, on a Copilot login

[GitHub Copilot CLI](https://docs.github.com/copilot/how-tos/use-copilot-agents/use-copilot-cli) is GitHub's agentic CLI: proprietary, shipped as the npm package `@github/copilot` (a launcher that execs the binary of its platform package, `@github/copilot-<linux|darwin|win32>-<x64|arm64>`, a Node single-executable application) and usable on a Copilot plan with the CLI enabled (Free, Pro, Pro+, Business, Enterprise). Its ACP server is built in: `copilot --acp` speaks stdio JSON-RPC with `session/new`, `session/load`, `session/list`, `session/close`, `session/prompt`, `session/cancel`, `session/set_config_option` and `session/set_mode`, permission requests, config options and HTTP/SSE MCP servers from the client. It talks to GitHub's Copilot API with a GitHub token; the models are Copilot's, metered server-side as premium requests. This ADR adds it the way ADR-0077 added fx; where that ADR made a choice, this one mirrors it unless Copilot forces otherwise.

## Decision

**Provider `copilot`, label "GitHub Copilot"**, alongside `claude-code`, `devin`, `codex`, `cursor`, `pi`, `opencode` and `fx`. The image fetches the two npm tarballs from the registry by exact version, **`1.0.91`**, and checks them against the sha256 observed at pin time (the registry's own integrity field, so a changed tarball fails the build): `4f305d718a1e6cb994e926d0f570883eb63bfb79ef091d00d5ff9c67d9d83781` (`@github/copilot`), `11d1dcd5a30d59b270b201e6eeea78fc8b89a59fa2f7da31fd62b35bdd708104` (`copilot-linux-x64`), `fbc585b4653505e0af63a2ca95a6d6e370b404b46c92f277bba8d66bc01f4829` (`copilot-linux-arm64`); for the record the other platform packages are `9f892eb8d5d39c7a59173c8037b3edcd6660832db735baf4c97ded2a1e5274b6` (darwin-x64), `fd5bddc8756e549e47c04a2f9082c50d04727e9dcdcc02ded8936e6e3d1bace0` (darwin-arm64), `cc6d4611ace50bdc496ab368058364fde1ac3f7435082c955aa99dc103a5a996` (win32-x64) and `95a51ed76ed299c8b1c78b2e8a0b84252a402dae6749cddd1f483afb6b48e93a` (win32-arm64). They are installed root-owned under `/opt/copilot` with `npm install` (one runtime dependency, `detect-libc`) and linked as `/usr/local/bin/copilot`. On first start the binary unpacks its application files (185 MB) into `~/.cache/copilot`; the build does that once into `/opt/copilot/dist` and `COPILOT_CLI_DIST_DIR` points every launch at it, so a Sandbox neither unpacks nor downloads anything. The Daemon runs it with `--no-auto-update` and `COPILOT_AUTO_UPDATE=false`, so a Sandbox runs the version the image was built with. The image grows by 182 MB (1,823,638,377 → 2,005,677,686 bytes; `/opt/copilot` is 356 MB uncompressed, most of it the binary and the unpacked application).

**The credential is a GitHub token, or Copilot's own login file, pasted once.** Copilot takes its token from `COPILOT_GITHUB_TOKEN`, then `GH_TOKEN`, then `GITHUB_TOKEN`, then `~/.copilot/config.json` (what `copilot login` writes when `~/.copilot/settings.json` has `storeTokenPlaintext: true`; otherwise the token goes to the OS keychain, which a container has not). A fine-grained personal access token with the **Copilot Requests** permission works, as does the OAuth token of the Copilot CLI or GitHub CLI app (`gho_…`, `ghu_…`); a classic `ghp_` token is refused by Copilot itself. Settings stores the paste write-only as `providerSecrets.copilot.COPILOT_LOGIN`; the Control Plane validates it (a token's character set, or a JSON object of `config.json`'s shape — `authTokens` keyed `<host>:<login>[:github]`, `lastLoggedInUser`, `loggedInUsers`, after Copilot's `//` comment lines are dropped), compacts the JSON, and publishes only `providerSecretsSet.copilot.COPILOT_LOGIN` and `copilotLogin: { kind: "token" | "config", tokenKind: "pat" | "oauth" | "other", login }`, the login being the GitHub user the file names (a bare token names none; nothing is verified against GitHub). `COPILOT_GITHUB_TOKEN` in the Control Plane's environment overrides the stored login, like `AI_GATEWAY_API_KEY` does for fx.

**The token of Sessionboxer's GitHub connector (ADR-0014) does not drive Copilot.** Tried: with that OAuth token as `COPILOT_GITHUB_TOKEN`, Copilot reaches the API and is turned away with `401 "checking third-party user token: unauthorized: Personal Access Token does not have "Copilot Requests" permission`. The connector's OAuth app is not Copilot's and its scopes cannot include that permission, so the connector is not offered as a Copilot login and the GUIDE says so; a user who has `gh auth login` on their machine can still paste that token if their org allows it.

**The login travels over the Daemon RPC: the token into the Agent's environment, the file onto tmpfs.** On every connection the Control Plane sends `_sessionboxer/copilot/auth/set` before the MCP set that starts the Agent, and again whenever the stored login changes (forgetting it empties both). The Daemon resolves the stored login to its token (the string itself, or the `lastLoggedInUser`'s entry of the file) and puts it in the Agent process as `COPILOT_GITHUB_TOKEN` only, which Copilot reads before any file: nothing reaches `docker inspect`, the container's environment, a Snapshot (`PROVIDER_ENV_KEYS` strips it from `docker commit` anyway), events or logs. A pasted `config.json` is also kept on tmpfs behind a symlink at `~/.copilot/config.json` (`AuthFile`, as for Codex and Cursor), so `copilot` in the Terminal is signed in too. Copilot rewrites that file as a regular file on every start (it adds `firstLaunchAt` and its two comment lines); the watcher moves it back onto tmpfs within half a second, and with the token in the environment the rewritten file holds no token at all (`authTokens: {}`), so nothing lands on the container disk. A rewritten file that does hold a login (a `copilot login` done in the Terminal) is reported as `_sessionboxer/copilot/auth/changed`; the Control Plane stores it when the stored login is a file or absent — a stored bare token is never replaced by the mirror the box made of it — and pushes it to every live Copilot Session. Copilot's OAuth tokens do not expire on a schedule, so there is no refresh to follow; the watcher is there for the Terminal case. A bare token leaves no file on tmpfs and no watcher: a `copilot login` in the Terminal then writes `~/.copilot/config.json` to the container disk and is not reported (accepted; the Snapshot strips nothing there, so the GUIDE tells users to sign in from Settings instead).

**Sign in with GitHub Copilot from Settings (ADR-0058) uses GitHub's device flow.** `copilot login --device-code` prints `To authenticate, visit https://github.com/login/device and enter code XXXX-XXXX` and `Waiting for authorization...`, then polls GitHub until the page is confirmed; that fits `provider-login.ts` as Codex's `--device-auth` does (the dialog opens the URL and shows the code; the page asks for it). The scratch home is seeded with `settings.json` `{ "storeTokenPlaintext": true }` so the token lands in `config.json` rather than a keychain, and the stored result is that file, compacted. `copilot login` without the flag tries the browser flow with a local callback first, which the Control Plane's machine cannot complete from a pty; `--device-code` is explicit.

**MCP, instructions, permissions.** Copilot advertises `mcpCapabilities` HTTP and SSE only and refuses a stdio server from the client (`Rejecting non-http/sse MCP server "<name>" from client`, logged, the session continues without it), while the built-in `desktop` and `sessionboxer` servers are stdio. So the Daemon writes the whole set — the built-ins and the user's servers, stdio ones with `type: "local"`, HTTP ones with `type: "http"`, every tool allowed (`tools: ["*"]`) — to `~/.copilot/mcp-config.json` before each spawn, on tmpfs behind a symlink like Devin's and pi's files (a user's MCP headers hold tokens), and sends no `mcpServers` in `session/new`; bare commands (`sessionboxer-computer-use-mcp`, a user's `npx`) are resolved to absolute paths on the Daemon's own `PATH` first, as for fx. Copilot exposes the tools as `<server>-<tool>` (`desktop-screenshot`, …) and loads them when the session is created, so a change to the user's servers takes effect at the next Agent start, as for pi. Session instructions are delivered on the first prompt (`instructionsDelivery("copilot")` is `first-prompt`): Copilot's `session/new` takes no system prompt (no `_meta` hook was found). The Sandbox briefing is installed as `~/.copilot/copilot-instructions.md`, Copilot's user-level instructions file, which reaches the model inside `<custom_instruction>` in the system prompt; Copilot also reads the repository's `.github/copilot-instructions.md` and `AGENTS.md`. Permissions: the Daemon passes `--allow-all` (tools, paths and URLs) and `--no-ask-user` (no `ask_user` tool, so a turn never waits for an answer that cannot come) and sets `COPILOT_ALLOW_ALL=true`, which also trusts the Workspace (its `.github` skills, agents and hooks load); `session/new` then returns the `allow_all` config option as `on`, and the Daemon still answers any `session/request_permission` (`allow_always`, then `allow_once`, then the first option). Copilot's ACP modes are `agent`, `plan` and `autopilot` (its own `mode` config option); none of them is a permission mode, so the Daemon leaves the mode alone. On macOS and Windows the same environment and files travel into the VM through the guest transport (ADR-0061): `settings.json`, `mcp-config.json`, the briefing as `copilot-instructions.md`, and `config.json`, pulled back when Copilot rewrites it.

**Model picker and usage.** The Daemon captures whatever `configOptions` `session/new` returns. Against the mock endpoint used for verification they were `mode` (agent/plan/autopilot) and `allow_all`, no `model`: with `COPILOT_MODEL` set Copilot has one model. Whether a real login makes it advertise its model list (`/model` in the TUI: Claude, GPT and Gemini models of the plan) as a `model` config option is not verified; if it does, the composer shows it like the others. Copilot's prompt response carries the standard ACP usage (`inputTokens`, `outputTokens`, `totalTokens`, `thoughtTokens`, `cachedReadTokens`, `cachedWriteTokens`), and it reports the context window as `usage_update` (`used`/`size`, the context bar) plus `session_info_update` with a title it chooses, but no rate windows: premium requests are counted on GitHub's side, so the usage bars are hatched with a pointer to github.com → Settings → Copilot → Usage (the Usage card says so for Copilot). A refusal naming the premium-request budget or a rate limit is classified as a limit hit like the others (the wording is a guess until seen on a real account).

**Linux, macOS and Windows.** Copilot ships for all three (Node single executables), so `providerUnavailableIn` disables nothing. The macOS base gets `npm install -g @github/copilot@1.0.91` in `finish()` (`TOOLCHAIN` bumped to 3, so existing bases show "Reprovision"), the Windows base the same in `images/windows/oem/install.bat`; both run `copilot --version` once so the application files are unpacked at install time, not at the first Session.

## Considered Options

- **Token only (no login file)**: simplest and the token never leaves the Agent's environment; but most users have `copilot login`, not a fine-grained PAT (which needs a trip to Developer settings and an org policy that allows it), so the file is accepted too and the device flow writes one, as for Cursor and fx.
- **A per-Session volume over `~/.copilot` like fx**: not needed — Copilot follows the symlink and the token in the environment keeps the file free of secrets; the volume would have carried `session-state/` (the saved conversations `session/load` needs), which here stays on the container disk like Codex's and Cursor's.
- **Writing the token into `config.json` only, no environment**: Copilot reads the file, but a Snapshot taken between a Copilot rewrite and the watcher's relink could carry it; the environment is the primary route and the file a convenience for the Terminal.
- **`session/new` `mcpServers`**: refused for stdio servers; `--additional-mcp-config <json>` on the command line would show user tokens in `ps` and `docker inspect`, so the file it is.
- **The GitHub connector's token**: lacks the Copilot Requests permission (above).
- **`copilot login` (browser flow) from the pty**: opens a browser and waits on a localhost callback the Control Plane cannot complete; `--device-code` is the flow ADR-0058 needs.

## Consequences

- Needs an image rebuild (182 MB more); existing Sandboxes keep working as before (a Daemon that predates this answers "method not found" to the auth push and is logged as such). A macOS base needs Reprovision before it can start Sessions again; a Windows base needs a reinstall for `copilot` to be on its PATH.
- The login is only as private as `~/.sessionboxer/config.json`, same as the other tokens; it is never in public settings, events, `docker inspect`, Snapshots or logs.
- What Copilot advertises over ACP (`1.0.91`, `initialize` in the image): protocol version 1; `loadSession: true`; `promptCapabilities` image and embedded context (no audio); `mcpCapabilities` HTTP and SSE (no stdio); `sessionCapabilities` list and close; `authMethods: [{ id: "copilot-login", name: "Log in with Copilot CLI" }]` with a `terminal-auth` `_meta` naming the binary and `login` (ADR-0058's flow stands in for it). `session/new` returns `configOptions` `mode` and `allow_all` and `modes` agent (default) / plan / autopilot, and the session sends `available_commands_update` (Copilot's slash commands) and `config_option_update` on start. Without a credential `initialize` succeeds and `session/new` fails with `-32000 "Authentication required"`; an invalid token (`COPILOT_GITHUB_TOKEN=github_pat_fake…`, network on) gets the same `session/new` refusal, which the UI shows as the usual "needs a login" error. Copilot reads `COPILOT_PROVIDER_BASE_URL` and `COPILOT_MODEL` for an OpenAI-compatible endpoint (BYOK), which bypasses the credential gate; the Provider does not set them up for users, verification did.
- Verified without a Copilot account: typecheck, lint, build, size budget, dup and the test suites; `copilot --acp` in the rebuilt image initialises as above and refuses `session/new` without a credential and with a fake one; `copilot --version` prints `1.0.91` from `/opt/copilot/dist` without touching `~/.cache`. In the image, by hand, with a mock OpenAI-compatible server and `COPILOT_PROVIDER_BASE_URL`/`COPILOT_MODEL`: `session/new` succeeded, a stdio MCP server written to `~/.copilot/mcp-config.json` showed up in the model's tool list as `<server>-<tool>`, the briefing from `~/.copilot/copilot-instructions.md` was in the system prompt, the reply streamed as `agent_message_chunk` and the turn ended with `end_turn` and the usage above; Copilot replaced the symlinked `config.json` with a regular file holding no token (the watcher's relink case). `copilot login --device-code` prints the URL and code the recipe parses (the command and its output were checked, not a completed sign-in). The connector token's 401 above. A full turn through Sessionboxer against the same mock (a wrapper in the box's `~/.local/bin` setting the two variables, something the Provider does not set up for users): the Session reached `idle`, the reply streamed into the transcript, the model got the briefing and the `desktop-*` / `sessionboxer-*` tools, Stop then Resume reached `session/load` (the first turn stayed in the transcript and the second request carried it), the composer showed the `allow_all` option and no model picker, the usage bars were hatched with the premium-request note, Delete removed the container. The web UI was checked in a browser against the running Control Plane: the Settings → Providers GitHub Copilot card with its help popover, an invalid paste refused with its message, a fake token accepted and shown as `fine-grained GitHub token`, Forget, the Connect dialog and Sign in with GitHub Copilot reaching github.com/login/device with a code (cancelled there), the New session Agent dropdown with GitHub Copilot, a fake-token Session showing `Authentication required`; Codex, Cursor, pi, OpenCode, fx and Kimi cards unchanged, no console errors. Not verified: a turn on a real Copilot login (and so the model list, premium-request counting and limit messages); the device flow completed to a stored login; a macOS or Windows VM (typecheck and build of the guest code only; the Agent dropdown on those environments could not be opened on a host without the runtimes).
