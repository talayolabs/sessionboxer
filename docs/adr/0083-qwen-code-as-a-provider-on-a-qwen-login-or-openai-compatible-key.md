# Qwen Code as an eighth Provider, on a Qwen login or an OpenAI-compatible key

[Qwen Code](https://github.com/QwenLM/qwen-code) is Alibaba's open-source coding agent (Apache-2.0): a fork of Gemini CLI, Node.js, published as npm `@qwen-code/qwen-code`. Its ACP server is built in: `qwen --acp` speaks stdio JSON-RPC, protocol version 1, with `session/new`, `session/load`, `session/list`, `session/resume`, `session/prompt`, `session/set_mode`, `session/set_config_option` and `authenticate`; it advertises `loadSession`, image/audio/embedded-context prompts and HTTP/SSE MCP servers. It runs on two kinds of credential: a **Qwen OAuth** login (a free qwen.ai account, obtained with a device flow — URL plus code — that writes `~/.qwen/oauth_creds.json`), or **any OpenAI-compatible endpoint** given as `OPENAI_API_KEY`, `OPENAI_MODEL` and `OPENAI_BASE_URL` (DashScope, ModelScope, OpenRouter, a local server). It reads its instructions from `QWEN.md`, keeps its settings in `~/.qwen/settings.json`, and is on Linux, macOS and Windows alike.

## Decision

**Provider `qwen`, label "Qwen Code"**, alongside the seven of ADR-0077. The image installs the npm tarball `https://registry.npmjs.org/@qwen-code/qwen-code/-/qwen-code-<version>.tgz` pinned to **`0.24.7`** (the version the ACP registry pins), checked against its sha256 (`64430248…5fa9`, one tarball for every architecture: it is JavaScript) before `npm install -g` as root, so `qwen` is on `PATH` and a Sandbox cannot update it in place; the image's `~/.qwen/settings.json` turns its update check and usage statistics off. The macOS base installs the same version with `npm install -g` in `macos.ts` `finish()` (`TOOLCHAIN` bumped) and the Windows base in `install.bat`; there is no `providerUnavailableIn()` rule. `--experimental-skills`, which the registry entry passes, is not passed: 0.24.7 marks the flag deprecated and ignored (skills are on by default).

**The credential is Qwen Code's `oauth_creds.json`, pasted once, and/or `NAME=value` lines for an OpenAI-compatible endpoint**, two fields on the Providers card as pi has (ADR-0075). The user runs `qwen`, `/auth` → Qwen OAuth on their own machine (the device flow opens the browser on chat.qwen.ai) and pastes or imports `~/.qwen/oauth_creds.json`; it is stored compacted under `providerSecrets.qwen.QWEN_OAUTH_JSON`, write-only. Settings sees `providerSecretsSet.qwen` and `qwenLogin` — the token's expiry (`expiry_date`), its `resource_url` and the names of the key lines, never the tokens or key values. The second field, `providerSecrets.qwen.QWEN_API_KEYS`, accepts `OPENAI_API_KEY`, `OPENAI_MODEL` and `OPENAI_BASE_URL` lines only (the first two required; the base URL defaults to Qwen Code's own `https://api.openai.com/v1`); `QWEN_OPENAI_API_KEY` (with `QWEN_OPENAI_MODEL`, `QWEN_OPENAI_BASE_URL`) in the Control Plane's environment overrides the stored lines, as `AI_GATEWAY_API_KEY` does for fx — the plain `OPENAI_*` names are deliberately not read from the Control Plane's environment, since other tools set them for other reasons. With both stored, the OAuth login wins.

**The login travels over the Daemon RPC, onto tmpfs behind a symlink, and the keys into the Agent process environment only.** On every connection the Control Plane sends `_sessionboxer/qwen/auth/set` (`PROVIDER_AUTH` row) before the MCP set that starts the Agent, and again whenever the stored login changes. The Daemon writes `oauth_creds.json` on tmpfs with `~/.qwen/oauth_creds.json` a symlink to it (`AuthFile`, as Codex and Cursor), and puts the key lines in the Agent's environment with `QWEN_OAUTH=1` when a login file is present: that variable is how Qwen Code's auth detection picks `qwen-oauth` over `openai` in `--acp` mode, where there is no `/auth` dialog. Qwen Code refreshes the OAuth token in the file (an atomic write with `noFollow`, mode 0600, which replaces the symlink by a regular file on the container's own filesystem); the Daemon's watcher reports `_sessionboxer/qwen/auth/changed` with the file and the Control Plane stores it when its `expiry_date` is newer, so the next Sandbox starts on the refreshed token. The rest of `~/.qwen` (settings, the project chats `session/load` reads) stays in the container, so Stop → Resume keeps the conversation. In a QEMU Sandbox the three files travel with the Agent start (`settings.json`, `QWEN.md`, `oauth_creds.json`, the last pulled back) as pi's do.

**The Session instructions go in `QWEN.md`** (`instructionsDelivery("qwen")` = context file): Qwen Code's ACP `session/new` has no `_meta.systemPrompt` that reaches the model, but it reads `~/.qwen/QWEN.md` and the project's `QWEN.md` into every request; the Sandbox briefing is the image's `~/.qwen/QWEN.md`, and the Session's own instructions are prepended to the first message as for the other context-file Providers. **MCP servers come from the client**: `session/new` `mcpServers` (stdio, HTTP and SSE) are started by Qwen Code itself, so the `desktop` and `sessionboxer` servers and the user's are handed over the way they are to Claude Code and fx, with no config file to write — but see Consequences: Qwen Code 0.24.7 starts them in `--acp` mode without exposing their tools to the model. **Permissions**: `qwen --acp --yolo` starts in its `yolo` mode (`fullAccessModeIds`), and the Daemon still answers `session/request_permission` with the "allow" option, so a turn never hangs. **Models**: `session/new` returns `models`/`configOptions` with a `model` select (one entry per login — `coder-model` for Qwen OAuth, `OPENAI_MODEL` for an endpoint), which the model picker shows. **Usage**: Qwen Code puts the token counts not in the `session/prompt` result (which carries only `_meta.qwen.branchPoint`) but in the `_meta.usage` of the turn's last `agent_message_chunk` updates — `inputTokens`, `outputTokens`, `totalTokens`, `thoughtTokens`, `cachedReadTokens`, `cachedWriteTokens` — so the Daemon keeps the last chunk usage of a turn (`chunkUsage()`, next to `turnUsage()` in `agent-options.ts`) and reports it when the result has none; no rate windows, so the usage bars are hatched with a pointer and `classifyUsageLimit()` recognises its quota/rate-limit messages.

**Sign in with Qwen Code (ADR-0058) runs the device flow over ACP.** `qwen` has no `login` subcommand and its `/auth` dialog is a TUI, but `qwen --acp` with `authenticate` `{ methodId: "qwen-oauth" }` starts the same device flow non-interactively: with `NO_BROWSER=1` it prints a "Qwen OAuth Device Authorization" box with `https://chat.qwen.ai/authorize?user_code=<code>&client=qwen-code` (also in an `authenticate/update` notification's `_meta.authUri`), polls until the browser side completes, writes `oauth_creds.json` and answers the request. One thing differs from the other recipes: Qwen Code reads ACP from stdin only when stdin is not a terminal (on a pty it answers nothing), so a `Recipe.drive` recipe runs the CLI on plain pipes on the host (`spawnHostPiped`), and in the Sandbox-image container behind a pipe that closes once the login file exists; the flow feeds the two JSON-RPC lines, parses the URL (the code is in it) from the output, opens the page in the browser pane and takes the file as the login.

## Considered Options

- **Qwen Code's own MCP config (`~/.qwen/settings.json` `mcpServers`) instead of `session/new`** — pi's path. Rejected: it starts the servers the client lists in `session/new` (a bogus one fails loudly as "MCP server(s) failed to start"), so nothing needs writing and the user's servers behave like everywhere else; and the settings file was tried too (below) without the tools reaching the model either, so writing it would buy nothing today.
- **A per-Session volume over `~/.qwen`, as fx has.** Rejected: Qwen Code reads the login through the symlink and rewrites the file in place; the conversation it would need for `session/load` lives in the container's `~/.qwen` already, which a Stop → Resume keeps. If a refresh turns out to replace the symlink by a file the watcher misses, the volume is the fallback.
- **Reading `OPENAI_API_KEY` from the Control Plane's environment as the override.** Rejected: too easy to route a Session to the wrong account by accident; the override is namespaced `QWEN_OPENAI_*`.
- **Passing `--experimental-skills` as the registry does.** Rejected for 0.24.7, which ignores it with a deprecation notice.
- **A terminal-driven `/auth` for the Settings sign-in.** Not needed: the ACP `authenticate` method starts the same device flow.

## Consequences

- One more Provider in the lists (`PROVIDERS`, labels, env keys, `QwenLogin`, `DAEMON_METHODS.qwenAuthSet/Changed`, `DaemonQwenAuthParams`, usage classifier); a `PROVIDER_AUTH` row; `qwen-login.ts` and `env-lines.ts` (the `NAME=value` parser pi used, now shared); the driven ACP sign-in recipe and its piped spawn in `qwen-login-recipe.ts` and the guest file table in the Daemon's `provider-files.ts`, to stay in the size budgets; the Qwen card as its own component (`settings/QwenProviderCard.tsx`, with the OpenCode card moved out to `settings/OpenCodeProviderCard.tsx` the same way to keep `ProvidersSettings.tsx` in budget) with its login one-liner in `settings/provider-login-labels.ts`, and the Connect dialog's paste field and secret mapping in `provider-connect-fields.ts`.
- The image grows by what `npm install -g @qwen-code/qwen-code` unpacks, about 200 MB (6.74 GB → 6.94 GB on amd64; the tarball is 36 MB, unpacked 146 MB plus its dependencies).
- The OAuth token is refreshed by Qwen Code itself; a free-tier account has daily quotas Qwen Code reports as an error the usage classifier maps to a limit. An OpenAI-compatible endpoint's cost and limits are the provider's own.
- Verified without a Qwen account: typecheck, lint, build, size budget, dup and the test suites. In the rebuilt image, `qwen --acp` (0.24.7) initialises with protocol 1, `agentCapabilities` `{ loadSession, promptCapabilities: { image, audio, embeddedContext }, sessionCapabilities: { list, resume }, mcpCapabilities: { sse, http } }` and a single `authMethods` entry, `openai` ("Use OpenAI API key", `_meta.type` `terminal`, `--auth-type=openai`; the registry's probe calls it `agent`); `session/new` answers `-32000 Authentication required: Use Qwen Code CLI to authenticate first.` with no credential, with a fake `oauth_creds.json` but no `QWEN_OAUTH`, and with `OPENAI_API_KEY`/`OPENAI_MODEL` but no `OPENAI_BASE_URL` (hence the Daemon's default); an invalid `oauth_creds.json` (not JSON, or without `expiry_date`) with `QWEN_OAUTH=1` gets `Authentication failed: Qwen OAuth credentials expired`; a fake but well-formed one with `QWEN_OAUTH=1` reaches `session/new` (`coder-model(qwen-oauth)`, Qwen 3.7 Max, mode `yolo`) and fails the turn at the token refresh (`405`). Against a mock OpenAI-compatible server (`OPENAI_BASE_URL`), a fake `OPENAI_API_KEY` completes a turn: `end_turn`, the reply streamed as `agent_message_chunk`s, the request carried `QWEN.md` in the system prompt, 17 tools and the usage in the chunks' `_meta.usage`; `session/load` of the same session answered with its modes and replayed the conversation; a bogus `session/new` `mcpServers` entry failed loudly, so the client-side list is read and started — but no MCP tool reached the model in `--acp` mode: a stdio probe server (one tool) handed over `session/new`, or configured in `~/.qwen/settings.json` `mcpServers` (where `qwen mcp list` reports it Connected), or allow-listed in `mcp.allowed`, in mode `yolo`, with `security.folderTrust` off, with a second prompt 40 s later, never appeared among the request's tools nor in `tool_search`'s deferred list, and a tool call the mock model made to it came back "Tool \"sbx_probe_tool\" not found in registry."; the same server in the non-ACP `qwen -p` run shows its tool to the model. So in 0.24.7 the `desktop` and `sessionboxer` servers and the user's MCP servers do not reach Qwen Code's model (an upstream `--acp` limitation to re-test on the next version pin; the Daemon keeps passing them so a fix upstream needs nothing here).
