# Kimi CLI as a Provider, on a Kimi Code login

[Kimi CLI](https://github.com/MoonshotAI/kimi-cli) is Moonshot AI's MIT-licensed coding agent. This follows [ADR-0077](0077-fx-as-a-seventh-provider-on-an-fx-login.md), except where the verified 1.52.0 binary requires a different choice. The filename retains the proposal's API-key wording; **the implemented authentication is OAuth only**.

## Decision

**Provider `kimi`, label "Kimi CLI".** The Linux image installs standalone **1.52.0**, root-owned at `/opt/kimi/kimi` with a PATH symlink. SHA-256 pins from the [ACP registry](https://github.com/agentclientprotocol/registry/blob/main/kimi/agent.json): Linux x86_64 `a676204f7804ed5dae87652a9d66f578e0718d5026c9cb1bfa32b9a5eace4208`, Linux aarch64 `9e06eea96273600aed485b1f0bedda95b7084db4f22cf28614fe20138933507a`; Windows x86_64 `2c269e15e152b9f28ac1556795280f90a2c9860ff44c60c628c3fce4dd4c58a7` in the Windows base installer. `KIMI_CLI_NO_AUTO_UPDATE=1` disables self-updates.

**Import the real OAuth file, not a key.** Run `kimi login` and paste/import `~/.kimi/credentials/kimi-code.json`. The Control Plane validates nonempty `access_token` and `refresh_token`, compacts the JSON and stores it write-only in `providerSecrets.kimi.KIMI_LOGIN`. Public settings contain only `providerSecretsSet.kimi.KIMI_LOGIN` and `kimiLogin: { kind: "oauth", expiresAt }` (Unix seconds converted to ISO). It has no reliable account label. Forget clears the login. No API-key environment override is accepted.

**OAuth over daemon RPC, credentials directory on tmpfs.** The `PROVIDER_AUTH` row sends `_sessionboxer/kimi/auth/set` before starting ACP and when Settings changes. `KimiAuth` links `~/.kimi/credentials` to a private tmpfs directory; `AuthFile` writes `kimi-code.json` directly there with mode 0600. Kimi reads through the directory symlink. Its atomic temp-file + rename refresh therefore stays on tmpfs even during replacement, rather than leaving a token on the snapshot disk until a sweep repairs a file-only symlink. The watcher reports `_sessionboxer/kimi/auth/changed`; newer expiry wins and identical/invalid/older files are ignored. Session records stay in `~/.kimi/sessions` on the container filesystem for Stop/Resume. No extra Docker volume is needed. Neither token enters container environment, inspection output, public settings or daemon logs. Windows uses the existing guest credential push/pull mechanism; guest credentials live on its per-Session VM disk, like the other guest Providers, not Linux tmpfs.

**Sign in with Kimi CLI** uses `kimi login` in the existing scratch-home pty/container flow. Even without a TTY, 1.52.0 prints `Verification URL: https://www.kimi.com/code/authorize_device?user_code=XXXX-XXXX`, then polls. The recipe accepts that host/path, extracts the code, and captures the credential file only after successful exit. It clears inherited `KIMI_SHARE_DIR` so login cannot write into the host's regular profile.

**ACP, MCP and instructions.** The daemon runs `kimi acp`. A fresh profile gets non-secret config for the documented `kimi-for-coding` model at `https://api.kimi.com/coding/v1`, referencing OAuth key `oauth/kimi-code`; importing the credential alone would otherwise leave Kimi without a model. Existing config is preserved. `default_yolo = true` grants tool permissions; the generic ACP permission responder remains active. Kimi honors client `mcpServers` on new/load, so both built-in servers and user servers go through ACP, not an extra MCP file. The existing image's `/AGENTS.md` delivers the Sandbox briefing; Kimi reads ancestor/project `AGENTS.md` and `.kimi/AGENTS.md`. Standing Session instructions and dynamic workspace briefing use the established first-prompt prefix, once per fresh conversation: Kimi has no ACP system-prompt append hook.

**Model picker and usage.** Kimi 1.52.0 returns the older `models.availableModels/currentModelId`, not `configOptions`. The daemon converts this to model choices and switches through `session/set_model`; newer adapters keep `session/set_config_option`. Kimi `session/load` returns an empty object, so the advertised catalog is persisted with daemon state and an explicit requested model is reapplied after load. Kimi drops its internal `StatusUpdate` events in ACP, and its prompt result has only `stopReason`: no invented token counts or rate windows. The UI shows hatched bars pointing to the Kimi Code account.

**Platforms.** Linux x86_64/arm64 and Windows have pinned builds. QEMU · macOS runs an x86_64 guest; the registry supplies only Darwin arm64. `providerUnavailableIn("kimi", "qemu-macos")` returns the reason, disabling that UI choice and rejecting creation server-side. No macOS installation or TOOLCHAIN bump is appropriate. Windows installation uses the registry's checksum-verified x86_64 ZIP.

## Considered Options

- **API-key-only ACP:** rejected based on the real binary: **Kimi CLI 1.52.0 `session/new` → "Authentication required" even with `KIMI_API_KEY` and valid Moonshot config**. Its ACP server checks `oauth/kimi-code` before model-provider configuration. API-key-only use is unsupported until Kimi's ACP server honours it. No synthetic credential is generated by product code. Synthetic, nonworking tokens were used only in isolated mock probes, never to claim real authentication.
- **A file symlink like Codex:** reads work, but Kimi atomically replaces the path. A directory symlink keeps temporary files, lock files and final tokens on tmpfs without a credential-on-disk interval.
- **A persistent login volume like fx:** unnecessary; Kimi tolerates the directory symlink. Keeping only credentials on tmpfs preserves native conversation persistence without another volume to delete.
- **Install Python/uv Kimi on the x86_64 Mac:** declined in favor of an explicit unavailable reason; no verified standalone build exists for that guest.
- **Fabricate a login to unlock a key:** rejected explicitly. Settings accepts genuine OAuth file structure only, and does not claim that structural validation authenticates an account.

## Consequences

The rebuilt amd64 image measured **1,919,386,555 bytes**, versus **1,823,630,300 bytes** for a paired build without the Kimi install layer: **+95,756,255 bytes (91.32 MiB)**. The standalone binary is 96,536,248 bytes; this is substantially larger than fx, but avoids installing a Python toolchain and dependencies. These are Docker inspect sizes; the Kimi installation layer itself is 96,563,200 bytes (92.09 MiB). The paired total also reflects other rebuilt layers. Docker Hub returned 429; the official node/Ubuntu images were pulled from the public ECR mirror, retagged, and the normal image build succeeded.

## Verified

**Verified against the rebuilt image:** `kimi, version 1.52.0`; ACP protocol 1; `loadSession`, `session/list`, `session/resume`; HTTP MCP support true, SSE false; image and embedded-context prompts true, audio false. The only auth method is `login` / "Login with Kimi account", terminal args `["login"]`. Missing, malformed and API-key-only credentials reject `session/new` with "Authentication required". An isolated synthetic OAuth-shaped test file plus a local OpenAI-compatible model config reached new/prompt/set_model/load, streamed "Kimi mock verified.", and delivered an AGENTS.md marker to the mock. The same probe succeeded with the credentials directory symlinked. A regression test atomically replaces the file, verifies the target remains behind the symlink, observes refresh notification, checks mode 0600 and ensures token text is absent from logs. Provider-auth, schema, routes, daemon-error tests, typecheck, lint, build, size-budget and duplication checks passed.

**Not verified with a real account:** completed browser authorization, OAuth refresh redemption/rotation against Kimi, membership entitlements, actual model answers, real account model catalog, billing/limits. ARM and Windows boot/runtime were not exercised; their installation artifacts are pinned, not claimed as runtime-tested. MCP advertisement was exercised, not real-model tool execution.


**Verified through the browser against an isolated Control Plane:** OAuth help/import/save/Forget/expiry metadata and blank stored field; real device URL/code generation then cancellation; existing Provider cards; Linux Kimi dropdown; disabled macOS entry using a response-only machine-availability fixture because no guest base disk was present. A config-only derivative of the rebuilt image kept the real Kimi executable and routed two mock models to a local streaming endpoint. A fresh Session reached idle, streamed three replies, exposed both models, switched to the second model, then Stop → Resume loaded the same ACP session and retained its transcript, catalog and selected model. Model request capture saw the standing marker and Sandbox briefing exactly once in conversation history, plus all 82 advertised tools including desktop, sessionboxer and a user HTTP MCP. UI Delete removed the Session and its container; no Kimi-specific volume existed. The final browser window had no console errors. The credential directory resolved into tmpfs, file mode was 0600, and synthetic token markers were absent from Docker environment, daemon/CLI/Control Plane logs, model requests, and 250 captured public API/websocket messages.

**Compatibility fixes found by that test:** Kimi rejected the desktop MCP tuple schemas under its modern JSON Schema validator. Coordinate and zoom-region schemas now use homogeneous integer arrays with exact lengths 2 and 4, preserving their runtime contract. The test also exposed an existing shared first-prompt bug: the daemon consumed its fresh-conversation marker before constructing the instructions prefix. Constructing the prefix first restores the documented delivery for Kimi and every other first-prompt Provider. Both failures have regression pins, and the final browser lifecycle passed after rebuilding.
