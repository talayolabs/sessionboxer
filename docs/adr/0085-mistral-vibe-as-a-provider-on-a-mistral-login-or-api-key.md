# Mistral Vibe as a Provider, on a Mistral login or API key

[Mistral Vibe](https://github.com/mistralai/mistral-vibe) is Mistral's open-source coding agent (Apache-2.0, Python). Its releases ship a standalone `vibe-acp` per platform (a PyInstaller bundle: Linux x86_64 and aarch64, macOS arm64 and x86_64, Windows x86_64), which is the ACP server the `vibe` TUI's `--acp` would start. It runs on a Mistral account: an API key from console.mistral.ai, or the key Vibe obtains when the user signs in through Mistral AI Studio in a browser. Version 2.25.8 is what the [ACP registry](https://github.com/agentclientprotocol/registry/tree/main/mistral-vibe) pins; every claim below was checked against that binary.

## Decision

**Provider `vibe`, label "Mistral Vibe"**, alongside `claude-code`, `devin`, `codex`, `cursor`, `pi`, `opencode` and `fx`. The image downloads the release archive for `TARGETARCH` (`vibe-acp-linux-{x86_64,aarch64}-2.25.8.tar.gz`), checks its SHA-256 against the registry's, unpacks it root-owned under `/opt/vibe` and links `vibe-acp` into `/usr/local/bin`; the Daemon spawns `vibe-acp` over stdio with `VIBE_ENABLE_AUTO_UPDATE=false` (the image pins the version) and `VIBE_TEST_DISABLE_KEYRING=1` (there is no OS keyring in a container; without the flag Vibe tries one, finds none and falls back to its `.env`, so this only saves the attempt and makes the file the one place the key lives). The macOS base gets the darwin archive for its architecture in `~/.local/share/vibe/<version>` with a link in `~/.local/bin` (`TOOLCHAIN` bumped); the Windows base gets the ZIP in `%LOCALAPPDATA%\Programs\vibe` on the user PATH; both verify the SHA-256. Vibe runs in every Machine, so `providerUnavailableIn("vibe", …)` is always `null`.

**The credential is a Mistral API key, or the `~/.vibe/.env` Vibe writes, in one field.** Vibe reads `MISTRAL_API_KEY` from its process environment, else from `~/.vibe/.env` (a dotenv file; where an OS keyring exists it prefers that and leaves the file alone). The Settings card accepts either a pasted key or a pasted/imported `.env`, like fx's one field for three files: `normalizeVibeLogin` keeps a key as is and a dotenv as its non-empty lines, refusing text that is neither a key nor a file with a `MISTRAL_API_KEY=` line (the two error messages are user-facing). The secret is `providerSecrets.vibe.VIBE_LOGIN`, write-only; `GET /api/settings` publishes `providerSecretsSet.vibe.VIBE_LOGIN` and `vibeLogin: { kind: "api-key" | "env-file" }` and nothing else, because the file has nothing else safe to show (no expiry, no account; the key is opaque). `MISTRAL_API_KEY` in the Control Plane's environment overrides the stored login, as `AI_GATEWAY_API_KEY` does for fx.

**The login travels over the Daemon RPC onto tmpfs, as Vibe's `.env`.** On every connection the Control Plane sends `_sessionboxer/vibe/auth/set` (the `PROVIDER_AUTH` row) before the MCP set that starts the Agent; the Daemon writes the key as `MISTRAL_API_KEY='…'` (a pasted `.env` as is) to `/dev/shm/sessionboxer/vibe-auth.json` (mode 0600) and symlinks `~/.vibe/.env` to it — Vibe follows the symlink, so the Codex/Cursor arrangement works and nothing touches the disk layer. The rest of `~/.vibe` (config, `logs/session/*` which `session/load` needs, `trusted_folders.toml`, `AGENTS.md`) stays on the container's disk. Vibe reads the file at start, so the Agent restarts in place when the login arrives or changes (a per-login `SESSIONBOXER_VIBE_LOGIN` marker in its environment makes the change visible to the restart logic without putting the key there). The `AuthFile` watcher reports a rewritten `.env` that holds a `MISTRAL_API_KEY` line as `_sessionboxer/vibe/auth/changed` — the file a sign-in from inside the Agent would write — and the Control Plane stores it when it carries a different key than the one it holds (`vibeAuthNewer`); an API key stored by the user is never replaced by a file with the same key. Forget sends an empty login; the Daemon removes the file and restarts the Agent, which then refuses as below.

**Sign in with Mistral Vibe from Settings (ADR-0058) uses Vibe's delegated browser auth over ACP.** `vibe-acp` has no `login` subcommand and its `--setup` is a TUI wizard, but when the client's `initialize` advertises `_meta: { "browser-auth-delegated": true }` the agent lists an `authMethods` entry `browser-auth-delegated`; `authenticate` with `_meta.action: "start"` returns an attempt id, an expiry and a sign-in URL on console.mistral.ai, and `authenticate` with `action: "complete"` and the id returns once the user has signed in, Vibe having stored the key Mistral issued in `~/.vibe/.env` (keyring disabled). `images/sandbox/vibe-login` is a 90-line Node client for that exchange, installed in the image as `sessionboxer-vibe-login`: it prints `Open <url>` and exits 0 once the key is written; `provider-login.ts` runs it on a pty like the other CLIs, shows the URL, and reads `~/.vibe/.env` from the scratch home when it exits. The helper is not installed on the Control Plane's machine, so the sign-in always takes the other CLIs' fallback, a throwaway box from the Sandbox image (a Control Plane without Docker reports that, as it does for a missing CLI). There is no device code to show: the browser session on console.mistral.ai is the whole check.

**MCP, instructions, permissions.** Vibe takes the client's MCP servers in `session/new` and `session/load` (the Daemon hands over `desktop`, `sessionboxer` and the user's servers as it does for the others, and Vibe registers their tools as its own: "MCP integration registered 66 tools"; `initialize` advertises no `mcpCapabilities`, so HTTP servers are untested). It reads `~/.vibe/AGENTS.md` as its global instructions, so the image copies the Sandbox briefing there (the Linux one; the Daemon rewrites it for the macOS and Windows guests as it does Cursor's). `session/new` takes no system prompt, so `instructionsDelivery("vibe")` is `first-prompt`: the Session's instructions go ahead of the first message of each conversation the box starts. Vibe runs tools only in folders it trusts, so the Daemon writes `~/.vibe/trusted_folders.toml` with the Workspace before the Agent starts. ACP modes are `ask`, `plan`, `accept-edits` and `auto-approve`; the Daemon switches to `auto-approve` (`fullAccessModeIds`) and still answers `session/request_permission` with the first allow option, so a turn never hangs. Vibe echoes each prompt it is given back as a `user_message_chunk` (the first one with the instructions in front), which Sessionboxer only expected from a history replay and showed as a second user bubble; the Daemon now drops `user_message_chunk`s while a turn is active — the prompt is on record as `user_prompt`. Vibe fetches an "admin-managed config" from chat.mistral.ai at start (HTTP 401 without an enterprise login, logged and ignored); nothing else leaves the box but the model calls.

**Model picker and usage.** `session/new` returns `configOptions` `model` (the models of Vibe's configuration: `mistral-medium-3.5`, `local`, plus whatever `~/.vibe/config.toml` adds) and `thinking` (off/low/medium/high/max); the Daemon captures them as for the others. Usage comes as a `usage_update` per turn (context used/size, prompt and completion tokens) and the prompt result carries `usage`; there are no rate windows, so the bars are hatched with a pointer to console.mistral.ai → Usage, and `usage.ts` knows the Mistral API's refusals (*rate limit*, *quota exceeded*, HTTP 429, *insufficient credits*).

## Considered Options

- **API key only**: simplest, and the key is what the Mistral console hands out; but Vibe's own first run is a browser sign-in that ends in the same key, and users of Vibe on their machine without a keyring have a `.env`, so both are taken, as fx takes a login file or a key.
- **The key in the Agent's environment only (Cursor's `CURSOR_API_KEY` route)**: works for a pasted key, but a sign-in from inside the Agent (`browser-auth` in the ACP auth methods) writes `.env`, which the environment would shadow and the Daemon could not report back; the file keeps one source.
- **A per-Session volume for `~/.vibe` (fx's route)**: unnecessary, Vibe follows the `.env` symlink onto tmpfs; its sessions and logs survive Stop → Resume on the container's disk like OpenCode's.
- **Writing the MCP servers to Vibe's `config.toml`**: unnecessary, `session/new` `mcpServers` are honoured.
- **`--setup` on a pty for the sign-in**: it is a Textual TUI wizard (API key or browser), not a device flow whose output can be parsed; the ACP `browser-auth-delegated` exchange is the headless form of the same sign-in and needs no TUI.
- **Running the Agent in `accept-edits`**: that mode still asks before shell commands; `auto-approve` is Vibe's yolo mode and the Sandbox is the isolation, as for the others.

## Consequences

- Needs an image rebuild (the Vibe layer is 201MB in `docker history`, the PyInstaller bundle under /opt/vibe being 192 MB on disk; `docker images` shows 7.02 GB for the image with Vibe — the exact size without it was not kept, since Copilot and Kimi CLI went into the same image in parallel); 6.74 GB → 7.02 GB as `docker images` shows); existing Sandboxes keep working as before (a Daemon that predates this answers "method not found" to the auth push and is logged as such). A macOS base needs Reprovision before it can start Sessions again; a Windows base needs a fresh install for `vibe-acp.exe` to be there.
- The login is only as private as `~/.sessionboxer/config.json`, same as the other tokens; it is never in public settings, events, `docker inspect`, Snapshots or logs (the Daemon logs byte counts).
- What Vibe advertises over ACP (`vibe-acp 2.25.8`, `initialize`): protocol version 1; `loadSession: true`; `promptCapabilities` image and embedded context (no audio); `sessionCapabilities` list, fork and close; `authMethods` `browser-auth` ("Sign in through Mistral AI Studio"), plus `browser-auth-delegated` and `vibe-setup` (`--setup`, type `terminal`) when the client advertises `browser-auth-delegated`/`terminal-auth` in `_meta`. `session/new` returns `modes` ask (default) / plan / accept-edits / auto-approve and `configOptions` model / thinking. Without a credential `initialize` and `session/new` succeed and the first prompt fails with "Missing API key for mistral provider."; with an invalid key (`MISTRAL_API_KEY=invalid-key-123` in `.env`) the prompt reaches api.mistral.ai and fails with "Invalid API key (from env var MISTRAL_API_KEY). Please check your API key and try again." — both arrive as an `agent_error` in the transcript, not as a hang. A fake key reaches `session/new` (the gate is the model call, as for fx's key).
- Vibe does not persist an ACP session that had no prompt: Stop → Resume of a Session that was never prompted gets "Session not found" from `session/load` and the Daemon creates a new session (logged). Fixing that path showed a Daemon bug that predates this ADR: the first prompt was marked as sent before the `first-prompt` prefix was built, so the standing instructions never reached Codex, Cursor, OpenCode, Devin and pi either; `agent.ts` now builds the text first.
- `VIBE_TEST_DISABLE_KEYRING` is an upstream test knob, not a documented setting; if a release drops it Vibe would try the keyring, find none, and read `.env` anyway, so the Sandbox keeps working and only the log changes.
- Verified without a Mistral account: typecheck, lint, build, size budget and the test suites; `vibe-acp` in the rebuilt image initialises as above, refuses without a credential and with an invalid one as quoted; the login reaches the box as a 0600 file on tmpfs behind the `~/.vibe/.env` symlink, absent from `GET /api/settings` (which shows `{ kind: "api-key" }`), the events and `docker inspect`; invalid logins get the two 400 messages. A full turn through Sessionboxer against a mock OpenAI-compatible endpoint (a `[[providers]]`/`[[models]]` entry in the Sandbox's `~/.vibe/config.toml`, something the Provider does not set up for users): the Session reached `idle`, the model got the briefing in its system prompt and the `desktop_*` and `sessionboxer_*` tools next to Vibe's own (76 in all), the reply streamed into the transcript as `agent_message_chunk`s, `usage_update` and the turn's `usage` arrived (1 276 tokens), Stop then Resume reached `session/load` and the second turn carried the first, Delete removed the container. Not verified: a turn on a real Mistral key or account; the browser sign-in end to end (the ACP exchange was driven by hand up to the sign-in URL on console.mistral.ai, not completed, so what the completed exchange writes to `.env` is taken from Vibe's source); a refreshed `.env` flowing back (the watcher and `vibeAuthNewer` are unit-tested, not exercised by a real sign-in); a macOS or Windows VM (the install stanzas mirror OpenCode's and fx's; the Windows ZIP's layout — `vibe-acp.exe` at its root — is taken from the registry entry). The web UI was checked in a browser against the running Control Plane: the Settings → Providers Mistral Vibe card with its help popover and Sign in button, the New session Agent dropdown with Mistral Vibe among the ten Providers (Docker · Linux; no QEMU base exists on the test machine), the mock Session's transcript, the composer model picker (`mock-1`) and the hatched usage bars with their pointer; the other cards unchanged, no console errors.
