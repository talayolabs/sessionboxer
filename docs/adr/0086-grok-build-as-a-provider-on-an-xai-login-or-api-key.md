# Grok Build as a Provider, on an xAI login or API key

[Grok Build](https://docs.x.ai/docs/grok-build) is xAI's own coding agent and CLI (proprietary, npm `@xai-official/grok`): a single native binary per platform, shipped Brotli-compressed inside a platform package (`@xai-official/grok-linux-x64`, `-linux-arm64`, `-darwin-x64`, `-darwin-arm64`, `-win32-x64`, `-win32-arm64`) and unpacked by the main package's postinstall into `~/.grok/bin`. Its ACP server is built in: `grok agent stdio` speaks stdio JSON-RPC with `session/new`, `session/load`, `session/list`, `session/resume`, `session/close`, `session/prompt`, `session/cancel`, permission requests, config options and MCP servers from the client. It runs on xAI's models only, with an xAI account (`grok login`) or an API key from console.x.ai. Sessionboxer already reaches a **Grok subscription** through fx (`fx login grok`, ADR-0077); this Provider is xAI's agent on an xAI login, and the GUIDE says which is which. This ADR adds it the way ADR-0077 added fx; where that ADR made a choice, this one mirrors it.

## Decision

**Provider `grok`, label "Grok Build"**, alongside `claude-code`, `devin`, `codex`, `cursor`, `pi`, `opencode` and `fx`. The image downloads the npm platform package the postinstall would fetch, pinned to **`1.0.49`** by `TARGETARCH`, checks it against the registry's sha256 observed at pin time (`578c9be9d1e3316c04acff2dada0d9cf9e9937e0a44bc1bfe33e08c2cfb6e7cf` linux-x64, `7945ed6d352e23378c346cde3b5fdee51c5132a21a9a9006c8e0ef83e6e4d6d1` linux-arm64), decompresses `bin/grok.br` with Node's `zlib` and installs the binary root-owned as `/opt/grok/grok`, linked as `/usr/local/bin/grok` (a global `npm install -g` would have put a per-user copy under `~/.grok/bin` and a shim that re-downloads it). The Daemon runs it with `GROK_DISABLE_AUTOUPDATER=1` and the image ships `~/.grok/config.toml` with `[cli] auto_update = false` for the terminal, so a Sandbox runs the version the image was built with.

**The credential is Grok Build's login file, or an xAI API key, pasted once.** The user runs `grok login` on their own machine (browser OAuth; `--device-auth` and `--device-code` print a URL and a code instead) and pastes or imports `~/.grok/auth.json`, a 0600 JSON object with the session `key`, `refresh_token`, `expires_at`, `create_time`, `auth_mode`, `user_id`, `email` and `oidc_issuer`; an API key (console.x.ai → API keys) is accepted in the same field. Settings stores it write-only as `providerSecrets.grok.GROK_LOGIN`; the Control Plane validates the paste (an API key's character set, or a JSON object with a `key`), compacts the JSON and publishes only `providerSecretsSet.grok.GROK_LOGIN` and `grokLogin: { kind: "api-key" | "account", email, expiresAt }`. `XAI_API_KEY` in the Control Plane's environment overrides the stored login, like `AI_GATEWAY_API_KEY` does for fx.

**The login travels over the Daemon RPC, onto tmpfs behind a symlink, like Codex's and Cursor's.** On every connection the Control Plane sends `_sessionboxer/grok/auth/set` before the MCP set that starts the Agent, and again whenever the stored login changes (forgetting it removes the file from running boxes). The Daemon writes the file to its tmpfs as a regular 0600 file and points `~/.grok/auth.json` at it; Grok Build follows the symlink (verified: `initialize` then advertises `cached_token` and a turn reaches xAI), so no per-Session volume is needed: the saved conversations `session/load` needs live in `~/.grok/sessions/<encoded cwd>/<id>/` on the container's own filesystem, which Stop/Resume keeps and Delete removes with the container. The Daemon deletes the file on shutdown; an API key becomes `XAI_API_KEY` in the Agent's process only (Grok Build reads the file first and the variable when there is none, and checks the key against its endpoint when it starts). Nothing reaches `docker inspect`, the container's environment, a Snapshot, events or logs. Grok Build refreshes the session token in place and reloads the file when it changes; the Daemon's watcher reports the rewritten file as `_sessionboxer/grok/auth/changed`, the Control Plane stores it when it is a newer login of the same kind (by `expires_at`, then `create_time`) and pushes it to every live Grok Build Session.

**Sign in with Grok Build from Settings (ADR-0058) uses xAI's device flow.** `grok login --device-auth` prints `To sign in, open this URL in your browser: https://accounts.x.ai/oauth2/device?user_code=XXXX-XXXX` and `Confirm this code in your browser: XXXX-XXXX`, then polls xAI until the page is confirmed; that fits `provider-login.ts` as Codex's `--device-auth` does (the dialog opens the URL and shows the code; the page prefills it). The stored result is `~/.grok/auth.json` from the scratch home. The macOS and Windows bases get Grok Build from npm (`npm install -g @xai-official/grok@1.0.49`, in `macos.ts` `finish()` with `TOOLCHAIN` bumped so existing bases show "Reprovision", and in `images/windows/oem/install.bat`); every platform has a build, so `providerUnavailableIn("grok", …)` is never set.

**MCP, instructions, permissions.** Grok Build takes the client's MCP servers in `session/new`/`session/load` (stdio with an `env` array, HTTP and SSE) and starts them itself — the built-in `desktop` and `sessionboxer` servers and the user's reach it this way; a server that fails its handshake is reported as `_x.ai/mcp/server_status` `unavailable` rather than failing the session, and the model reaches the servers' tools through Grok Build's own `search_tool`/`use_tool` pair rather than one function per MCP tool. Session instructions are delivered as a system prompt: `session/new` accepts `_meta.rules` (appended to Grok Build's own prompt as `<human_rules>`; `_meta.systemPromptOverride` would replace it), so `instructionsDelivery("grok")` is `system-prompt` and the Daemon sends `{ rules: text }`. The Sandbox briefing is installed as `~/.grok/rules/sandbox-briefing.md`, one of the user-level rules files Grok Build reads (`$GROK_HOME/rules/*.md`; it also reads the repository's `AGENTS.md`, `AGENT.md`, `CLAUDE.md` and `.grok/rules/*.md`). Permissions: the Daemon starts it with `--always-approve` (alias `--yolo`), its documented "approve everything" mode; the Sandbox is the isolation, and the Daemon still answers any `session/request_permission` (`allow_always`, then `allow_once`, then the first option) so a turn never hangs. On macOS the same files travel into the VM through the guest transport (ADR-0061): `~/.grok/config.toml`, the rules file and `~/.grok/auth.json`, pulled back when Grok Build rewrites it.

**Model picker and usage.** `session/new` returns `configOptions` with a `model` option (xAI's catalogue for the login; `mock-1` from the custom endpoint used for verification), and Grok Build's own reasoning levels (`low`/`medium`/`high`/`xhigh`); the Daemon captures them as for the others, so Model appears in the composer and in New session. The prompt response carries no ACP `usage`; the counts (`inputTokens`, `outputTokens`, `totalTokens`, `cachedReadTokens`, `cacheCreationTokens`, `reasoningTokens`) sit under its `_meta.usage` (and in a `turn_completed` update), so the Daemon reads `_meta.usage` when `usage` is absent and `cacheCreationTokens` as the cache-write count (it knew `cachedWriteTokens`/`cacheWriteTokens`). Grok Build sends no `usage_update` either, but `session/new` lists each model's window (`availableModels[]._meta.totalContextTokens`: 500k for grok-4.6, 256k for the mock's model), so the Daemon derives one at the end of a turn that brought none: used = the turn's input (cache reads included) plus output, size = the window of the model the response names (`_meta.modelId`); exact for a turn with one model call, an over-estimate for a turn with several, so the context gauge is indicative. Grok Build reports no rate windows and its model calls do not pass through the box, so the usage bars are hatched with a pointer to console.x.ai; a refusal mentioning insufficient credits, a usage limit or a quota is classified as a limit hit like the others.

## Considered Options

- **`XAI_API_KEY` only**: simple and secure, but a key needs a prepaid balance on console.x.ai; `grok login`'s file is what a Grok subscriber has. Both are accepted, as for fx.
- **A per-Session volume over `~/.grok` like fx**: unnecessary, Grok Build reads the login through a symlink and its session store survives Stop/Resume on the container's filesystem; tmpfs keeps the secret off the host's disk, as for Codex and Cursor.
- **`npm install -g` in the image**: the main package's postinstall downloads the platform package again and unpacks it per user under `~/.grok/bin`, with a shim that would re-run that on an empty home; the platform package itself, pinned by sha256 and unpacked at build time, is what the installer would have fetched.
- **Writing the MCP servers to `~/.grok/config.toml`**: unnecessary, Grok Build takes them from the client.
- **`_meta.systemPromptOverride`**: replaces Grok Build's own system prompt (tool guidance included); `_meta.rules` appends, which is what claude-agent-acp's `systemPrompt.append` does.
- **Running `grok login` from the box**: Grok Build polls xAI itself, so the ADR-0058 flow in a scratch home works from the Control Plane's machine; nothing has to call back into the Sandbox.
- **fx's `grok` login instead of a Provider**: that is a Grok subscription behind Vercel's agent; Grok Build is xAI's agent, with its own tools, rules and models, so the two stay apart and the GUIDE says which to pick.

## Consequences

- Needs an image rebuild (about 176 MB more, the decompressed binary); existing Sandboxes keep working as before (a Daemon that predates this answers "method not found" to the auth push and is logged as such). A macOS base needs Reprovision and a Windows base a rebuild before they can start Grok Build Sessions.
- The login is only as private as `~/.sessionboxer/config.json`, same as the other tokens; it is never in public settings, events, `docker inspect`, Snapshots or logs.
- What Grok Build advertises over ACP (`1.0.49`, `initialize`): protocol version 1; `loadSession: true`; `promptCapabilities` embedded context only (no image, no audio); `mcpCapabilities` HTTP and SSE (stdio is implied); `sessionCapabilities` list, resume and close; `authMethods` is `[{ id: "grok.com", name: "Grok", description: "Sign in with Grok" }]` without a credential and `[{ id: "cached_token", description: "Cached token from ~/.grok/auth.json" }]` with one. Without a credential `session/new` fails with `-32000 Authentication required` (`no auth method id provided`), which the UI shows as the usual "needs a login" error; with a fake login file the session starts and the first turn fails with `Unauthorized (401) from https://cli-chat-proxy.grok.com/v1/responses: Invalid or expired credentials`; an API key is checked against the endpoint during `initialize` (`xai.api_key` joins `authMethods` only when the endpoint accepts it), so a fake `XAI_API_KEY` leaves `session/new` at `Authentication required`. `--xai-api-base-url` (or `GROK_XAI_API_BASE_URL`) points it at another OpenAI-compatible endpoint, which is how the mock turn was run; Grok Build does not expose usage windows or the raw model calls (Inspect LLM stays Claude Code only); `session/load` replays the saved conversation.
- Verified without an xAI account: typecheck, lint and build; `grok agent stdio` in the rebuilt image initialises as above and refuses `session/new` without a credential; the login reaches the box as a 0600 file on tmpfs behind `~/.grok/auth.json` (or as the Agent's environment alone), absent from `GET /api/settings`, the events, `docker inspect` and the Snapshot image; `_meta.rules` reaches the model (the marker appeared in the mock endpoint's request); the client's MCP servers are accepted and a broken one is reported as `handshake_failed`. A full turn through Sessionboxer against a mock OpenAI-compatible endpoint (`[endpoints] xai_api_base_url` added to the Sandbox's `~/.grok/config.toml` by hand, with `xai-mock` as the API key; something the Provider does not set up for users): the Session reached idle, the model's request carried the Session instructions and the Sandbox briefing inside `<human_rules>`, the `desktop` (22 tools) and `sessionboxer` (44 tools) servers as connected MCP servers behind `search_tool`/`use_tool`, the reply streamed into the transcript with `mock-1` in the model picker, the transcript showed the turn's token counts from `_meta.usage` and the Context pane the derived occupancy against the model's window, Stop then Resume reached `session/load` (the conversation came back and a second turn carried the first), Delete removed the container and its volume. Not verified: a turn on a real xAI login or API key; the device-flow dialog end to end (the command and its output were checked, not a completed sign-in); whether the repository's `AGENTS.md` reaches the model (the docs say so; the mock request did not show it); a macOS or Windows VM. The web UI was checked in a browser against the running Control Plane: the Grok Build card with its help popover, sign-in, paste/import, metadata line (`xAI API key`) and Forget; all eight Providers in New session's Agent menu with Grok Build enabled; the mock Session's transcript (`in 42 / out 7`), model picker (`mock-1`), context gauge (49 of 256,000) and hatched usage bars with the console.x.ai pointer; the seven other cards unchanged; no console errors.
