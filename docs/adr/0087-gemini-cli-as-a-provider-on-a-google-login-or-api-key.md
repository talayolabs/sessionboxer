# Gemini CLI as a Provider, on a Google login or an API key

[Gemini CLI](https://github.com/google-gemini/gemini-cli) is Google's open-source coding agent (Apache-2.0): a Node.js program published as the npm package `@google/gemini-cli`, so it runs wherever Node 20+ does — Linux, macOS and Windows. Its ACP server is built in: `gemini --acp` speaks stdio JSON-RPC with `session/new`, `session/load`, `session/prompt`, `session/cancel`, `session/set_mode` and `session/set_model`, permission requests, and MCP servers from the client. It talks to Gemini through one of four credentials: a Google account ("Login with Google", the free Code Assist tier or a Code Assist subscription), a Gemini API key from AI Studio, Vertex AI, or a custom API gateway. This ADR adds it the way ADR-0077 added fx; where that ADR made a choice, this one mirrors it unless Gemini CLI forces otherwise.

## Decision

**Provider `gemini`, label "Gemini CLI"**, alongside `claude-code`, `devin`, `codex`, `cursor`, `pi`, `opencode`, `fx`, `kimi`, `copilot`, `vibe` and `grok`. The image downloads the npm tarball `https://registry.npmjs.org/@google/gemini-cli/-/gemini-cli-<version>.tgz` pinned to **`0.62.0`** (the version the ACP registry pins) and checks it against the sha256 the registry publishes for it, `2276032b1c33d2b828b1cf197e52f48e74b0a395326763ff01a80d97d0fbc0c3`, then installs it with `npm install -g --omit=optional`: root-owned under `/usr/lib/node_modules/@google/gemini-cli` (one 100 MB bundle plus its native dependencies), linked as `/usr/bin/gemini`. The package is pure JavaScript, so one tarball serves both `TARGETARCH`es. The image's `/home/agent/.gemini/settings.json` turns the self-update and its notice off (`general.enableAutoUpdate`, `general.enableAutoUpdateNotification`), the usage statistics off (`privacy.usageStatisticsEnabled`) and the folder-trust prompt off (`security.folderTrust.enabled`); the Daemon also runs the Agent with `GEMINI_CLI_TRUST_WORKSPACE=true` (Gemini CLI silently drops `--yolo` to the default approval mode in a workspace it does not trust), `NO_BROWSER=true` (it never gets to open one) and `GEMINI_TELEMETRY_ENABLED=false`.

**The credential is Gemini CLI's own Google login file, or a Gemini API key, pasted once.** The user runs `gemini` on their own machine, chooses "Login with Google", and pastes or imports `~/.gemini/oauth_creds.json` (an OAuth session: `access_token`, `refresh_token`, `id_token`, `expiry_date`); or pastes an API key from [AI Studio](https://aistudio.google.com/apikey) in the same field, as fx does. Settings stores it write-only as `providerSecrets.gemini.GEMINI_LOGIN`; the Control Plane validates the paste (an API key's character set, or a JSON object with `access_token` and `refresh_token`), compacts the JSON, and publishes only `providerSecretsSet.gemini.GEMINI_LOGIN` and `geminiLogin: { kind: "api-key" | "google", expiresAt, email }` — `expiresAt` from the file's `expiry_date`, `email` from the `id_token`'s claims, read without verifying the token (it is only shown back to the user who pasted it). `GEMINI_API_KEY` in the Control Plane's environment stands in for a stored key, as `AI_GATEWAY_API_KEY` does for fx. Vertex AI (`GOOGLE_API_KEY` with `GOOGLE_GENAI_USE_VERTEXAI`, or application-default credentials) and the API-gateway method are out of scope: they need a Google Cloud project and credentials Sessionboxer has no field for.

**The login travels over the Daemon RPC onto tmpfs, and the auth method into `settings.json`.** On every connection the Control Plane sends `_sessionboxer/gemini/auth/set` before the MCP set that starts the Agent, and again whenever the stored login changes (forgetting it removes the file from running boxes). Gemini CLI tolerates a symlinked login file, so the Sandbox keeps it as Codex's and Cursor's: `~/.gemini/oauth_creds.json` is a symlink to a 0600 file on `/dev/shm`, never in the container's layers or a Snapshot; `~/.gemini` itself stays a real directory because Gemini CLI writes its chat records, history and `projects.json` next to the login. An API key goes into the Agent process environment alone (`GEMINI_API_KEY`), never into the container's environment or `docker inspect`. Under `--acp` Gemini CLI does not infer the auth method from what is present: with only the login file (or `GOOGLE_GENAI_USE_GCA=true`) it still asks for an API key, so the Daemon writes `security.auth.selectedType` into the image's `settings.json` — `oauth-personal` for a login file, `gemini-api-key` for a key, removed with the login — and restarts the Agent in place, as the other synced logins do. Gemini CLI refreshes an expired Google access token on its own and rewrites `oauth_creds.json` in place (mode 0600); the Daemon watches the file as it does Codex's and reports the new contents as `_sessionboxer/gemini/auth/changed`, so the Control Plane stores the refreshed session and later Sessions start from it. In a QEMU VM (Windows or macOS) the file is pushed into the guest's `.gemini/` and pulled back the same way.

**No "Sign in with Gemini CLI" button.** Gemini CLI's Google login is a browser OAuth that calls back to a loopback port on the CLI; with `NO_BROWSER=1` it prints the URL and asks for the code to be pasted back — but only inside its interactive terminal UI (`gemini -p …` refuses: "Manual authorization is required but the current session is non-interactive"), the TUI redraws the prompt so the URL and the paste-back are not reliably parsable from a pty, and it writes the result into the home of the process rather than a path it can be told. Like OpenCode (ADR-0076), the login is pasted or imported from the user's machine; the card says so, and its import of the login this machine holds (`readHostLogin`) reads `~/.gemini/oauth_creds.json` where the Control Plane runs.

**MCP, instructions, permissions.** Gemini CLI takes the client's MCP servers in `session/new` and `session/load` (stdio; its `mcpCapabilities` also advertise HTTP and SSE) and starts them itself, exposing their tools as `mcp_<server>_<tool>` — the built-in `desktop` and `sessionboxer` servers and the user's reach it this way, nothing is written to `settings.json`'s `mcpServers`. Session instructions are delivered as Gemini CLI's context file: the Sandbox's briefing is the image's `~/.gemini/GEMINI.md` (Gemini CLI reads the global context file in every project, and the project's own `GEMINI.md` on top), and the Session's instructions go into the first prompt (`instructionsDelivery: "first-prompt"`) as for the other ACP agents without a system-prompt hook — `GEMINI_SYSTEM_MD` would replace Gemini CLI's whole system prompt, tool guidance included, and `session/new` takes no `_meta` system prompt. Permissions: the Daemon spawns `gemini --acp --yolo`, `session/new` confirms `currentModeId: "yolo"`, and the Daemon still answers `session/request_permission` with the first "allow" option so a turn never hangs if Gemini CLI asks anyway (it did not in any verified turn).

**Model picker and usage.** `session/new` returns no `configOptions` but a `models` object — `availableModels` (`auto`, then the models the credential may use; an API key saw `gemini-2.5-pro`, `gemini-3.8-flash`, `gemini-3.5-flash-lite`) and `currentModelId` — and `modes` (`default`, `autoEdit`, `yolo`, `plan`). The Daemon turns `models` into the one config option the model picker shows, and a pick goes out as `session/set_model` (`unstable_setSessionModel` in Gemini CLI's ACP client) rather than `session/set_config_option`; the switch takes effect on the next turn (`turn_context.model` and the request path `models/<id>:streamGenerateContent` confirm it). Usage comes back on the prompt result as `_meta.quota.token_count` (`input_tokens`, `output_tokens`) with a `model_usage` breakdown; `usage.ts` reads that snake_case shape next to the standard ACP `usage`, so the composer shows tokens per turn and a hatched bar: Gemini CLI reports no rate windows (`usage_update` never came), the Usage panel points at AI Studio for an API key's quota and at `/stats` in Gemini CLI itself, and `usage.ts` classifies its `RESOURCE_EXHAUSTED`, quota-exceeded and rate-limit errors as a limit.

**Available everywhere.** Node runs on all three guests, so there is no `providerUnavailableIn` row. The macOS base installs the package in `finish()` with the same pinned version (`npm install -g @google/gemini-cli@0.62.0`, `TOOLCHAIN` bumped so existing bases show "Reprovision"), the Windows base in `images/windows/oem/install.bat` next to OpenCode and pi.

## Considered Options

- **`GEMINI_API_KEY` only**: simple and secure, but a key needs an AI Studio project and billing beyond the free tier; a Google login is what most users have and the only way onto a Code Assist subscription. Both are accepted, as for fx.
- **A per-Session volume for `~/.gemini`, as fx got**: unnecessary, Gemini CLI follows the symlink to the tmpfs login and keeps its chat records in the plain directory next to it; a volume would only make the login survive Delete.
- **Writing the MCP servers to `~/.gemini/settings.json`**: unnecessary, Gemini CLI takes them from the client in `session/new` and starts them itself.
- **`GEMINI_SYSTEM_MD` for the Session's instructions**: it replaces the whole system prompt, so Gemini CLI would lose its own tool and safety guidance; the global `GEMINI.md` carries the briefing and the first prompt the Session's instructions, like the other agents without a system-prompt hook.
- **`tools.approvalMode: "yolo"` in `settings.json` instead of `--yolo`**: equivalent; the flag keeps the permission grant visible in the spawn line, and the trusted-workspace variable is needed with either.
- **Driving the Google login from Settings (ADR-0058)**: see above — the flow only exists inside the TUI and leaves its result in the process's home; documented as paste/import, as for OpenCode.
- **Three fields for login file, API key and Vertex**: one field with the kind read from the paste keeps the card as simple as fx's; Vertex is scoped out rather than half-supported.

## Consequences

- Needs an image rebuild (about 175 MB more: the install layer is 173 MB; `sessionboxer/sandbox:dev` went from 6.70 GB to 6.87 GB on the `main` this was built against, and is 8.15 GB with Kimi CLI, GitHub Copilot CLI, Mistral Vibe and Grok Build installed alongside); existing Sandboxes keep working as before (a Daemon that predates this answers "method not found" to the auth push and is logged as such). A macOS base needs Reprovision before it can start Sessions again.
- The login is only as private as `~/.sessionboxer/config.json`, same as the other tokens; it is never in public settings, events, `docker inspect`, Snapshots or logs. A Google login is a long-lived refresh token for the user's Google account: the card says to paste it only on a machine the user trusts, as for Codex.
- A Google login file whose refresh token Google no longer accepts cannot be told from a valid one before the Agent starts: Gemini CLI then prints "Failed to authenticate with authorization code: invalid_grant", falls back to its interactive login prompt on stdout, never answers `initialize` and exits with code 41 after a few retries; the Session shows "ACP connection closed" and the user pastes a fresh login.
- What Gemini CLI advertises over ACP (`0.62.0`, `initialize` in the rebuilt image): protocol version 1; `authMethods` `oauth-personal` ("Log in with Google"), `gemini-api-key`, `vertex-ai` and `gateway` (there is no ACP `authenticate` round trip: the method is `security.auth.selectedType` in `settings.json`); `agentCapabilities` `loadSession: true`, `promptCapabilities` image, audio and embedded context, `mcpCapabilities` HTTP and SSE; no `sessionCapabilities` (no `session/list`, `fork` or `resume`). `session/new` returns `modes` (default/autoEdit/yolo/plan) and `models` as above, followed by an `available_commands_update` with its slash commands. Without a credential `session/new` fails with "Gemini API key is missing or not configured."; an invalid API key gets through `session/new` and fails the turn with HTTP 400 `API_KEY_INVALID` from `generativelanguage.googleapis.com`; a fake Google login file behaves as the previous bullet says.
- `session/load` is advertised but does not restore a conversation in 0.62.0: with the same `~/.gemini`, the same `cwd` and the earlier process's chat record on disk (`~/.gemini/tmp/<project>/chats/session-…-<id>.jsonl`), a new `gemini --acp` answers `session/load` with "Internal error" ("No previous sessions found for this project."), verified by hand in the image and through Stop → Resume in Sessionboxer, where the Daemon logs `session/load failed, creating a new session` and starts a fresh one. The transcript in Sessionboxer stays complete, but after Resume the model no longer sees the earlier turns; a user who needs them repeats what matters in the next prompt.
- Verified without a Google account or API key: typecheck, lint, build, size budget, duplicate scan and the provider-auth/schema/routes/daemon-errors tests; `gemini --acp` in the rebuilt image initialises as above, refuses `session/new` without a credential, and with `GOOGLE_GEMINI_BASE_URL` pointed at a mock that speaks the Gemini `generateContent`/`streamGenerateContent` shape (`scripts/` has none; a 60-line Python server was used) a fake key reaches `session/new`, the `auto` model routes a classifier call to `gemini-3.5-flash-lite:generateContent` and the turn to `gemini-2.5-pro:streamGenerateContent?alt=sse` with the key in `x-goog-api-key`; the mock saw the briefing from `~/.gemini/GEMINI.md`, the `desktop` and `sessionboxer` servers' tools as `mcp_desktop_*`/`mcp_sessionboxer_*`, and a client-supplied stdio server's tool. Through Sessionboxer against the same mock: the Session reached `idle`, the first turn (the prompt the Session was created with) and the following ones streamed the reply into the transcript with per-turn tokens, the login reached the box as a 0600 file on tmpfs behind the symlink with `selectedType` written (a Google login) or as the Agent's environment alone (a key; `docker inspect` shows only `GOOGLE_GEMINI_BASE_URL`), the model picker switched to `gemini-3.5-flash-lite` and the next request went to that model, Stop → Resume came back to `idle` on a new Gemini session (see the `session/load` bullet), Delete removed the container (no volume). Not verified: a real turn on a Google login or a real API key (so the Code Assist model list, quota errors and the token refresh in place — the refresh path is read from Gemini CLI's source, the Daemon's watcher is the one Codex uses), Gemini CLI on the macOS and Windows bases, and whether a later Gemini CLI restores conversations over `session/load`.
